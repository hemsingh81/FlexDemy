Fair

This is a rigorous, decision-dense PRD: the design decisions carry real rationale and named costs, the brownfield grounding (§1.1's verified-against-main table) is unusually honest, and the FRs are testable enough to slice directly into the Appendix C story list. The rubric pass found the risk mechanical rather than conceptual — a self-contradicting DD count in §0, an Assumptions Index that only half round-trips to inline tags, a dangling Appendix A cross-reference (FR-42), and one FR (FR-48) that never lands in a story.

The adversarial pass materially shifts that picture. It went beyond the PRD text and checked the claims against the actual codebase (git show f3131d9, CourseService.MoveToReviewAsync, LifecycleState), and surfaced substantive gaps the rubric pass couldn't see from the document alone: FR-45's new confirmation gate never reconciles with the file-parsed check that exists in code today; a brand-new Confirmation concept collides in name with the existing ReviewConfirmed lifecycle state; the publish/versioning pipeline (heavily rewritten in the same commit that removed the old content tree) is never addressed for the new Page/Resource graph; and Appendix B's entire API is gated to tutor-owned-Draft with no stated access path for student or reviewer consumption of the same resources — a real authorization gap, not a nicety. It also flagged an SVG upload path (FR-42) with no XSS discussion despite FR-48's no-raw-HTML guarantee. These are the kind of findings that argue for a resolution pass before this PRD is treated as build-ready, even though none of them individually break the PRD's structure.

Adversarial review

review-adversarial-general.md

A cynical pass that cross-checked the PRD's claims against the actual codebase rather than treating the document as ground truth. It found the PRD's brownfield narrative in §1.1 undersells the real blast radius of the commit it cites, surfaced an unreconciled conflict between the new confirmation gate and code that exists today, a naming collision on "Confirmation," an internal contradiction in DD-2/FR-5, several data-model and cross-reference gaps, a security gap on SVG uploads, an authorization gap in Appendix B, and understated migration risk. 17 findings total; the most consequential are surfaced below.

Flag

§1.1's "what exists today" table understates f3131d9's actual scope

§1.1
Inspecting the commit itself shows it also deleted the entire AdaptiveLearning/Exercise/AiGateway application slice and substantially rewrote PublishService.cs and VersionService.cs — none of which §1.1 mentions. FR-24 describes a future story "reinstating" AI extraction as if only the staging tables are missing, but the AI gateway infrastructure it would depend on is also gone.
Flag

FR-45's confirmation gate never reconciles with the gate that already exists in code

FR-45
CourseService.MoveToReviewAsync currently blocks Draft→InReview on "at least one uploaded file has successfully parsed" — a check DD-5 makes semantically wrong once uploaded files stop being content. FR-45 never says whether that existing check is replaced, kept, or removed.
Flag

"Confirmation" collides with an existing, unrelated concept of the same name

FR-44 vs LifecycleState
LifecycleState already has ReviewConfirmed, a course-level reviewer-driven action. This PRD introduces an unrelated per-node/per-page Confirmation enum that is tutor-driven. Two different actors, two different granularities, same name, undisambiguated.
Flag

DD-2's "flat page sequence" claim is contradicted by FR-5

DD-2, FR-5
DD-2 claims "the student reader is a flat page sequence, not a recursive renderer." FR-5 has a node's Description render as a section-opening card before that node's first page — exactly the node-aware, hierarchy-sensitive rendering DD-2 claims to avoid.
Flag

FR-10's "What you'll learn" bullet list has no home in the data model

FR-10, Appendix A
Appendix A's Chapter/Topic/Subtopic rows expose exactly one text field (Description) for what FR-10 collects as chapter overview prose plus a separate repeatable bullet list. As written, an engineer cannot determine where the bullets are stored.
Flag

FR-8 + DD-7 leave in-body resource references dangling after a page move

FR-8, DD-7, FR-30
If a page body embeds a reference to an inherited ancestor resource and the page is then moved to a different chapter (FR-8), that resource may no longer be an ancestor. FR-8 only describes the resource panel re-resolving, not what happens to an existing in-body reference. FR-31's in-use guard only fires on explicit deletion, not on a move.
Flag

FR-6's cascade-delete wording omits node-owned resources' fate

FR-6
FR-6 names "their pages and their page-scoped resources" in the cascade but never confirms node-owned (chapter/topic/sub-topic-level) resources are included, or shown in the destruction count.
Flag

FR-42 permits SVG uploads with no XSS discussion

FR-42, FR-48
SVG can carry <script> elements and event-handler attributes. FR-41's malware scan is not the same control as sanitizing scriptable SVG content, and this isn't connected to FR-48's separately-asserted no-raw-HTML guarantee.
Flag

Appendix B has no access path for student/reviewer resource consumption

Appendix B
Every route, including GET /resources/{id}/content, is gated to EnsureOwnedDraftAsync (tutor, owner, Draft-only). FR-46 and UJ-3/UJ-4 assume student- and reviewer-facing access to the same resources, but no route describes that authorization path. A security-relevant gap, not a documentation nicety.
Flag

§6.3 understates migration risk — DD-5 can blank live Draft courses before the backfill ships

§6.3, Appendix C
"Blocking for §6.3 only" glosses over the fact that shipping DD-5's behavior change is not safe independently of the migration decision — Appendix C's migration story (C-11) is listed last, dependent on C-9, with no stated requirement that it ship atomically with or before the DD-5 change.
Flag

The recommended migration option is silently contingent on an assumption flagged unverified elsewhere

§6.3 option 1, FR-20, OQ-4
Option 1 reuses FR-20's section splitter, which is explicitly [ASSUMPTION]-tagged and tied to OQ-4 ("Confirm against real Docling output during dev"). If the heuristic doesn't hold, the recommended one-time backfill produces a bad starting outline for every migrated course — a much bigger blast radius than a single mis-split page in ordinary authoring.
Flag

The publish/versioning pipeline is never addressed for the new content graph

whole doc
PublishService.cs and VersionService.cs were substantially rewritten in the same commit that removed the old content tree. Nothing in this PRD describes how a course publish snapshots or versions the new Chapter/Topic/Subtopic/Page/Resource graph, or how version restore is expected to behave against the new shape.
Flag

FR-44 doesn't define confirmation-reset behavior for a page move

FR-44, FR-8
FR-44's rule is stated per single "immediate parent." Moving a page (FR-8) is a structural edit to two nodes at once, and also re-resolves inherited resources — the PRD never says whether both nodes reset, or whether the page's own confirmation resets.
Flag

The reviewer-rejection path (InReview back to Draft) is never addressed

FR-45, FR-48, UJ-4
FR-48's Draft-only edit guard and FR-45's confirmation gate interact once a course leaves Draft, but UJ-4 only shows the happy path to Review and stops — the PRD doesn't work through what happens when review sends work back, even though the lifecycle already has states for it.
Flag

M-2, M-3 and M-4 lack a measurement window, cohort, or denominator rule

§7
Bare percentages with no defined cohort/time boundary mean two people computing "the" number from the same data could get different answers — unlike M-1 and M-6, which specify "same session" and a concrete failure rate.

DD-6's copy-on-insert stance creates unflagged content staleness

DD-6, UJ-2
UJ-2's edge case has Meera re-extract into a new page after a corrected re-upload, but the original, now-known-wrong page keeps rendering to students indefinitely with no "source file changed since extraction" indicator anywhere in FR-18–FR-24.
