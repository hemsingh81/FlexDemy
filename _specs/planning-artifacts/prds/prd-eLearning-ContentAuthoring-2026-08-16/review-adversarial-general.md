# Adversarial Review — Tutor Content Authoring — Wizard, Pages & Per-Page Resources

- **The §1.1 "what exists today" table is incomplete in a way that misrepresents the size of `f3131d9`.** The PRD frames commit `f3131d9` as removing only the content tree (`Chapter`/`Topic`/`Subtopic`/`ContentBlock`, `ContentTreeController`) and the AI `extractStructure` staging. Inspecting the commit itself (`git show --stat f3131d9`) shows it also deleted `AdaptiveLearningController.cs`, `ExerciseController.cs`, the entire `AdaptiveLearning/` application slice, `AiGateway/IAiGateway.cs`, `IAiTaskGateway.cs`, `AiTaskGateway.cs`, and substantially rewrote `PublishService.cs` (159 lines changed) and `VersionService.cs` (199 lines changed). FR-24 casually describes a future story that "reinstates" the AI structure-extraction pipeline as if the staging tables are the only missing piece — but the AI gateway infrastructure it would depend on is also gone. A reader relying on §1.1 as ground truth will underestimate that follow-on work.

- **FR-45's confirmation-based "Move to Review" gate doesn't reconcile with the gate that already exists in code.** `CourseService.MoveToReviewAsync` currently blocks the Draft→InReview transition on "at least one uploaded file has successfully parsed" — a comment in the source even calls this "the simplest honest replacement" for the old confirmation-scoped gate that was removed with the tree. DD-5 makes uploaded files non-content ("a source, not content"), which makes this existing gate semantically wrong once this PRD ships, yet FR-45 never says whether the file-parsed check is replaced, kept as an additional guard, or removed. "Replaces a generic 'content not ready' message" implies the author knew about the existing check but didn't actually resolve what happens to it.

- **"Confirmation" is a new term colliding with an existing, unrelated concept of the same name.** `LifecycleState` already has `ReviewConfirmed`, produced by `CourseService.ConfirmReviewAsync` — a course-level, presumably reviewer-driven action. This PRD introduces a completely different per-node/per-page `Confirmation` enum (`Unconfirmed`/`Confirmed`) that is tutor-driven sign-off (FR-44). Two unrelated actors, at two different granularities, both called "confirm/confirmed," in the same codebase, are not disambiguated anywhere in the PRD — a real source of confusion in code search, API naming, and support conversations ("is this course confirmed?").

- **DD-2's central claim — "the student reader is a flat page sequence, not a recursive renderer" — is contradicted by FR-5 two paragraphs later.** FR-5 has a node's Description render "as a section-opening card before that node's first page," which is content interleaved with pages, keyed to outline position. That is exactly the kind of node-aware, hierarchy-sensitive rendering DD-2's rationale claims to avoid. The PRD should either drop the "flat sequence" claim or admit the reader has to walk the outline, not just a page list.

- **FR-10's "What you'll learn" bullet list has no home in the data model.** FR-10 (Step 1 of the wizard) collects "an optional repeatable 'What you'll learn' bullet list" in addition to the chapter overview. Appendix A's `Chapter`/`Topic`/`Subtopic` rows expose exactly one text field for this purpose — `Description`. Either the bullets are meant to be serialized into the same Markdown-lite `Description` string as the overview prose (undocumented, and in tension with FR-4's "paragraphs and bullets only" cap of 2,000 chars) or a field is missing from Appendix A. As written, an engineer implementing Appendix A literally cannot store what FR-10 collects.

- **FR-42 cites Appendix A for a "bounded extension allowlist" for code/text resources that Appendix A does not contain.** Appendix A's data model sketch and "Suggested bounded limits" list chapter/topic/page/resource counts and size caps, but no file-extension list of any kind. This is a dangling cross-reference — a concrete, checkable defect, not a matter of opinion.

- **FR-8 (move a page to a different node) and DD-7 (resources are visible down the tree, never up) leave inline resource references dangling after a move.** DD-7 says a resource attached to an ancestor node is visible only to descendants; FR-30 allows page body blocks to reference any visible resource by `resource:{resourceId}`, and FR-36 shows inherited resources in the panel a tutor inserts from. If a page's body embeds `![alt](resource:{ancestorResourceId})` for a resource inherited from its *current* chapter, then the page is moved to a different chapter (FR-8), that resource is no longer an ancestor of the page — the reference is now to a resource the page can no longer see. FR-8 only says "inherited node resources are re-resolved against the new ancestry," which describes the resource *panel*, not what happens to an existing in-body reference that pointed at a since-un-inherited resource. FR-31's in-use guard only fires on explicit resource deletion, not on a move that silently orphans the same reference.

- **FR-6's cascade-delete wording only names "page-scoped resources," leaving node-owned resources' fate unstated.** "Deleting a node cascades to its descendants, their pages and their page-scoped resources" does not say what happens to the deleted node's *own* resources (chapter/topic/sub-topic-level attachments) or to descendant nodes' own resources, as distinct from their pages' resources. Appendix A's polymorphic `Resource.OwnerType {Chapter|Topic|Subtopic|Page}` implies node-owned resources are a first-class case, but FR-6 doesn't confirm they're included in the cascade or the destruction count shown to the tutor ("3 topics, 7 pages, 4 resources" — no "2 chapter-level resources" line item).

- **FR-42 permits `svg` uploads with zero discussion of SVG's script/XSS surface, despite FR-48 loudly asserting a no-raw-HTML guarantee elsewhere.** SVG is not a passive image format — it can carry `<script>` elements and event-handler attributes. FR-41 covers malware scanning (ClamAV-style) but that is not the same control as sanitizing or refusing scriptable SVG content before it is served back as an "Inline" resource or opened directly via `GET /resources/{id}/content`. The PRD asserts the Markdown renderer itself never emits raw HTML, then separately allows a file type that can carry executable content through a completely different code path, without connecting the two.

- **Appendix B's API surface is entirely gated to `EnsureOwnedDraftAsync` (tutor, owner, Draft-only), but the PRD elsewhere assumes student- and reviewer-facing access to the same resources.** FR-46 requires "Preview as student" to render "through the same component path the student player uses," and UJ-3/UJ-4 describe students downloading attachments and a course moving through Review/Published states. None of Appendix B's routes — including `GET /resources/{id}/content`, the one that actually serves bytes — describe an authorization path for a non-owner, non-Draft context. As written, the only access-control story in the document would make student consumption of a published course's resources impossible, which can't be the intent, but the PRD never states what the real rule is (published + enrolled? published + public? signed URL with its own expiry?). That's a security-relevant gap, not a documentation nicety.

- **§6.3's claim that OQ-1 is "blocking for §6.3 only" understates real migration risk.** DD-5 changes what a Draft course renders the moment it ships (parsed files stop being shown as content). If DD-5 and the outline/page features ship before the chosen backfill (option 1, 2, or 3) is built and released, any existing Draft course with parsed files and no pages goes blank in production during that gap — the PRD's own §6.3 opening line says as much ("will render as empty") but the "in scope" list in §6.1 and the story slicing in Appendix C (C-11, migration, listed last, dependent on C-9) don't call out that C-11 needs to ship atomically with — or before — the DD-5 behavior change, or be hidden behind a flag until it does. "Every other part of this PRD can be built while [OQ-1] is open" glosses over the fact that shipping the DD-5 behavior itself is not safe to do independently of the migration decision.

- **The recommended migration path (§6.3 option 1) is silently contingent on an assumption the PRD itself calls unverified elsewhere.** Option 1 "reuses FR-20's section splitter," and FR-20's splitting rule is explicitly flagged `[ASSUMPTION]` and tied to open question OQ-4 ("Confirm against real Docling output during dev"). If that heuristic doesn't hold across real parsed files, the recommended one-time backfill produces a bad starting outline for every migrated course, which is a much bigger blast radius than a single mis-split page during ordinary authoring. §6.3 doesn't mention this dependency or suggest validating the splitter against production-shaped documents before committing to option 1 as "recommended."

- **The publish/versioning pipeline is never mentioned, despite being the actual mechanism that makes content live for students, and despite being heavily touched by `f3131d9`.** `PublishService.cs` and `VersionService.cs` were substantially rewritten in the same commit that removed the content tree, and `ReturnToDraftAsync`'s comment references `RestoreVersionAsync` as "the distinct operation that replaces content." Nothing in this PRD — not the FRs, not Appendix A, not Appendix B — describes how a course "publish" snapshots or versions the new Chapter/Topic/Subtopic/Page/Resource graph, or how `RestoreVersionAsync` is expected to behave against the new shape. For a PRD whose entire purpose is to define what a student ultimately sees, silence on how that gets captured at publish time is a real scope gap, not an implementation detail to defer.

- **FR-44 doesn't define confirmation-reset behavior for a page move (FR-8), which touches two nodes at once.** FR-44's rule is stated per single "immediate parent." Moving a page from Node A to Node B is simultaneously a structural edit to A (losing a child) and to B (gaining a child), and per FR-8 it also re-resolves the page's own inherited resources. The PRD never says whether both A and B reset to Unconfirmed, whether the moved page's own confirmation resets, or whether only the destination is affected — an ambiguity a story writer will have to invent an answer to, exactly the kind of thing DD-1 says an FR shouldn't leave to improvisation.

- **The interaction between confirmation-gated review and the existing Draft-only edit guard is unaddressed.** FR-48 states ownership + Draft-state guards apply "to every mutation," and `EnsureOwnedDraftAsync` throws once a course leaves `Draft`. FR-45 blocks moving to Review while anything is `Unconfirmed`. But nothing describes the reviewer-rejection path: once a course is `InReview`, can the tutor still fix content (the guard says no, Draft-only), and is `ReturnToDraftAsync` a precondition for addressing reviewer feedback? UJ-4 only shows the happy path to Review and stops there — the PRD doesn't work through what happens when review sends work back, even though the lifecycle already has states for it.

- **Success metrics M-2, M-3 and M-4 are stated as bare percentages with no measurement window, cohort, or denominator refresh rule, making them untestable as written.** "≥ 60% of authored pages contain at least one non-paragraph block" — measured once at some fixed date, as a rolling window, per tutor, per course, including pages later deleted or still in Draft years from now? Without a defined cohort and time boundary, any two people computing "the" number from the same data will get different answers, and the metric can't be adjudicated pass/fail at ship time the way M-1 and M-6 (which do specify "same session" and a concrete failure rate) can.

- **DD-6's "never a live link" stance is presented as a clean resolution but sidesteps the resulting content-staleness problem it creates.** UJ-2's edge case has Meera re-upload a corrected PDF and says she "re-extracts into a new page" to get the corrections — but this means the original (now known-wrong) extracted text keeps rendering to students on the original page indefinitely, with no flag, warning, or "source file changed since extraction" indicator anywhere in FR-18–FR-24. DD-6's rationale ("a tutor... must never have it clobbered by a background job") is a reasonable argument against silent overwrite, but the PRD doesn't even name the weaker, cheaper alternative it's implicitly rejecting — a non-destructive staleness notice — it just asserts copy-on-insert and moves on.
