# Architecture Feasibility Review — New Course Wizard

## Overall verdict

Buildable, and §4.1's FR-1–FR-5 are coherent enough for an architect to start designing the gateway from — no incoherence there, just normal build-time decisions correctly left open. The real risk is everything the async publish mechanics (FR-21/FR-24, and the multi-file async pipeline in FR-11–FR-13) quietly require: durable job/task state and a worker execution model that neither architecture spine establishes anywhere (the backend spine's own Deferred section explicitly punted "AI microservice pipeline" and the Docker Compose envelope has no worker/queue service). That, plus a real tension between FR-2's "no redeploy" promise and the self-hosted LiteLLM-class posture's typical file-driven config model, are the two items that should block sign-off until an architecture doc addresses them explicitly — not because the PRD is wrong to want them, but because they're genuine new infrastructure, not a hand-wave-able detail.

### Findings

- **high** Async publish batch (§4.10 FR-21, §4.11 FR-24) implies job/worker infrastructure absent from both architecture spines (§4.1/§4.10) — FR-21 requires a `Publishing` sub-state that only flips to `Published` once a background batch finishes generating Drill-Down/Way content for every confirmed node, with per-node failure tracked and independently retryable ("until its batch entry is retried"). That needs durable, queryable job/task state and a worker execution model. The backend spine's AD-3 establishes only plain synchronous `I{Feature}Service` calls (no mediator, no pipeline), and its Deferred section explicitly says the AI pipeline is "likely its own Infrastructure-layer client... or a separate service, decided when that feature is scoped" — i.e., this decision has never been made. AD-13's Docker Compose envelope has exactly three services (`postgres`, `api`, `web`); no worker container, no Redis, no queue. FR-11–FR-13's async multi-file upload/parse/extract pipeline (independent per-file status, independent retry) is the same shape of problem, reinforcing that this is a real, load-bearing addition, not an edge case. *Fix:* the architecture doc must explicitly decide the execution model (in-process `IHostedService`/`BackgroundService` vs. a durable job library like Hangfire with its own Postgres-backed storage vs. an external queue) and, if it needs new infra (Redis, a worker container, new Postgres tables for job/batch state), add it to the deployment envelope — this is squarely an architecture-phase decision, but the PRD should flag it as a known infra addition rather than leaving it implicit inside "asynchronous... background job."

- **high** FR-2's "no redeploy" commitment isn't reconciled with the self-hosted (LiteLLM-class) phase's typical config model (§4.1 FR-2, FR-5, FR-29) — FR-5 requires prompt/model config to live in "one centralized, versioned location," and FR-2/FR-29 both promise a provider/model or threshold change "takes effect for the next request... no redeploy." Neither FR nor the addendum specifies *where* that config is persisted. Managed gateways (OpenRouter/Portkey) expose this via API/dashboard already, so phase 1 is fine. But LiteLLM-class self-hosted proxies are conventionally configured via a static `config.yaml` — changing routing/model/budget settings there typically means restarting or reloading that process, which is a real operational discontinuity even if it's not "feature code" redeploy in the strict FR-1 sense. If the self-host phase is implemented against LiteLLM's DB-backed virtual-key/model management (Postgres-backed admin API) instead of static YAML, this is a non-issue — but the PRD doesn't commit to that, and it's the kind of decision that changes what "self-hosted, no redeploy" actually buys. *Fix:* either the PRD or the follow-on architecture doc should state explicitly that the self-hosted gateway's config store must support runtime (DB/API-driven) updates, not file-based config requiring a process restart, so FR-2/FR-29's "no redeploy" guarantee survives the phase-2 migration.

- **medium** FR-3/FR-29's fallback and budget-threshold behavior are described as a "base-URL/key change, not a rewrite" migration, which understates the real cost (§4.1 FR-2, FR-3, FR-29; addendum "AI Gateway: Options Considered") — that claim is accurate for a plain chat-completion call (OpenAI-compatible surface), but FR-3's cross-provider fallback chains and FR-29's per-task budget enforcement are gateway-native features whose configuration format differs between OpenRouter/Portkey and LiteLLM. Migrating from managed to self-hosted means re-authoring fallback and budget policy against a different config schema, not just swapping a base URL — a real, if bounded, migration cost the PRD's committed two-phase posture should own rather than imply away. *Fix:* note in the PRD (or defer explicitly to architecture) that FR-3/FR-29's routing and budget config are gateway-specific and will need re-authoring at the phase-2 migration, distinct from the "just a base URL/key" framing used for basic completions.

- **medium** FR-16's golden-file visual-regression suite is new CI/testing infrastructure not covered by either spine's testing conventions (§4.5 FR-16) — the frontend spine's AD-5 fixes the test stack as `vitest` + `@testing-library/react` + `jsdom`, which is DOM-assertion testing, not pixel-level rendering — it cannot produce or diff a golden-file screenshot. FR-16 requires "a golden-file (visual-regression) diff test suite... for editor-vs-student-view rendering for math, chemistry, and Hindi-script content" with PR-blocking behavior on drift. That's a genuinely different tooling category (e.g., Playwright + pixel-diff, or a hosted visual-regression service) with its own CI runner and baseline-image storage/update workflow. *Fix:* the architecture doc should pick and scope this tooling explicitly rather than let it fall out of AD-5's existing (DOM-only) test convention.

- **medium** FR-25's post-publish versioning has an unsized data-modeling question (§4.11 FR-25, interacting with §4.10 FR-21) — "prior published state retained as a version" plus FR-21's per-node cached Drill-Down/Way content means every republish must decide whether it deep-copies the entire confirmed content tree (all Chapters/Topics/Subtopics/Content Blocks) plus its cached AI content, or uses a lighter diff/audit-log approach. The PRD's testable consequences ("a prior published version remains retrievable") are satisfiable either way, but the storage/complexity cost differs by an order of magnitude between the two, and nothing in the PRD or either spine picks one. Not a blocker to starting architecture, but real design work with real storage-growth implications that should be explicitly scoped rather than discovered mid-build.

- **low** DrilldownPanel.tsx reuse claim is accurate only for FR-17; FR-18/19/20's UI surfaces aren't confirmed to exist there (§0, §4.6–§4.9, §5) — the PRD's framing ("reuses the existing DrilldownPanel.tsx UI... wiring it to AI-generated content") is correct for FR-17's level-gated reveal, which the component already implements with mock data. FR-18 ("Ways" as a secondary-menu entry point relative to Drill-Down), FR-19 (exercises), and FR-20 (keyword popovers) are not described anywhere (PRD or addendum) as already present in DrilldownPanel.tsx's current shape — they read as net-new UI that will live alongside or be added to that component, not literal reuse. Non-blocking, but the UX/architecture pass should treat §4.7–§4.9 as new surfaces rather than assume they're "already built, just wire data."

- **low** ReaderCanvas.tsx's existing fake "Ask AI" affordance is never assigned to an FR (addendum "Repository prior art"; §4.9 FR-20) — the addendum notes `ReaderCanvas.tsx` has a simulated `handleAskLevelLLM` (hardcoded response, no network call) "to be replaced by real AI Service Layer calls," but no FR in the PRD body claims this surface. It's unclear whether this fake affordance is meant to become FR-20 (keyword definitions), a distinct feature this PRD doesn't otherwise scope, or is left as dead/fake code alongside newly-real AI elsewhere in the same view. *Fix:* the PRD or architecture doc should explicitly state ReaderCanvas's disposition — folded into FR-20, replaced by something else, or explicitly out of scope for this pass.

- **low** Tags admin CRUD's relationship to MasterDataManager is unstated (§4.2 FR-7, §4.12 FR-26) — FR-8 (Taxonomy) explicitly reuses MasterDataManager/masterDataService for Country→State→City→Board→ClassLevel→Subject; FR-26 (Tag CRUD) is described as a separate admin feature but never states whether it's a new "master data type" plugged into MasterDataManager's existing generic scaffold or an entirely separate admin surface to build from scratch. If MasterDataManager is taxonomy-specific rather than a generic master-data framework, FR-26 is unscoped net-new work currently framed only as "Admin — Tag Management" with no reuse note at all. Worth a one-line clarification before the architecture pass.

- **low** FR-29's real-time budget-gating on a high-volume task implies a concurrency-safe usage counter on the hot path (§4.13 FR-29, §4.9 feature NFR) — blocking a request that "would exceed a configured hard threshold" requires reading current spend before every call, and `defineKeyword` is explicitly called out as high-volume. Many concurrent `defineKeyword` calls checking/incrementing the same per-task counter is a real (if standard) concurrency design point — not a blocker, but worth the architecture doc naming the mechanism (e.g., atomic DB counter, cached running total with periodic reconciliation) rather than leaving "blocks routing... before it's exceeded" as an implied instant, perfectly-consistent check.
