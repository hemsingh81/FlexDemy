# PRD Quality Review — Centralized Error Observability & Management

## Overall verdict

This is an unusually rigorous PRD — nearly every FR carries testable consequences, assumptions are consistently tagged and indexed, and the addendum grounds every mechanism in real, cited code. It holds up well on strategic coherence, scope honesty, and shape fit for a single-operator internal tool. What's at risk: a genuine FR-vs-FR contradiction between FR-7 (client error reporting must work unauthenticated) and FR-19 (Master-only policy gates "the new controller"), which as literally specified would silently break frontend crash capture for every non-Master/anonymous user — undermining SM-1's own 100%-coverage claim. A second, quieter issue is that FR-10's blanket P0 for any "Data Integrity Error" (which per the addendum maps to routine `ConflictException` 409s like duplicate tag names) risks flooding the P0 queue and defeating the triage premise the whole priority system is built on — a debatable call that wasn't flagged as an assumption the way comparable judgment calls elsewhere in the PRD were.

## Decision-readiness — adequate

Trade-offs are named explicitly and well throughout: FR-17's Assumptions Index entry states plainly "no manual decrease and no jump-to-any-level in v1... there's currently no way to correct that downward except Archive/Resolve," FR-14's Archive-not-Delete substitution is justified against named industry precedent rather than asserted, and three `[NOTE FOR PM]` callouts land at real tensions (estimation risk in §4.6, the alerting non-goal in §5, and the GDPR/data-subject-deletion gap in Constraints and Guardrails) rather than safe checkpoints. The five Open Questions are genuinely open, not rhetorical.

### Findings
- **high** Blanket P0 for "Data Integrity Error" is a live design call presented as settled, unlike comparable judgment calls elsewhere that were tagged `[ASSUMPTION]` (§4.5 FR-10, rule 1: "the ErrorRecord's Category is Data Integrity Error" → automatic P0). Per FR-9's table and the addendum's real throw-site list, `ConflictException` — the exception type that drives Data Integrity Error — is thrown from `TagService.cs` and `UserService.cs`, which by REST/409 convention is typically a routine business-rule conflict (e.g., duplicate tag name), not data corruption. Auto-escalating every such conflict to the same P0 tier as a Critical Path outage risks flooding the priority-1 queue with routine noise, which directly undercuts the JTBD this feature exists to serve ("failures ranked by how bad they are... so I can spend my limited attention on what actually matters," §2.1) and SM-3's triage-throughput premise. Other equally debatable rules (the spike threshold, the Critical Path starting list) got `[ASSUMPTION: ... confirm before build]` treatment; this one didn't. *Fix:* Either tag this as an `[ASSUMPTION]` pending confirmation, or narrow the rule (e.g., only DB constraint-violation exceptions, not all `ConflictException` call sites, drive automatic P0).

## Substance over theater — strong

The single-persona JTBD framing (§2.1–2.2) is deliberate and self-aware ("journeys are kept light per the PRD's own scope dial guidance," §2.3) rather than padding, the Vision statement (§1) is anchored in a specific, dated incident ("diagnosing a real production issue this session required manually reading Docker container logs by hand") that couldn't swap into another PRD, and the "not a full APM/tracing platform" framing keeps the ambition honest rather than inflated. No findings.

## Strategic coherence — strong

The thesis — "no failure goes unseen," closing specifically-confirmed gaps (§1) — drives feature sequencing cleanly: capture (4.1–4.2) → data model (4.3) → categorization/priority (4.4–4.5) → admin surface (4.6) → lifecycle (4.7) → access control (4.8). Success Metrics validate the thesis directly rather than measuring activity (SM-1 silent-failure coverage, SM-2 time-to-visibility) and SM-C1 explicitly counter-balances the temptation to game SM-1/SM-3 by mass-archiving without fixing anything — exactly the kind of counter-metric the rubric looks for. No findings.

## Done-ness clarity — adequate

The FR-level rigor is a standout: nearly all 19 FRs carry explicit, testable "Consequences" (e.g., FR-1: "still returns the existing catch-all 500 `ProblemDetails` response... AND produces exactly one new ErrorRecord"). That said, two real gaps sit underneath this strength.

### Findings
- **critical** FR-7 and FR-19 contradict each other on authentication. FR-7 requires that client error reporting work without authentication: "a failure to report an error must never itself surface as a visible error to the user... if not [authenticated] (e.g. a crash on the login screen itself), the ErrorRecord is still created with `UserId = null` — reporting is not gated behind authentication." FR-19 states: "A new `FeatureKeys.ErrorsManage` policy gates **the new controller** and every write action on it (`[Authorize(Policy = FeatureKeys.ErrorsManage)]`), seeded as a Master-only row." The addendum's RBAC wiring section reinforces this without disambiguating: "New controller: `[Authorize(Policy = FeatureKeys.ErrorsManage)]` at class level, mirroring `AiConfigController.cs`/`AiUsageController.cs` exactly." Neither the PRD nor the addendum states that `POST /api/v1/errors/client` (FR-7) lives on a separate, non-Master-gated controller from the admin Error Log actions (FR-11–FR-18). If built literally as described, a class-level Master-only `[Authorize]` on "the new controller" would 403 every anonymous or non-Master crash report — silently breaking FR-7's entire purpose and directly contradicting SM-1's claim that "100% of... all frontend runtime errors produce an ErrorRecord." *Fix:* Add one clarifying sentence to FR-19 (or the addendum's RBAC section) stating that the client-reporting endpoint (FR-7) is a separate, unauthenticated-eligible endpoint/controller, explicitly excluded from the `ErrorsManage` policy.
- **medium** FR-8 and FR-14 contradict each other on Fingerprint uniqueness. FR-8 states the model "persists **one row per distinct Fingerprint**, incrementing occurrence data on repeat rather than duplicating rows." FR-14 then carves out an exception without reconciling it: "a new occurrence of an archived Fingerprint creates a **new** ErrorRecord rather than reopening the archived one." An engineer reading only FR-8's NFR ("index `Fingerprint`... at minimum") could reasonably add a unique constraint on `Fingerprint`, which would break FR-14's behavior outright. *Fix:* State explicitly in FR-8 (not just FR-14) that Fingerprint uniqueness holds only among non-`Archived` records, and adjust the indexing guidance accordingly (e.g., a partial/filtered unique index, or no uniqueness constraint at all).
- **medium** Performance/scale NFRs rely on adjectives instead of bounds, which the rubric flags explicitly. FR-1's NFR: capture "must not add meaningfully to response latency" (no number). FR-8's NFR: "Query performance... must remain acceptable at realistic volume" (no target latency, no volume figure). The Cross-Cutting NFRs section repeats the pattern: "negligible overhead," "remain responsive." Contrast this with FR-10's spike-threshold rule, which gives a concrete placeholder number (10x/24h/1h) even while flagging it as unconfirmed — the same treatment is missing here. *Fix:* Give even a placeholder bound (e.g., "p95 write overhead < 20ms," "responsive at 100k active records") tagged `[ASSUMPTION: ... confirm before build]`, matching the pattern already used elsewhere in this PRD.

## Scope honesty — strong

§5's Non-Goals section does real work (7 explicit non-goals, several with rationale and a `[NOTE FOR PM]` flagging the alerting deferral as a likely v2). All 6 inline `[ASSUMPTION]` tags round-trip cleanly to §9's Assumptions Index (verified: Critical Path list, fire-and-forget capture, rule-based-not-AI categorization, spike threshold, one-way Increase Priority, 180-day retention — each appears exactly once inline and once in the index).

### Findings
- **medium** Open-items density (5 Open Questions + 6 `[ASSUMPTION]` tags + 3 `[NOTE FOR PM]` = 14 markers) is high relative to a PRD paired with an implementation-ready addendum containing exact file paths, real code snippets, and wiring steps — i.e., this reads as close to green-light-to-build. None of the 14 are individually inflated (each is narrow and concrete — a threshold, a list, a binary choice), but several are true build-blockers (OQ-1 Critical Path completeness, OQ-4 retention window, OQ-5 spike threshold) that should be resolved in a short confirmation pass before implementation starts rather than discovered mid-build. *Fix:* No structural change needed — flag these three as the must-resolve-before-sprint-planning subset when this PRD is handed off.

## Downstream usability — strong

The Glossary (§3) is precise and every term is used with consistent casing throughout (spot-checked `ErrorRecord`, `Fingerprint`, `Critical Path`, `Category`/`Priority`/`Status`). FR IDs (FR-1–FR-19) are contiguous with no gaps or duplicates; cross-references resolve correctly (e.g., the Glossary's `Occurrence` entry points to §6.2, which does contain "Per-occurrence detailed audit trail (only aggregate counts in v1)"). The PRD/addendum split is disciplined — technical-how (real class names, exact wiring steps) is consistently pushed to the addendum rather than bleeding into the capability narrative.

## Shape fit — strong

This is correctly shaped as a capability spec for a single-operator internal tool: one JTBD-driven persona, one representative UJ explicitly justified as sufficient ("journeys are kept light... one representative journey," §2.3), SMs that are operational rather than user-facing vanity metrics. The addendum's brownfield grounding is a particular strength — it doesn't just assert architectural fit, it demonstrates it with real file paths, exact class/field names, and actual retry-exhaustion code (`ScanFileJob.cs`), giving downstream architecture work concrete hooks rather than hand-waving.
