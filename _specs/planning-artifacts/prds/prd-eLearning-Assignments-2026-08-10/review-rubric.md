# PRD Quality Review — Assignments (Merged into Dashboard)

## Overall verdict
This PRD is structurally strong and unusually well grounded in the actual codebase (every file/type reference — `AssignmentsView.tsx`, `useAssignments.ts`, `QuizQuestion`, `DEFAULT_VISIBLE_TABS`, `CourseOverviewScreen.tsx`'s scroll pattern — checks out against source). Its genuinely-new FRs (creation, visibility mode, review/re-evaluate) mostly carry real testable Consequences, which is the right instinct for a PRD with no prior behavior to fall back on. But two things undercut it: the Glossary promises a "standalone" Tutor-assignment target that no FR ever implements or resolves how it reaches students, and the gamification/points mechanic (central to the existing auto-grade flow this PRD explicitly reuses) is left undefined for the two newest paths — Hold-then-reviewed reveal and Re-evaluate. Combined with zero inline `[ASSUMPTION]`/`[NOTE FOR PM]` tags despite an Assumptions Index and several real judgment calls, this PRD is buildable but has load-bearing gaps precisely in the new capability it was written to spec.

## Decision-readiness — adequate
Trade-offs are mostly named honestly: FR-12's Out of Scope bullet states the actual workflow cost of the decision ("a tutor who needs to fix a published assignment un-publishes... first") rather than hiding it, and §5 Non-Goals is a real list, not a fig leaf. Open Questions 2 and 3 are genuinely open (vocabulary, Draft-preview visibility) with defaults documented as assumptions, not rhetorical.

Open Question 1, however, is not genuinely unresolved — it's answerable today by reading the codebase the PRD already cites elsewhere. `CoursePlayer.tsx` (lines 305–311) already renders a "Take Quiz" button wired to `onOpenAssignment` whenever `currentLesson.assignment` exists — i.e., a second entry point into a lesson's embedded quiz already exists today, independent of the standalone Assignments tab being retired. The PRD's own Non-Goals bullet (§5) defers this to "an open question (§8)... needs a build-time check against `CoursePlayer.tsx`" — but that check is a two-minute grep, not a build-time discovery, and the PRD does exactly this level of check elsewhere (e.g., confirming `QuizQuestion` reuse for the Assumptions Index). Given the PRD is otherwise disciplined about grounding claims in code, this one reads as skipped rather than truly unknowable.

### Findings
- **medium** Open Question 1 is answerable by inspection, not genuinely open (§8 Q1, §5 last bullet) — `CoursePlayer.tsx` already has a "Take Quiz" entry point (`onOpenAssignment`, lines 305–311) gated on `currentLesson.assignment`. The PRD treats this as unknown pending a "build-time check" when the same grep used to verify other claims in this PRD would have resolved it. *Fix:* Resolve now — decide whether the in-lesson "Take Quiz" button stays as a second access path or redirects into the new unified Dashboard list, and turn this into a stated decision (or an explicit `[NOTE FOR PM]` if the tradeoff needs stakeholder input) rather than an open question.
- **medium** No `[NOTE FOR PM]` callouts anywhere in the document, despite several real judgment calls in genuinely new territory — e.g., FR-12's "un-publish to edit" workflow (a real usability cost imposed on tutors), the Draft-invisibility assumption (§9, tied to Open Question 3), and the standalone-Tutor-target gap (see Done-ness finding below). The sibling base PRD (`prd-eLearning-2026-08-10/prd.md` §4.1 FR-3) uses `[NOTE FOR PM]` at exactly this kind of judgment-call site; this PRD has zero. *Fix:* Add `[NOTE FOR PM]` at FR-12's Out of Scope bullet and at the standalone-target gap, flagging them as decisions worth a second look post-launch.

## Substance over theater — strong
No findings. Two personas (Student, Tutor), both drive real decisions (visibility mode, review/re-evaluate, source badges) — no persona padding. The Vision statement (§1) is specific to this product's actual current brokenness ("submit a quiz and the result evaporates on reload") rather than swappable boilerplate. The Cross-Cutting NFRs (§4.6) name specific files and mechanics (`AssignmentsView.tsx`'s grading logic, `useAssignments.ts` flattening course data) instead of generic "must be scalable/secure" filler — this is NFR substance, not theater.

## Strategic coherence — strong
No findings. The thesis is explicit and singular: turn Assignments from an ephemeral, course-only picker into a persistent, multi-source system with tutor authorship (§1). Every FR traces back to either the persistence half (My Submissions, Submission Status) or the authorship half (creation, visibility mode, review/re-evaluate) of that thesis — no orphaned capabilities. SM-C1 (§7) is a genuine counter-metric, not decoration: it explicitly counterbalances SM-1's parity pressure by protecting Source-badge visibility, which is exactly the kind of "metric a team might quietly erode while chasing the primary metric" the rubric is looking for.

## Done-ness clarity — thin
This is the dimension the task flagged for extra scrutiny, and it's where the PRD's new-capability FRs show real gaps — not everywhere, but in specific, costly spots.

The Glossary (§3) defines Assignment Source "Tutor" as "created by a tutor and linked to one of their courses, **or standalone**" — but no FR ever implements the standalone case. FR-10 (creation form) only offers two targets: "link to one of their own courses, or flag 'Open / Competition.'" FR-5 (Available Assignments) says "Tutor-source items only appear for assignments Published... and targeted at a course the student is enrolled in" — which structurally requires every Tutor-source assignment to have a course target, contradicting the Glossary's "or standalone" clause. A standalone (non-course-linked, non-Competition) Tutor assignment has no defined audience anywhere in §4, so it's unbuildable as specified. This is exactly the kind of ambiguity the task warned is more costly here than in a restructuring PRD — there's no existing "standalone tutor assignment" behavior to fall back on.

The points/gamification mechanic — central to the existing auto-grade flow this PRD explicitly reuses (§4.6: "the single implementation backing all three Sources") — is only specified for the Immediate-visibility path. FR-7 explicitly carries forward "confetti/points threshold at ≥70%." But FR-14 (Review action, Hold path) says only that "the score becomes visible to the student" — silent on whether `awardPoints()`/confetti fire at that moment, or ever, for a Hold submission. FR-15 (Re-evaluate) is silent on whether overriding an already-published score adjusts points already awarded. Since Hold and Re-evaluate are both brand-new paths with no existing behavior to imply an answer, this is a real acceptance-criteria gap, not a stylistic one.

Several new-capability FRs also lack the Consequences block the PRD's own convention note (§4 preamble, line 64) promises: "new FRs need their own explicit acceptance criteria, which are included below." FR-4 (My Submissions), FR-9 (My Assignments list), and FR-13 (Submissions view) have no Consequences — sort order, empty states (e.g., a Published assignment with zero submissions, distinct from UJ-2's "Draft has zero submissions by definition" edge case), and score-formatting details are left to prose-inference only.

### Findings
- **high** Standalone Tutor-source assignments are defined in the Glossary but not implemented by any FR (§3 vs FR-5, FR-10) — see above. *Fix:* Either drop "or standalone" from the Glossary's Tutor Source definition (if v1 truly requires a course link), or add a target option and an audience rule (e.g., "visible to all of this tutor's students across all their courses") to FR-10/FR-5.
- **high** Points/confetti behavior undefined for Hold-then-Reviewed reveal (FR-14) and Re-evaluate (FR-15) — no existing behavior to imply an answer since both paths are new. *Fix:* Add a Consequences line to FR-14 stating whether `awardPoints()`/confetti fire on Review, and to FR-15 stating whether Re-evaluate adjusts previously-awarded points.
- **low** FR-4, FR-9, FR-13 lack Consequences blocks despite the PRD's stated convention that new FRs get explicit acceptance criteria (§4 preamble) — sort order and empty-state behavior are unspecified. *Fix:* Add a one-line Consequences bullet to each covering ordering and the empty-state case.

Open-items density (3 Open Questions, 5 Assumptions Index entries, 1 NON-GOAL tag) is proportionate for an internal-tool-shaped, non-green-light-to-build-blind PRD.

## Mechanical notes

This PRD's assumptions are traceable only via the Open Questions section and the index itself, not from the FR/Glossary text where they apply. Not blocking, but it weakens the index's purpose as an at-a-glance flag for a reader scanning §3/§4 directly.
- No `[NOTE FOR PM]` tags anywhere (see Decision-readiness finding above) — flagged there since it affects the substance of what got surfaced, not just the mechanics.
- No glossary drift or ID gaps otherwise observed. "Open / Competition" (FR-10 form copy) vs. "Competition" (Glossary term) is a minor label variance, not a substantive drift — likely fine as UI copy vs. formal term, but worth a one-line note if a UX spec inherits this PRD's copy verbatim.
