- (decision) AD-1 [ASSUMPTION] Paradigm: Clean Architecture / Onion with 4 projects -- LearnSphere.Domain (entities, value objects, domain rules, zero project references), LearnSphere.Application (use-case interfaces + services + DTOs, references only Domain), LearnSphere.Infrastructure (EF Core/Npgsql, external services, implements Application interfaces, references Application+Domain), LearnSphere.Api (controllers, middleware, composition root, references Application+Infrastructure). Binds: whole BackEnd/src tree. Prevents: a controller or use-case reaching straight into EF Core/Postgres, and Domain acquiring a framework dependency. User confirmed this over simple N-Tier.
- (decision) AD-2 [ASSUMPTION] Layer communication rule: Application defines interfaces for everything it needs from outside (repositories, external services, clock/id providers); Infrastructure implements them; dependency injection wiring happens ONLY in LearnSphere.Api/Program.cs (the composition root). Binds: all cross-layer calls. Prevents: Infrastructure types (DbContext, EF entities-as-DTOs) leaking into Application or Api signatures, and DI registration scattered across multiple files. Rule: Application and Domain projects must never reference Infrastructure; only Api may reference Infrastructure, and only to register it in Program.cs.
- (decision) AD-3 [ASSUMPTION] No mediator/CQRS-pipeline library (no MediatR). Application layer exposes plain interface+implementation service classes per feature area (e.g. ICourseService/CourseService), called directly by controllers via constructor injection. Binds: Application layer structure. Prevents: encumbering the project with MediatR 13+'s RPL-1.5 copyleft/commercial licensing for an unscoped-revenue project. Deferred: revisit if the team later wants CQRS + cross-cutting pipeline behaviors (validation/logging/caching per request) and is fine accepting MediatR's license, or an alternative like Mediator (martinothamar, MIT, source-generator based, no licensing concern) or Mediatr-free source-generated approach.
- (decision) AD-4 [ASSUMPTION] Data access: EF Core (Npgsql.EntityFrameworkCore.PostgreSQL provider) via Repository + UnitOfWork interfaces defined in Application (e.g. ICourseRepository, IUnitOfWork), implemented in Infrastructure. Domain entities are persistence-ignorant (POCOs, no EF Core attributes) -- table/column mapping lives in Infrastructure via Fluent API IEntityTypeConfiguration<T> classes, one per entity. Binds: all data access. Prevents: EF Core-specific attributes or query patterns leaking into Domain/Application, and ad-hoc DbContext usage scattered through controllers.
- (decision) AD-5 [ASSUMPTION] API conventions: controllers are thin (HTTP <-> Application DTO mapping only, zero business logic), routes versioned as /api/v1/{resource} matching BACKEND_PRD.md's existing endpoint shapes, errors returned as RFC7807 ProblemDetails (ASP.NET Core's built-in support), DTO naming is {Entity}Dto for reads and Create{Entity}Request/Update{Entity}Request for writes. Binds: LearnSphere.Api and LearnSphere.Application DTO layer. Prevents: inconsistent error shapes and controllers accumulating business logic that belongs in Application services.
- (decision) AD-6 [ASSUMPTION] Feature-folder organization WITHIN each layer, not type-folder -- e.g. Application/Courses/{ICourseService.cs, CourseService.cs, CourseDto.cs}, Application/Tutoring/, Application/Notes/, Application/Reviews/, Application/Users/ -- mirroring the same feature-folder philosophy the frontend spine already adopted, rather than Application/Interfaces/ + Application/Services/ type-folders. Binds: internal structure of Domain/Application/Infrastructure. Prevents: a growing Services/ or Interfaces/ folder with no feature boundary, and keeps the two halves of the stack (frontend features/, backend feature-folders) conceptually aligned for anyone working across both.
- (decision) AD-7 [ASSUMPTION] Testing: xUnit (standard .NET test framework) + NSubstitute for mocking (MIT, avoids Moq's reputational baggage) + xUnit's built-in Assert (avoids FluentAssertions 8+'s commercial license; AwesomeAssertions noted as a free opt-in upgrade later if wanted). One test project per layer mirroring src/ -- LearnSphere.Application.Tests, LearnSphere.Infrastructure.Tests, LearnSphere.Api.Tests -- test classes live in a namespace-mirrored folder path (standard .NET convention: a parallel tests/ tree, not file-colocation like the frontend's *.test.tsx -- this is a deliberate per-ecosystem difference, not an inconsistency).
- (decision) AD-8 [ASSUMPTION] Migrations strategy: EF Core Migrations live in LearnSphere.Infrastructure/Persistence/Migrations, authored via 'dotnet ef migrations add' against the Api project (which holds the DbContext factory for design-time). Applied automatically on Api startup in Development/Docker-Compose (Program.cs calls db.Database.Migrate() behind an environment check) for fast local iteration; Deferred: switch to an explicit migration step/job before any real production deployment, since auto-migrate-on-startup is a known anti-pattern at scale (concurrent instances racing to migrate).

- (decision) FIX AD-4 extended: use EFCore.NamingConventions (SnakeCaseNamingConvention) registered once in Infrastructure's DbContext options, so C# PascalCase entities/properties map automatically to the PRD's snake_case SQL schema (users, course_notes, tutor_id, etc.) without per-property .HasColumnName() calls scattered across every IEntityTypeConfiguration. - (decision) AD-9 [ASSUMPTION] Entity IDs: string IDs matching the PRD's VARCHAR(64) columns, generated application-side (not DB identity/serial) as ULIDs via a small IIdGenerator interface in Application, implemented in Infrastructure. Binds: all entity primary keys. Prevents two engineers independently choosing GUID vs auto-increment int vs ad-hoc string ids for new entities. Rule: every new aggregate root's Id is assigned by calling IIdGenerator.NewId() before the entity is constructed, never left to the database to generate.
- (decision) AD-10 [ASSUMPTION] Service DTO boundary + mapping ownership: every I{Feature}Service method accepts and returns DTOs only at its public signature -- Domain entities never cross out of Application. Mapping between Domain entities and DTOs happens inside the service implementation via a static {Entity}Mapper class (ToDto/ToEntity methods) colocated in the same feature folder -- no AutoMapper (Jimmy Bogard's AutoMapper went commercial alongside MediatR in 2026, same licensing concern as AD-3). Binds: every Application service. Prevents controllers doing their own ad-hoc mapping and Domain entities leaking into Api-layer JSON responses.
- (decision) AD-11 [ASSUMPTION] Transaction/commit ownership: only the Application service method calls IUnitOfWork.SaveChangesAsync(), exactly once per use-case, after all repository calls for that use-case have staged their changes. Repositories only stage changes (Add/Update/Remove via DbContext) and never call SaveChangesAsync themselves. Binds: all write use-cases. Prevents partial-commit bugs when a use-case needs to touch two repositories, and stops repositories from silently committing before a use-case's business rules finish validating.
- (decision) AD-12 [ASSUMPTION] Cross-feature-folder reference rule: a feature's service (e.g. TutorService) may depend on another feature's SERVICE interface (e.g. ICourseService) to reuse its business rules, but never on another feature's REPOSITORY interface directly (e.g. TutorService must not inject ICourseRepository). Binds: Application-layer feature folders (extends AD-6). Prevents a feature bypassing another feature's validation/business rules by reaching straight into its data access.
- (decision) FIX AD-5/AD-10: Application-layer failure signaling is via typed exceptions deriving from a common AppException base (NotFoundException, ValidationException, ConflictException), caught by one global exception-handling middleware in Api that maps each to the correct ProblemDetails status code. Not a Result<T> wrapper -- keeps the convention idiomatic ASP.NET and avoids inventing a second, incompatible failure-signaling convention alongside exceptions that framework code (EF Core, model binding) already throws.

- (decision) FIX AD-8: clarified the startup migrate condition -- ASPNETCORE_ENVIRONMENT defaults to Production inside a plain container, not Development, so 'behind an IsDevelopment() check' would silently never fire in Docker Compose as originally worded. - (decision) AD-13 [ASSUMPTION] Docker/Compose operational envelope (the dimension the rubric walker flagged as under-specified despite being the user's explicit deployment choice): LearnSphere.Api/Dockerfile is a multi-stage build (mcr.microsoft.com/dotnet/sdk:10.0 to restore+publish, mcr.microsoft.com/dotnet/aspnet:10.0 to run). docker-compose.yml defines api + postgres services; api reads its connection string from ConnectionStrings__Default (the ASP.NET config double-underscore env-var convention, not a bespoke key); postgres uses a named volume (pgdata) for persistence and a healthcheck (pg_isready); api's depends_on the postgres healthcheck being 'service_healthy', not just container start. Binds: the deployment envelope. Prevents two engineers inventing different env var names for the same connection string, and the API container starting before Postgres is actually ready to accept connections.
