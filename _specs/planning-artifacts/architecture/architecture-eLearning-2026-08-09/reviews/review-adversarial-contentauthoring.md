# Adversarial Review — ContentAuthoring pass (frontend + backend spines)

## Verdict

Nine findings, three of them critical. The pattern that recurs across all of them: this pass
introduced a genuinely new *shape* (a polymorphic owner reference, a document canvas whose body
lives outside Context, a versioned snapshot of a graph that itself has no DB-level referential
integrity) and, each time, pinned down one half of the shape (the entity, the rule that triggers
a state change, the security intent) while leaving the other half (the exact wire contract, the
mutation-notification path, the physical storage representation) as an implementation choice two
engineers could make differently and both be correct against the AD's literal text. Two of the
three critical findings sit exactly on the seam the task asked me to probe hardest: AD-20's
`OwnerType` (an exact string set never pinned down) and AD-29's enrollment check (a primitive
that does not exist anywhere in either spine's Domain model, referenced as if it obviously does).
The third — Review-as-Student's page-body source going undefined the moment AD-4 stripped page
bodies out of `CourseContentContext` — is the most consequential: it breaks a named PRD flow
(FR-46) and the one sanctioned cross-feature exception (AD-3) that exists specifically to serve
it.

## Findings by severity

### CRITICAL

**1. `OwnerType`'s exact value set is never pinned down as a wire contract — two engineers can spell "Subtopic" differently and neither is wrong by the letter of AD-20.**

- **Where:** Backend AD-20's Rule: `Page.OwnerType ∈ {Chapter, Topic, Subtopic}`, `Resource.OwnerType ∈ {Chapter, Topic, Subtopic, Page}` — set notation, not a typed contract. PRD Appendix A mirrors the same set notation. Appendix B's only remark on wire format is generic: "Enum wire format follows this codebase's existing PascalCase `.ToString()` convention (`"Confirmed"`, `"Inline"`)." AD-25, by contrast, explicitly settles this exact question for `Setting.KeyType` ("KeyType is a plain string column, not a C# enum... this codebase's existing convention for category-like fields... is enum-first, but FR-7's... intent needs the open-ended string shape here instead"). AD-20 has no equivalent sentence. Frontend AD-9/AD-10 and the Consistency Conventions table (`src/types.ts` — "a type used by 2+ features stays here") never mention an `OwnerType` union at all.
- **The gap:** Nothing states whether `OwnerType` is a C# enum (in which case the member name, not just conceptual meaning, is the wire value under `.ToString()`) or a plain string column (in which case any code path that constructs the literal is a place spelling can drift). Nothing states the frontend's matching TypeScript literal-union type is generated from, or unit-tested against, the backend's values — it is Consistency-Conventions "shared type in `types.ts`," hand-maintained on both sides of an HTTP boundary. The entity class itself is spelled `Subtopic` (one word) throughout Domain/Courses, but nothing declares that this is *also* the mandated enum-member/string-literal spelling as opposed to the more idiomatic two-word C# PascalCase `SubTopic` a second engineer might reach for by convention.
- **Incompatible-build scenario:** Backend engineer A implements `Page.OwnerType` as `enum ContentOwnerType { Chapter, Topic, Subtopic, Page }` (matching the entity class name exactly). Backend engineer B, working `Resource.OwnerType` in a separate story (per AD-20's own text, Resource's owner set is a superset of Page's, built at a different time), independently reaches for the two-word PascalCase convention more common elsewhere in the codebase (`SubTopic`) since nothing tells them otherwise. Frontend engineer C, building the "Move page to…" action (FR-8) and `POST /pages {ownerType, ownerId, title}`, hand-types the TypeScript union from reading the PRD's Appendix A prose (which spells it `Subtopic`) into `courseContentService.ts`. If any one of the three disagrees, a `Move page to a Sub-Topic` action either 400s server-side on a value the frontend swears is correct, or — worse, if OwnerType is a loosely-validated plain string column with no DB constraint (consistent with AD-20's explicit "no DB-level FK... cascade is entirely a service-layer responsibility") — silently creates a `Page`/`Resource` row with an owner value that matches nothing any query for `Subtopic`-owned content will ever find: an orphaned row, invisible on the outline, present in the database, discovered only when someone diffs storage against what renders.
- **Hole to close:** AD-20 needs the same explicit typing decision AD-25 already made for `KeyType` — enum vs. string, and if enum, the literal member spelling stated once as the single source of truth both the C# type and the frontend's `types.ts` union are checked against.

**2. AD-29's "requester is enrolled" branch assumes an enrollment-check primitive that does not exist anywhere in either spine's Domain model — two resolutions are both textually defensible and produce opposite security postures.**

- **Where:** Backend AD-29's Rule: "allow if `course.LifecycleState == Published` **and** (requester is enrolled **or** requester is the owning tutor **or** requester is Admin)," immediately followed by its own `[ASSUMPTION: assumes an existing enrollment-check primitive this policy branch can call — confirm the exact enrollment lookup against live code at story time, not re-derived here.]`, restated verbatim in the Deferred section. The backend Structural Seed's entire Domain entity list — `Courses/`, `Tutoring/`, `Notes/`, `Reviews/`, `Users/`, `Jobs/`, `AiUsage/`, `AiConfig/`, `Tags/`, `ErrorObservability/`, `Settings/` — contains no `Enrollment` entity and no `Progress`/`CourseProgress` entity of any kind. Frontend AD-4 references `DomainContext.user` carrying "progress, points" but this is explicitly a frontend-only, mock-data-era shape with no confirmed backend-persisted counterpart in either spine.
- **The gap:** "Confirm the exact enrollment lookup against live code at story time" presupposes a lookup exists to confirm. It does not, in either spine reviewed here. This is not a missing implementation detail behind an otherwise-settled concept — the concept itself (what makes a Student "enrolled" in a course, in a persisted, backend-checkable sense) is absent from the Domain model this pass shipped.
- **Incompatible-build scenario:** Engineer A, implementing the policy branch at story time, adds a first-class `Enrollment` join entity (`Domain/Courses/` or a new `Enrollment/` folder) with an explicit enroll action and `IEnrollmentRepository.IsEnrolledAsync(userId, courseId)`, gating `GET /resources/{id}/content` on a real row's existence — the conservative, deny-by-default reading. Engineer B, finding no `Enrollment` entity anywhere to reuse and reading AD-29's Rule as merely wanting "a real check, not signed URLs" (its stated Prevents is about *mechanism*, not about *what enrolled means*), resolves the `[ASSUMPTION]` by treating any authenticated `Student`-role requester as implicitly "enrolled" for a `Published` course (there is, after all, no per-course enrollment gate anywhere else in either spine that this pass's own Discover/catalog browsing implies exists) — collapsing the enrolled/owner/admin three-way check into "any authenticated non-owner is allowed," which is not what AD-29's Binds/Prevents text intends but is fully consistent with what its Rule text can be resolved against, since the Rule cites a primitive neither spine defines. Both engineers satisfy AD-29's literal Rule; one builds real per-student access control, the other builds a check that is a no-op against any authenticated Student.
- **Hole to close:** the enrollment primitive's existence (and its entity shape, if it doesn't exist yet) needs to be resolved as an architecture-level decision, not deferred to "confirm against live code" when the live-code confirmation itself will find nothing to confirm.

**3. AD-4's amendment strips Page bodies out of `CourseContentContext` but never re-sources them for Review-as-Student's whole-chapter/whole-course walk — the one sanctioned cross-feature exception (AD-3) this pass depends on has no defined data path left.**

- **Where:** Frontend AD-4 (amended): "A Page's actual body content lives in whichever Tiptap editor instance currently has that Chapter's document open, fetched in one call via the backend's `GET .../chapters/{id}/document` endpoint... — **not held in Context**, since nothing needs every Chapter's full document simultaneously." The Structural Seed's `context/CourseContentContext.tsx` line is stale against this amendment — it still reads "the confirmed Chapter->Topic->Subtopic tree, draft AND published... shared by `CourseContentEditor` and `CoursePlayer`'s Review-as-Student mode," implying Context is a shared source of page content for both consumers, which the AD-4 prose immediately above it contradicts. AD-3's sanctioned cross-feature exception exists explicitly so "Review-as-Student renders byte-for-byte identical to what a real student sees" across an entire chapter/course walk (PRD FR-46: "available at page, node **and course** scope").
- **The gap:** Once page bodies are excluded from Context, and `DomainContext.courses` is explicitly published-only (AD-4's own rule: draft content "live**s** only in `CourseContentContext`, never in `DomainContext.courses`"), there is no defined data source for a **read-only, multi-page walk** of Draft content. The Tiptap-editor-instance-holds-the-body model that AD-4 relies on to justify keeping bodies out of Context is scoped to *one Chapter a tutor is actively editing* — it is not a source anything can query for "every page in this course, read-only, in order," which is exactly what a course-scope Review-as-Student walk needs.
- **Incompatible-build scenario:** Engineer A, building Review-as-Student per the Structural Seed's (stale) framing that Context is the shared source both consumers read, wires it to read page bodies straight out of `CourseContentContext` — and gets `undefined`/empty bodies for every page, since AD-4's amended Context only holds outline metadata. Engineer B, reading AD-4's amended prose literally, has Review-as-Student fetch each page's body on demand via `GET /pages/{id}` as the reader navigates — a real, working implementation, but one that never goes through `GET .../chapters/{id}/document` (the call AD-4 names as the canonical page-body fetch, used by the authoring Tiptap instance) and therefore has its own, second, independently-built fetch/cache/loading-state path for the same content, built to a different endpoint shape than the one AD-4 actually documents. Neither engineer is wrong against the letter of what they each read; the two builds don't just diverge, one of them (A) doesn't function at all, and nothing in AD-3, AD-4, or AD-9 says which reading governs.
- **Hole to close:** AD-4 (or AD-3's exception) needs an explicit statement of what data path a read-only, multi-page/whole-course Review-as-Student walk uses, now that page bodies are excluded from both Context and `DomainContext.courses` by construction.

### HIGH

**4. Three independent Markdown surfaces — Tiptap's `@tiptap/markdown` serializer, the existing hand-rolled `lib/markdown.ts` renderer, and the backend's unvalidated `BodyMarkdown` passthrough — have no assigned single owner for FR-28's three custom block syntaxes, and AD-9 never requires them to agree.**

- **Where:** Frontend AD-9: `@tiptap/markdown` is "the Markdown round-trip layer that makes DD-3's 'persists a single Markdown string' contract possible" — this is the editor-side serializer/parser. PRD §1.1 confirms `lib/markdown.ts` is a separate, pre-existing, hand-rolled renderer ("Built... never emits raw HTML") — this is what actually renders to students in Course Player and Preview. PRD FR-28 explicitly scopes new renderer work for exactly three block types Tiptap's `starter-kit` does not natively support: Math (`$$…$$`, not CommonMark), Callout (`> [!note]`, a GFM-adjacent convention, not CommonMark), Resource card (`[label](resource:{resourceId})`, a domain-specific URI scheme). Backend `Page.BodyMarkdown` (AD-20 / Appendix A) is stored as opaque `text` with only a length cap — no format validation of any kind.
- **The gap:** AD-9 assigns Tiptap-the-editor-foundation but never assigns ownership of the **custom Tiptap node extensions** these three block types require (`starter-kit` has no Math/Callout/ResourceCard nodes) — each needs its own hand-written `parseMarkdown`/`renderMarkdown` (or equivalent `@tiptap/markdown` serialization) rules. AD-10 only splits "generic slash-menu mechanism" (`lib/editor/`) from "feature-owned command list" (`features/CourseContentEditor/`) — neither bucket is where a Tiptap *node's* markdown-serialization behavior naturally lives, and neither AD requires that behavior to be cross-checked against `lib/markdown.ts`'s independently-written parser for the same three constructs. AD-6's golden-file testing covers KaTeX/Devanagari **visual** rendering parity, not **Markdown-syntax** parity between the two libraries.
- **Incompatible-build scenario:** The engineer building the Tiptap Math node extension emits `$$...$$` on its own line with Tiptap's default whitespace/escaping behavior (matching FR-28's stated syntax literally). The engineer extending `lib/markdown.ts` per FR-28's separately-tracked renderer work writes a regex/parser against their own reading of "`$$…$$` fenced math" — with no golden text to cross-validate against, since the two were never required to test against each other's actual output, only against KaTeX's rendered pixels once parsed. A tutor authors a page with inline math adjacent to a Callout in the same paragraph; Tiptap round-trips it perfectly in the editor (both nodes are its own schema, its own serializer, self-consistent) but `lib/markdown.ts`'s independently-built parser — the one Course Player and "Preview as student" actually use — mis-tokenizes the boundary and renders it as literal text or a broken card. This directly defeats FR-46/UJ-1's "she switches to Preview and sees the page exactly as a student will."
- **Hole to close:** ownership of the three custom block types' canonical Markdown grammar (one definition, not two independently-implemented ones) needs an explicit AD, plus a syntax-level (not just pixel-level) parity test between Tiptap's serialized output and `lib/markdown.ts`'s parser.

**5. `CourseContentContext` is the declared owner of Page confirmation state, but the Tiptap autosave path that FR-44 requires to flip that same state is explicitly routed *around* Context — nothing keeps the two in sync.**

- **Where:** Frontend AD-4 (amended): `CourseContentContext` holds "outline metadata (Chapter/Topic/Subtopic/Page titles + **confirmation state**...)". The same paragraph: page-body autosave (FR-34) is "not held in Context." Structural Seed's `courseContentService.ts` line confirms: outline/confirm-state calls are "backed by `CourseContentContext`"; "Chapter document fetch/autosave (Page bodies, Resources) is a separate set of calls this same service exposes, consumed directly by the Tiptap editor instance... **not routed through Context**." PRD FR-44: "A page's own confirmation resets on any structural change to its body's non-text blocks (image, resource card, math, table)."
- **The gap:** FR-44's confirmation-reset trigger (inserting an Image block, say) fires *inside* the Tiptap editor instance, on the exact path AD-4 just declared bypasses Context. The Table-of-Contents rail's Confirmed/Unconfirmed badge (EXPERIENCE.md's `content-page-marker`) reads its state from `CourseContentContext` (the declared owner). Nothing in AD-4, AD-9, or AD-10 says the autosave call's response (or a side-channel) patches Context's confirmation field when a structural body edit silently un-confirms a page server-side.
- **Incompatible-build scenario:** Engineer A builds the Tiptap autosave integration by AD-4's letter — no Context writes from the editor's save path at all. Engineer B builds the ToC rail's confirmation badge by AD-4's letter — reads exclusively from `CourseContentContext`. Both are individually compliant. The moment a tutor inserts an image inside a page body, the backend (per FR-44) flips that page's confirmation server-side, but the frontend Context that owns "confirmation state" was never told — the rail keeps showing "Confirmed" until the next full outline refetch, silently violating EXPERIENCE.md's own accessibility rule that a confirmation reversion "is announced at the moment it happens via `aria-live='polite'`... a tutor may not expect their edit to have un-confirmed something" — an announcement that structurally cannot fire if the state it announces was never updated.
- **Hole to close:** AD-4 needs to say who re-synchronizes `CourseContentContext`'s confirmation field after a page-body autosave triggers a server-side confirmation reset that never routes through Context's own write path.

**6. AD-29's Rule condition (`course.LifecycleState == Published`) structurally excludes the `InReview` reviewer-read case that AD-29's own Binds/Prevents text names as the thing it resolves — and "reviewer" is undefined as a role anywhere in either spine.**

- **Where:** AD-29 Binds: "resource reads reached by a non-owner (**student, reviewer**) on a `Published` course." AD-29 Prevents: names the gap this closes as making "non-owner, non-Draft reads well-defined rather than silently unreachable," and closes with "**Resolves OQ-11**." But its Rule's actual condition is `course.LifecycleState == Published AND (...)` — an `InReview`/`ReviewConfirmed` course fails this condition outright, for every requester type. `EnsureOwnedDraftAsync` (the pre-existing authoring-path guard) is explicitly Draft-only and owner-only per FR-45's own text ("Once a course is `InReview`, `EnsureOwnedDraftAsync`'s Draft-only guard... blocks further tutor edits by construction"). Neither guard grants a non-owning reviewer any access during `InReview` — the one lifecycle state whose entire purpose is review.
- **The gap:** AD-29 claims to resolve OQ-11 for "reviewer" access, but its literal Rule leaves the reviewer's actual working state (`InReview`) with zero defined read path — worse than before this AD, in the sense that it now looks resolved (closed as "Resolves OQ-11") when the concrete case named in its own Binds line is unaddressed. Neither spine defines who "the reviewer" role even is (a distinct `Reviewer` role? An Admin/Master doing review? A Support-tier reviewer?) — `UserRole` values referenced elsewhere are `Master`/`Support`/(implicitly) `Tutor`/`Student`.
- **Incompatible-build scenario:** Engineer A (frontend, building a reviewer-facing preview surface) reads AD-29's "Resolves OQ-11" and Binds-line mention of "reviewer" as license to assume `GET /resources/{id}/content` works for a reviewer on an `InReview` course, and ships a reviewer preview UI against that assumption. Engineer B (backend, implementing the policy branch literally from the Rule text) returns 403 for any non-Published course regardless of requester role — fully AD-29-compliant — and the reviewer surface silently 403s on every resource in every course still under review, the only lifecycle state a reviewer actually needs to read.
- **Hole to close:** either extend AD-29's condition to cover `InReview` for a defined reviewer identity, or explicitly narrow its Prevents/Binds language so it stops claiming to resolve the reviewer case it structurally excludes.

**7. AD-17's amended snapshot rule requires an efficient "is this Resource referenced by *any* version snapshot" query before allowing hard-delete, but the physical storage shape of a `CourseVersion` snapshot is never pinned down — and AD-20's "no DB-level FK" choice makes the two plausible shapes behave very differently under that exact query.**

- **Where:** AD-17 (amended): "each publish deep-copies the entire confirmed outline+page+resource graph... into a versioned snapshot." Same AD: "hard-deleting a `Resource` is blocked if it's referenced by **any** version snapshot, not only by a live page body." AD-20: "no DB-level `FOREIGN KEY`/`ON DELETE CASCADE` for `Page`/`Resource` ownership — cascade-delete... is entirely a service-layer responsibility."
- **The gap:** "Deep-copies... into a versioned snapshot" is compatible with at least two very different persistence shapes: (a) a single serialized JSON blob per `CourseVersion` (literal to AD-17's original "simplicity... literal match to FR-25's wording" rationale, and the cheapest to build), or (b) fully relational versioned rows (`VersionedPage`, `VersionedResource`, etc., each carrying a `SnapshotId` and a plain, non-FK `ResourceId` reference column, per AD-20's polymorphic-without-FK pattern extended to the version graph). Under (a), "is `ResourceId=X` referenced by any version snapshot" requires deserializing and scanning every historical snapshot blob — expensive, and not indexable without extra denormalized structure the AD never mentions. Under (b), it's a straightforward indexed query. AD-17 assumes the query is cheap enough to run synchronously on every hard-delete attempt without ever choosing between these.
- **Incompatible-build scenario:** The engineer implementing AD-15/AD-16's publish batch (which is what actually writes the snapshot) picks shape (a) — a single JSON column — because it's the literal, simplest reading of "deep-copy... into a versioned snapshot" and matches AD-17's own stated storage-cost trade-off framing. The engineer implementing FR-31/AD-17's resource-delete guard (a different story, per Appendix C's C-3/C-8 split from the publish/versioning stories) needs shape (b) to make the "referenced by any version snapshot" check performant, and either builds a second, denormalized index the publish job was never told to populate (drifts out of sync with the JSON blob it's supposedly indexing) or discovers at implementation time that the guard as specified isn't buildable against what was actually shipped.
- **Hole to close:** AD-17 or AD-20 needs to state the physical representation of a `CourseVersion` snapshot explicitly enough that the resource-delete guard's query is known to be buildable against it, not left to whichever story lands first to decide unilaterally.

### MEDIUM

**8. `lib/editor/`'s documented call path directly contradicts the frontend spine's own "lib/ is only ever called from services/" paradigm rule — two engineers each have textual authority for opposite import graphs.**

- **Where:** Design Paradigm section, `lib/` bullet: "framework- and domain-agnostic utilities... **only ever called from `services/`**." AD-3's Rule (the binding dependency-direction contract): "`features/*` may import `ui/*`, `hooks/*`, `services/*`, **`lib/*`**, `types.ts`, and the Context from AD-4." Structural Seed's `lib/editor/` line: "AD-9/AD-10: generic Tiptap slash-menu mechanism... **Called only from `features/CourseContentEditor/`**" — a direct feature-to-lib import, no `services/` indirection.
- **The gap:** These three statements are not reconcilable as written. The Design Paradigm's `lib/` rule and the Structural Seed's own `lib/editor/` annotation directly disagree about whether a feature may import `lib/` code without going through a service — and AD-3, the AD that actually governs dependency direction, sides with the Structural Seed (features may import `lib/*` directly), leaving the Design Paradigm's introductory bullet as a standing, un-reconciled contradiction inside the same document.
- **Incompatible-build scenario:** Engineer A, treating the Design Paradigm's prose as the load-bearing rule (it reads as a flat architectural invariant, not a draft note), builds a thin `services/`-layer indirection so `CourseContentEditor` never imports `lib/editor/` directly — e.g., wrapping the Suggestion-menu's exports behind a service-shaped module. Engineer B, citing AD-3's explicit Rule text and the Structural Seed's own annotation, wires `features/CourseContentEditor/` directly to `lib/editor/` with no indirection. Code review has no single authority to point to that resolves which import graph is "the" compliant one — both engineers can cite a different part of the same spine.
- **Hole to close:** the Design Paradigm's `lib/` description needs to either be corrected to match AD-3/AD-10's actual permitted import graph, or AD-10's `lib/editor/` carve-out needs to be named as an explicit, bounded exception to the paradigm's general `lib/`-via-`services/` rule (the way AD-25 explicitly names itself a bounded exception to AD-20).

**9. FR-4's "Markdown-lite: paragraphs and bullets only" restriction on node Descriptions lives inside the *same* single continuous Tiptap document as full-palette Page bodies — no AD assigns ownership of enforcing a narrower block set in that one zone, or of cursor-position-aware menu filtering.**

- **Where:** PRD FR-4: node Description is "Markdown-lite: paragraphs and bullets only." PRD FR-10: the chapter overview is "an ordinary paragraph block" written "immediately below" the Chapter `h1`, inside the same document DD-4 describes as one continuous canvas. AD-9's Rule scopes Tiptap to "`CourseContentEditor`'s document canvas and page-body editing" without distinguishing a description zone from a page-body zone. AD-10 splits ownership into exactly two buckets — generic mechanism (`lib/editor/`) and feature-owned command **list** (a flat vocabulary) — neither of which is "which commands are valid at this specific cursor position in the document."
- **The gap:** Tiptap's node schema is normally global to one editor instance. Constraining "this paragraph directly under an `h1`/`h2`/`h3` is Description text and may only ever contain paragraph/bullet nodes, while forty lines further down in the same document a Page body may contain Image/Table/Math" is a real, non-trivial schema-and-menu-filtering problem that neither AD-9 nor AD-10 acknowledges exists, let alone assigns.
- **Incompatible-build scenario:** Engineer A ships one global Tiptap schema with the full block palette available everywhere, relying on server-side FR-4 validation to reject (or silently strip) a disallowed block type if a tutor inserts one into a Description — a save that appears to succeed in the editor and then loses content, or errors, only on the round trip. Engineer B builds cursor-position-aware command filtering so the "/" menu itself never offers Image/Table/Math while the cursor is inside a Description zone — a different, additional mechanism that has to live somewhere AD-10 never named (is position-aware filtering "mechanism," and thus `lib/editor/`'s job, or "vocabulary," and thus feature-owned?). The two produce different UX (silent-loss-on-save vs. structurally-prevented) and different code (validation-only vs. schema-plus-filtering), and nothing in AD-9/AD-10 says which is required.
- **Hole to close:** assign ownership of Description-zone content restriction (client-side schema constraint vs. server-side-only validation) and, if client-side, where cursor-position-aware menu filtering lives relative to AD-10's mechanism/vocabulary split.
