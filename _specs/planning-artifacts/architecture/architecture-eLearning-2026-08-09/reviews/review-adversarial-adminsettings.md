# Adversarial Review — AD-8 (SiteSettingsContext)

## Verdict

AD-8 has one genuine, safety-critical hole: it never mentions Preview at all, despite Preview
(FR-13/FR-14) and its isolation guarantee (NFR-3) being the PRD's most consequence-tested
requirement. AD-8's rule text describes exactly two data paths — SiteSettingsContext's read at
boot, and the Admin screen's "CRUD/Apply/Restore/history" write path — and silently invites an
implementer to fold Preview into whichever one seems convenient. Because AD-8 also supplies the
*only* concrete technique in the whole spine for realizing a font pairing (a global
`document.documentElement.style.setProperty` call) without scoping it, an engineer building
Preview has every reason, under the letter of AD-8, to reuse that exact global mutation for the
"live preview" — which breaks FR-13's own consequence test the moment it's tried. This needs a
tightened AD-8 before implementation starts, not a docs note; the leak-to-other-users scenario
the reviewer lens was asked to hunt for is real and reachable by two engineers each doing
exactly what AD-8 says.

## Findings by severity

### CRITICAL

**1. AD-8 never names Preview as a state at all — two AD-compliant `settingsService.ts` designs diverge into one that transiently persists a candidate value, leaking it to every other user's boot-time fetch.**

- **Where:** AD-8's Rule text enumerates exactly two things `settingsService.ts` backs: "`SiteSettingsContext` (read)" and "the Admin Settings/ subtab's own CRUD/Apply/Restore/history UI (write)" — Preview (PRD FR-13/FR-14, Glossary §3 "Preview") appears in neither clause. AD-1's rule that "every backend... call goes through a `services/*` function" applies uniformly to all of `settingsService.ts`'s exports, but AD-8 gives no function-level split between "safe to call speculatively, never persists" and "persists."
- **The gap:** FR-10 says server-side curation enforcement must reject an invalid pairing "regardless of which client made the request... including attempts made via a direct API call rather than the Settings screen" — this reads naturally as "there is a server-side check Preview should also exercise before Apply." Nothing in AD-8 or the PRD specifies a distinct, non-persisting `validateCandidate()`-style endpoint separate from the one that actually writes the Value/IsActive row. AD-1's module-boundary discipline gives no protection here: both a correct read-only preview call and an incorrect persisting one legitimately live inside `services/settingsService.ts` per AD-1's own "one module per domain entity" convention, so code review checking "did this call go through `services/`" would pass either way.
- **Incompatible-build scenario:** Engineer A builds `SiteSettingsContext` exactly as AD-8 specifies: it calls `settingsService.getActiveSettings()` once at app boot (any user, any tab, any time) and applies whatever Font-KeyType row comes back with `IsActive: true`. Engineer B builds the Admin Settings Preview per FR-13, and — reading FR-10's "enforced... regardless of which client" as requiring a live server round-trip for curation checking before showing the preview, and finding no AD-8 text telling them otherwise — implements candidate selection by calling the same `settingsService.updateSetting()`/`applySetting()` function Apply uses, just without surfacing a second confirmation step (nothing in AD-8 names a distinct, non-mutating validation path). The moment Priya opens the font picker and selects a candidate to preview, Engineer B's implementation has already written the candidate Value to the row Engineer A's `getActiveSettings()` reads from. Any other user's page load — or the same admin's own other browser tab — that boots during that window (which per NFR-1 is expected to happen continuously, since propagation is defined as "next page load") now renders the previewed, unapplied pairing as if it were live. This is precisely NFR-3's forbidden outcome ("no observable effect on any other user's session... until Apply is clicked") and directly contradicts FR-13's consequence test ("every other user continues rendering the current live pairing"), yet neither engineer violated AD-8 or AD-1 as written.
- **Fix:** Tighten AD-8 to name Preview as a third, explicit state distinct from both the read path and the write path: state that Preview MUST be realized without any call to a persisting `settingsService.ts` function — either (a) purely client-side, using data already resident in memory from the curated-pairings list (satisfies FR-13/NFR-3 by construction, since there is no network write to race against), or (b) if server-side curation validation is required before Preview renders, name a specific, explicitly non-persisting `settingsService` function (e.g. `validateCandidate()`) and state in AD-8's Rule that it is the *only* function Preview may call — `applySetting()`/`updateSetting()` are reachable only from the Apply action.

### HIGH

**2. AD-8's only documented technique for applying a font pairing is a single global, shared mutable target — Preview's most natural reuse of it breaks FR-13's "rest of the app is unaffected" test and FR-14's "discard on navigate-away" test.**

- **Where:** AD-8's Rule: "it applies the active Font Pairing by calling `document.documentElement.style.setProperty('--font-display', ...)` (and `--font-sans`, `--font-mono`) directly for each CSS custom property... the more idiomatic... way to override the custom properties already defined in `index.css`'s `@theme`." This is the *only* concrete rendering technique named anywhere in the spine for realizing a Setting.
- **The gap:** `document.documentElement` is one global DOM node shared by the entire single-page app for the lifetime of the session. AD-8 gives this technique to `SiteSettingsContext` for the boot-time apply, but says nothing about how — or whether — Preview should render its candidate differently. FR-13's own consequence test is explicit: "Selecting a candidate pairing updates only the preview area; the rest of the application (this admin's own other tabs, and every other user) continues rendering the current live pairing" — "this admin's own other tabs" reads as other Admin subtabs (`AiConfiguration/`, `TagManagement/`, `ErrorLog/`) within the same SPA session, all of which inherit `:root`-scoped custom properties from the same `documentElement`.
- **Incompatible-build scenario:** Engineer B, building the Preview panel and needing it to render real site content (a heading, a body paragraph, a card, per FR-13) in the candidate typography, reaches for the one technique the spine itself documents as idiomatic — `document.documentElement.style.setProperty('--font-display', candidate.display)` — on candidate selection. This is legal under AD-8's letter (AD-8 never restricts the technique to boot-time-only use, nor scopes it to `SiteSettingsContext`). The effect: selecting a candidate in the picker changes typography for the *entire* admin session — every other Admin subtab, not just the preview panel — failing FR-13's testable consequence outright. Worse, on FR-14's "navigate away without Apply discards it" path, nothing in AD-8 specifies who resets `documentElement`'s custom properties back to the live value: `SiteSettingsContext` "fetches... once at app boot" per AD-8's own text, so it has no re-apply/reset hook to fire on preview-abandon. The admin's session is left rendering an uncommitted, discarded preview until a hard reload — violating FR-14 even though both engineers followed AD-8 to the letter.
- **Fix:** Add to AD-8's Rule that Preview MUST render through a mechanism scoped to the preview panel's own DOM subtree — e.g. custom-property overrides on a container element wrapping only the sample content (`<div class="settings-preview" style={{'--font-display': candidate.display, ...}}>`), never on `document.documentElement` — reserving the global `documentElement`-level `setProperty` call exclusively for `SiteSettingsContext`'s boot-time apply of the confirmed live value.

**3. Overloaded "active" semantics: `Setting.IsActive` (FR-8, controls Effective Value) and a Font Pairing's curated/decurated status (FR-10) plausibly share the same generic store, but AD-8 never scopes `SiteSettingsContext`'s "fetch all active Settings" query.**

- **Where:** AD-8's Rule: "It fetches all active Settings once at app boot"; PRD FR-6/FR-7 ("Settings are persisted... KeyType... distinguished only by KeyType, not separate tables"; "a new KeyType can be introduced by data alone"); FR-10's consequence: "Removing a pairing from the curated list makes it immediately unavailable for new Applies... a historical entry referencing it can still be viewed but not reapplied."
- **The gap:** FR-10's curated-list membership reads as its own on/off state per pairing (curated vs. decurated) — conceptually adjacent to, but distinct from, `Setting.IsActive` (which per FR-8 selects the *Effective Value* of the one governing Font-KeyType row). The PRD never states whether the curated pairing catalog itself is modeled as rows in the same generic settings store (a natural extension-without-migration choice per FR-7's own design intent) or as a separate static/constants source. AD-8 doesn't decide this, and its "fetch all active Settings" phrasing doesn't name a query scope (e.g. `WHERE KeyType = 'Font'` vs. `WHERE IsActive = true` across all KeyTypes).
- **Incompatible-build scenario:** Engineer A (backing store/settingsService) satisfies FR-7's extensibility requirement by modeling the curated Font Pairing catalog as `Setting` rows too (e.g. `KeyType = 'FontPairingCatalog'`, one row per pairing, each with its own active/inactive-style flag governing curation per FR-10). Engineer B (`SiteSettingsContext`), following AD-8's literal "fetch all active Settings" without a narrower filter, receives catalog rows mixed in with the one operative Font-KeyType setting, and a boot-time reducer that picks "the active Font-ish row" by a loose match can select a catalog entry instead of the actually-applied pairing — rendering the wrong typography, or crashing on an unexpected shape (catalog rows likely carry a pairing *identifier*, not resolved font-family values, per FR-11: "Display, Body, and Mono roles are resolved together from that one identifier").
- **Fix:** Add to AD-8's Rule an explicit query scope — e.g. "`SiteSettingsContext` fetches only rows where `KeyType` matches a known *applied-setting* KeyType (`Font` today) and `IsActive = true`; the curated Font Pairing catalog (FR-9/FR-10), if stored in the same table, is a structurally distinct KeyType that `SiteSettingsContext`'s boot fetch MUST exclude by construction, not by convention."

### MEDIUM

**4. AD-8 breaks AD-4's Context-mediated-write precedent without naming Preview's third state or a post-Apply reconciliation rule for the admin's own session.**

- **Where:** AD-4's precedent (`CourseContentContext`, "shared by `CourseContentEditor` and `CoursePlayer`'s Review-as-Student mode") implies a single Context is the seam both readers and writers of a cross-cutting entity go through. AD-8 explicitly departs from this: "`SiteSettingsContext` is the read-only, app-wide consumption path; the Admin screen is the write path" — writes go straight from the feature to `settingsService.ts`, bypassing the Context entirely.
- **The gap:** This departure is defensible (Deferred explicitly accepts stale Context state after Apply, citing NFR-1's "next page load" allowance), but AD-8 doesn't reconcile it with the fact that the *same admin, same tab* just applied a change and is looking at the Settings screen's own post-Apply confirmation UI (FR-14, FR-15's "the Settings list (FR-5) reflects the newly selected pairing"). Nothing says whether that confirmation reads from `SiteSettingsContext`'s (now-stale) snapshot or issues its own fresh `settingsService` read — and AD-8 also never names where the ephemeral, non-persisted "preview candidate" state (PRD Glossary §3) is supposed to live: per AD-4's general "single-feature state stays feature-local" rule it belongs in the `Admin/Settings/` feature's own `useSettings.ts` hook, but AD-8 doesn't say so, leaving room for an engineer to instead wire it through `SiteSettingsContext` (reasoning that it's "the settings Context") — reintroducing Finding 2's global-mutation collision through a different door.
- **Fix:** State explicitly in AD-8 that (a) the Settings screen's own list/history views always re-read via `settingsService.ts` directly, never via `SiteSettingsContext`, so post-Apply UI is never accidentally coupled to the stale boot-time snapshot; and (b) the preview-candidate value is feature-local state in `Admin/Settings/useSettings.ts` (per AD-2/AD-4's own local-state rule) and is never written into `SiteSettingsContext`.

**5. AD-8 is silent on NFR-4 (fail-safe defaults when the settings store is unreachable, malformed, or times out at boot) — divergent error handling risks breaking the AD-2 composition root, not just settings.**

- **Where:** AD-8's Rule describes only the happy path: "It fetches all active Settings once at app boot... applies the active Font Pairing." NFR-4: "If the settings store is unreachable, returns malformed or invalid data, or times out at page load, the system SHALL render using hardcoded defaults rather than failing to load."
- **The gap:** `SiteSettingsContext` is mounted at the `App.tsx` composition root per AD-2 ("mounts the Context providers from AD-4" — AD-8 extends that precedent). AD-8 never states that the boot fetch must be wrapped to fail soft.
- **Incompatible-build scenario:** Engineer A treats NFR-4 as implicit and wraps the fetch in try/catch, no-op on failure (leaving `index.css`'s hardcoded `@theme` defaults untouched) — correct. Engineer B, following AD-8's rule text literally (which describes an unconditional fetch-then-apply with no mention of failure handling), lets a rejected promise propagate; depending on how the Context provider's effect is written, this can surface as an unhandled rejection or a stuck-loading provider at the composition root, which per AD-2 sits above every feature — a settings-fetch failure could plausibly block or blank the entire app, not just typography, contradicting NFR-4's "rather than failing to load."
- **Fix:** Add a sentence to AD-8's Rule requiring the boot fetch to be wrapped such that any failure (network error, malformed payload, timeout) results in no `setProperty` calls at all — leaving `index.css`'s hardcoded defaults as the rendered result — and that this failure must never block `App.tsx`'s own render.
