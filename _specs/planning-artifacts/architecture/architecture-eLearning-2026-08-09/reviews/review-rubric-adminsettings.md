# Rubric Walk — AD-8 (SiteSettingsContext) vs. `prd-eLearning-AdminSettings-2026-08-15`

**Scope:** ARCHITECTURE-SPINE.md read in full (AD-1 through AD-8); judgment focused on AD-8, the entry added for this PRD. Cross-checked against `prd-eLearning-AdminSettings-2026-08-15/prd.md` (FR-1–FR-17, NFR-1–NFR-5) and `addendum.md`.

## Verdict: CONDITIONAL PASS

AD-8's core call — a dedicated `SiteSettingsContext`, split out from `DomainContext` per AD-4's own precedent, applying fonts via `setProperty` on CSS custom properties rather than templating a `<style>` tag — is sound, well-justified, and consistent with AD-1/AD-2/AD-4. It is not a rubber-stamp pass, though: one gap (NFR-4 fail-safe-default under malformed data) is a real, unaddressed divergence point that a future engineer will resolve two different ways depending on who implements it, and two more findings below are secondary but genuine.

## Findings

### 1. (High) NFR-4 "fail-safe default" is only accidentally satisfied for total fetch failure, and not at all for malformed/invalid data
AD-8's Rule says `SiteSettingsContext` "fetches all active Settings once at app boot… On fetch, it applies the active Font Pairing by calling `document.documentElement.style.setProperty(...)`." There is no stated error handling. For a hard fetch failure (network down, 500, timeout), the *lack* of a call to `setProperty` happens to leave `index.css`'s `@theme` defaults in place — so total failure is fail-safe by accident of the mechanism, but the AD never says so, so nothing stops one implementation from adding a try/catch that still calls `setProperty` with `undefined`/partial data on error while another leaves it untouched.

More importantly, NFR-4 also covers "returns malformed or invalid data" — and here the mechanism gives no protection at all. `setProperty` will happily set `--font-display` to whatever string comes back, whether or not it's a currently-curated pairing (FR-10 is a server-side *write*-time check; nothing in AD-8 re-validates on the *read* path). A stale/removed pairing, a partial row, or a bad KeyType payload gets applied verbatim, producing an arbitrary browser font-fallback result — not "render using hardcoded defaults" as NFR-4 requires. AD-8 needs an explicit validation step (only call `setProperty` if the fetched Value matches a known-curated pairing id; otherwise skip and leave the CSS defaults) and an explicit statement that fetch failure is a no-op, not a partial-apply.

### 2. (High) Preview isolation (FR-13/NFR-3) has no scoped mechanism, and AD-8's only stated mechanism is the wrong one to reuse
AD-8 gives exactly one technique for applying a Font Pairing: `document.documentElement.style.setProperty` — i.e., global, `:root`-scoped. FR-13/NFR-3 require the Admin Settings screen's live Preview to affect *only* the preview area — not "this admin's own other tabs," not the live site, until Apply. If a future engineer builds Preview by reusing the only pattern AD-8 documents, they will call `setProperty` on `documentElement` for the candidate pairing and instantly leak it site-wide within that admin's own session, violating FR-13's explicit consequence. AD-8 is silent on this; it should call out that Preview requires a *different*, scoped mechanism (e.g., CSS custom properties set on a wrapper element around the preview sample content, not on `documentElement`) distinct from the Apply-time global mechanism it does specify. This is exactly the kind of divergence point AD-8 exists to close, and it doesn't.

### 3. (Medium) "Calls `settingsService.ts` directly" is ambiguous against AD-2's uniform-hook rule
AD-8: "the Admin screen … calls `settingsService.ts` directly for its own CRUD/Apply/Restore/history UI." AD-2 requires every feature folder to own state via a colocated `use<FeatureName>.ts` hook, "even a thin pass-through," specifically so AD-5's hook-testing convention applies uniformly. "Directly" is plausibly meant only to contrast with going through `SiteSettingsContext` (i.e., "the write path bypasses the Context, not the hook convention") — but as written it can just as easily be read as license to call the service straight from `Settings.tsx`, skipping a `useSettings.ts` hook entirely. That reading would contradict AD-2 and leave the Settings feature without the pure-logic hook test AD-5 expects every other feature to have. Worth one clause of disambiguation.

### 4. (Medium) AD-8's Binds clause overpromises relative to what its Rule actually specifies
AD-8 binds "any future feature reading a runtime UI setting (font today; color/spacing/logo later, per the PRD's own generic settings table)." But the Rule only describes a CSS-custom-property side-effect pathway (`setProperty` on `--font-*` variables) — it establishes no general read API (e.g., a `useSiteSettings()` hook returning `{ data, isLoading, error }` per AD-1's own hook-shape convention) for a setting that isn't naturally CSS-representable, such as a future Logo URL that a component would need to read as a JS value for an `<img src>`, not as a custom property. A future engineer extending this for Color/Spacing/Logo has no established consumption pattern to follow beyond the font-specific one — the AD claims broader scope than it delivers.

### 5. (Low) Role-gating precedent citation is internally inconsistent
AD-8's Structural Seed entry for `Settings/` says it matches "the `AiConfiguration/`/`TagManagement/`/`ErrorLog/` sibling precedent already in the seed." But those three are not a single access pattern: `AiConfiguration` and `ErrorLog` are both Master-only per this same spine (ErrorLog's seed comment says so explicitly), while the PRD (§4.2, FR-4) deliberately puts Settings at Support-tier, explicitly *unlike* AI Configuration's stricter gate ("Support-tier access mirrors the lower-risk Tag Management precedent rather than AI Configuration's stricter one"). Citing all three as one undifferentiated precedent glosses over exactly the distinction the PRD calls a deliberate decision. Not a fabricated risk — FR-4/NFR-2 role-gating plumbing itself is pre-existing (`useAdminPanel.ts`'s `AdminSubTab` pattern) and outside AD-8's real scope — but the seed's wording could mislead an implementer into copying `AiConfiguration`'s Master-only gate instead of `TagManagement`'s Support-tier one.

## Non-findings (checked, no issue)

- **AD-4 relationship:** AD-8 correctly extends AD-4's already-established precedent (`CourseContentContext`) for splitting out a second cross-cutting entity rather than folding settings into `DomainContext`. No scope-blur repeat of the `DomainContext.courses`/drafts near-miss.
- **AD-1 relationship:** the fetch goes through `settingsService.ts`, matches the async/`Promise`-typed convention, and doesn't reach around the data-access boundary. No `fetch`/`axios` call sites bypass `services/*`.
- **AD-2 relationship:** `SiteSettingsContext` is created at the `App.tsx` composition root as required; App.tsx itself gains no new business logic.
- **Deferred section:** the one AD-8-relevant Deferred item ("Real-time settings push") is correctly scoped to and justified by NFR-1 (next-page-load propagation is sufficient) — it does not open a divergence gap for this feature.
- **FR-12 (runtime application without rebuild):** the `setProperty`-on-custom-property mechanism is a real, technically sound way to satisfy this without a `<style>`-tag templating footgun, and the addendum's codebase research backs the approach.
