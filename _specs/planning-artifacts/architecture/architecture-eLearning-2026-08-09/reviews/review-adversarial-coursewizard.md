# Adversarial Review — New Course Wizard Additions

## Verdict

The spine leaves at least two genuine two-owners-of-one-entity holes (the content tree, and the draft Course) and one enforceability gap (AD-1 vs. `aiGatewayService.ts`) wide enough that two AD-compliant engineers would ship incompatible builds; it needs a new/tightened AD before implementation starts, not just a docs note.

## Findings by severity

### CRITICAL

**1. The Chapter→Topic→Subtopic content tree has no named home — CourseContentEditor and CoursePlayer will each build their own copy.**

- **Where:** AD-4 (`context/DomainContext.tsx`, line 167: `"courses + user (profile, progress, points, streak)"`); Structural Seed `features/CourseContentEditor/` (line 149) and `features/CoursePlayer/` (lines 135–143).
- **The gap:** AD-4's own rationale paragraph explicitly anticipates this failure mode for `user.progress`/`totalPoints` ("if each feature independently fetched/cached its own copy... one feature's mutation would silently not appear in another's view") and fixes it by putting `courses` + `user` in `DomainContext`. But the PRD/UX spec establish that Course Content Editor (tree authoring: add/edit/delete/reorder Chapter/Topic/Subtopic/Content Block, per-node confirmation state) and Course Player (Drill-Down levels, Ways, Exercises, keyword popovers — read from the *same* Topic/Subtopic nodes, per PRD §4.6–§4.9 and EXPERIENCE.md lines 238–242) both read and write the identical nested tree. `DomainContext`'s `courses` is never disambiguated as catalog-summary (title/tags/thumbnail — what CourseDiscover/Dashboard need) vs. full nested tree with cached AI content (what the editor and player need) — these are materially different shapes and payload sizes.
- **Incompatible-build scenario:** Engineer A (Course Content Editor) reads `DomainContext.courses` and assumes the course object there already carries the full tree, patching it via `setCourses`/a reducer inside the Context. Engineer B (Course Player), needing per-Topic Drill-Down/Ways/Exercise/keyword data, reasonably infers `DomainContext.courses` is the lightweight catalog shape (since that's what `CourseDiscover` needs it for) and instead adds a feature-local `useCoursePlayer` fetch-and-cache of `coursesService.getCourseContent(courseId)`. Both engineers followed AD-4's letter ("entity read/written by 2+ features → Context"); neither agreed on *what* "courses" contains. Result: two independently fetched, driftable copies of the tree — a tutor's node edit/confirm in the editor doesn't invalidate the Player's cached copy (or vice versa for a student's exercise submission), reproducing exactly the bug AD-4 was written to prevent, just for the PRD's new entity.
- **Fix:** Add a new AD (or extend AD-4 with an explicit sub-clause) that (a) names the content-tree entity — Chapter/Topic/Subtopic/Content Block plus its Drill-Down/Way/Exercise/keyword-definition cache and per-node confirmation state — as cross-cutting between `CourseContentEditor` and `CoursePlayer`; (b) states explicitly whether it lives in `DomainContext` (and if so, gives `DomainContext.courses` two documented shapes — summary vs. full — or splits into `DomainContext.courses` + a new `DomainContext.courseContent` keyed by course id) or in a new `CourseContentContext`; and (c) states that both features must consume it through the same accessor, not independent service calls.

**2. Draft Course has no named owner between CourseWizard/CourseContentEditor (authoring) and the catalog-facing DomainContext (publishing).**

- **Where:** AD-4's Rule ("any domain entity read or written by two or more features... lives in a Context provider... at App.tsx"); Structural Seed `features/CourseWizard/` (line 148, "metadata side-panel steps 1-4") and `features/CourseContentEditor/` (line 149).
- **The gap:** Per the PRD's entity model (`prd.md` line 88), "Course" = metadata (from CourseWizard) + content tree (from CourseContentEditor), and it isn't a finished, catalog-visible entity until Publish (Draft → In Review → Review Confirmed → Published, PRD line 518). `Course` as an entity is now read/written by CourseWizard, CourseContentEditor, CourseDiscover, Dashboard, CourseOverview, and CoursePlayer — squarely "2+ features" under AD-4's literal rule. Nothing in the spine distinguishes an in-progress draft from a published, catalog-eligible course.
- **Incompatible-build scenario:** Engineer A reads AD-4 literally — `Course` touches 2+ features, so it belongs in `DomainContext` — and has CourseWizard push its in-progress draft (partial metadata, no confirmed tree yet) straight into `DomainContext.courses` as soon as Step 1 is filled in, because that's the one Context every course-reading feature already consumes. This leaks unpublished drafts into `CourseDiscover`'s public catalog and `Dashboard`'s "My Courses" list, both of which assume `DomainContext.courses` means "published." Engineer B, sensing that's wrong, keeps wizard/editor draft state entirely feature-local (a shared hook or route-param-threaded id between `CourseWizard` and `CourseContentEditor`) and only calls a service to add the course to `DomainContext.courses` at Publish. Both builds satisfy AD-4's text; they disagree on when a `Course` becomes visible through the shared Context, and integrating them means CourseDiscover has two possible, contradictory sources of "current courses."
- **Fix:** State explicitly in the spine that `Course` has a draft/authoring-phase representation that is *not* the same object as the one in `DomainContext.courses`, name where draft state lives during CourseWizard→CourseContentEditor handoff (feature-local, shared between exactly those two features — not the cross-cutting Context), and state that only the Publish action's service call is what makes a course appear in `DomainContext.courses`.

### HIGH

**3. AD-1's enforceable rule only names two files, not "any direct network/backend call" — leaves `aiGatewayService.ts` bypassable by construction, not just by convention drift.**

- **Where:** AD-1 Rule ("only `src/services/*` may import `src/data/mockData.ts` or `src/lib/offlineStorage.ts`"); `services/aiGatewayService.ts` (line 177, described only as "same async/typed-Promise shape as every other service, per AD-1").
- **The gap:** AD-1's *Binds* section says "all persistence (mock data today, `localStorage`, and a future API)" in prose, but the actual checkable Rule sentence enumerates exactly two files — `mockData.ts` and `offlineStorage.ts` — and says nothing about raw `fetch`/`XMLHttpRequest`/HTTP-client calls to the backend. There is no lint enforcing any of this today (AD-3's Deferred note admits the whole layering rule is code-review-only). A component that calls `fetch('/api/ai/explainTopic', ...)` directly imports neither forbidden file, so it doesn't violate AD-1's literal rule at all.
- **Incompatible-build scenario:** Engineer A, building Course Content Editor's "regenerate explanation" / "extract structure" actions, wires them straight to `fetch()` against the backend's `IAiGateway` endpoints (AD-14 in the backend spine) — fast, and passes review under AD-1's literal text since it touches neither named file. Engineer B, building Course Player's on-demand generation fallback (UX spec line 123: a failed pre-generation regenerates on-demand) and Admin's AI Configuration usage view, correctly routes through `aiGatewayService.ts`. The two paths diverge in request/response typing, retry/error handling, and loading-state shape (AD-1's `{ data, isLoading, error }` convention only applies to the service-routed path); AD-5's "service module is the mock boundary, never mock lower" testing convention has nothing to mock for the direct-`fetch` path; and AD-1's whole reason for existing — swap mock/backend by editing `services/` only — breaks for every direct-`fetch` call site.
- **Fix:** Tighten AD-1's Rule to read "no module outside `services/*` may perform a network call (fetch/XHR/HTTP client) or import a persistence module directly — this covers `data/mockData.ts`, `lib/offlineStorage.ts`, and any call to the backend API including AI gateway endpoints," explicitly naming `aiGatewayService.ts` as the only legal caller of `IAiGateway`.

**4. AD-6 promises editor/student rendering parity but AD-3's import list gives no legal, shared home for the Drill-Down/Ways/Exercise/keyword renderer both views need.**

- **Where:** AD-6 Binds ("editor and student views"); AD-3 Rule (`features/*` may import only `ui/*`, `hooks/*`, `services/*`, `lib/*`, `types.ts`, and the AD-4 Context — no mention of importing another `features/*`); `features/CourseContentEditor/` (line 149, no component listed for Review-as-Student); prior-art gap already flagged in `review-architecture-feasibility.md` (low finding): FR-18/19/20 (Ways, Exercises, Keywords) are "not confirmed to already live in `DrilldownPanel.tsx`" and read as net-new UI whose placement is undecided.
- **Incompatible-build scenario:** FR-23's "Review as Student" mode inside Course Content Editor must exercise "every interactive adaptive-learning affordance available to a real student" (drill-down, way-cycling, exercise submission, keyword click) — i.e., the same rendering as the real `CoursePlayer`. AD-3's checkable import list gives `features/CourseContentEditor/*` no legal way to reuse `features/CoursePlayer/*` components, and the renderer can't live in `ui/*` either (it fetches/mutates domain data per AD-3's own disqualifying test). Engineer A imports `DrilldownPanel`/Ways/Exercise/keyword components directly from `features/CoursePlayer/` into `features/CourseContentEditor/` — functionally correct for parity, but violates AD-3's letter (no feature-to-feature import is permitted anywhere in the spine). Engineer B, respecting AD-3 as written, duplicates the Drill-Down/Ways/Exercise/keyword rendering logic inside `features/CourseContentEditor/`. The two implementations are free to diverge pixel-for-pixel over time — exactly the drift AD-6's golden-file screenshots exist to catch — except there's no single canonical implementation for the golden files to be golden *of*, since two independently-built trees now exist.
- **Fix:** Either (a) amend AD-3's checkable import list to explicitly permit `features/CourseContentEditor/*` to import specific exported components from `features/CoursePlayer/*` (naming CoursePlayer as canonical owner of the adaptive-learning renderer), or (b) extract the Drill-Down/Ways/Exercise/keyword-popover renderer into its own shared location (e.g. a new `features/ContentRenderer/` or a carve-out under `hooks/`+`ui/`-adjacent shared components) that both `CoursePlayer` and `CourseContentEditor` import, and update AD-3 to name that path explicitly.

### MEDIUM

**5. No single owner for the "edit resets confirmation state" business rule across the manual-edit path and the AI-regeneration path.**

- **Where:** PRD line 268 (an edit that changes structure/content or triggers Drill-Down/Way regeneration resets that node's confirmation, FR gate on Review-as-Student/Publish); spine names no service/hook for content-tree node writes at all (no `contentService.ts`/`courseContentService.ts` in the `services/` list at lines 172–177).
- **Incompatible-build scenario:** A tutor's manual node edit (through Course Content Editor's UI) and an `aiGatewayService.ts`-driven regeneration (`rewriteExplanation`/`explainTopic` results overwriting a node's cached content) both need to reset the same node's `confirmed` flag under the same business rule, but the spine names no single function both paths must call. Engineer A implements the reset inside a `CourseContentEditor`-local hook that runs on manual edits only. Engineer B implements a second, separate reset inside whatever wraps the `aiGatewayService` regeneration call. The two copies of "when does confirmation reset" logic drift (e.g., one resets on any AI regeneration even when content is byte-identical after a fallback-served response; the other doesn't reset on a structural reorder that changes a node's context without changing its own text) — a state-mutation-path clash on the same entity.
- **Fix:** Name a single content-tree write function (e.g. `coursesService.updateNode()` or a new `contentService.ts`) as the only path both manual edits and AI-regeneration writes flow through, so confirmation-state derivation is implemented exactly once.

**6. Tag entity has two touching features (TagManagement CRUD owner, CourseWizard Step 2 consumer) and isn't named in AD-4's Context list.**

- **Where:** AD-4's enumerated Context contents (`DomainContext` = courses + user; `SessionContext`; `AccessibilityContext` — no Tags); `features/Admin/TagManagement/` (line 152) vs. `features/CourseWizard/` Step 2 ("Tags").
- **Incompatible-build scenario:** Under AD-4's literal "2+ features → Context" rule, Tags qualify, but nothing says so. TagManagement reasonably keeps its list feature-local (it owns CRUD). CourseWizard's Step 2 independently fetches its own tag list via a feature-local hook for the picker. Lower-stakes than findings 1–4 (read-mostly, no concurrent-write race), but if a tutor deactivates/renames a tag in TagManagement mid-session while a CourseWizard tab elsewhere is open with a stale fetched list, the two disagree on which tags are selectable/valid.
- **Fix:** State explicitly whether Tags are feature-local-with-refetch-on-mount (acceptable given low churn) or added to `DomainContext` — don't leave it to be inferred from AD-4's general rule.
