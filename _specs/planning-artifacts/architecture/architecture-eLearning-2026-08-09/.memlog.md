- (decision) AD-1 [ASSUMPTION] Paradigm: feature-folder architecture with a repository/service boundary. Layers: features/ (composed, stateful) -> ui/ (pure presentational primitives) + hooks/ (shared cross-feature hooks) + services/ (data-access boundary) + lib/ (pure framework-agnostic utils, unchanged) + types.ts (shared domain types). Binds: whole src/ tree. Prevents: features reaching past the service boundary straight into mock/API data, and presentational primitives picking up feature-specific business logic. Chosen because it generalizes the one convention the codebase already has (CoursePlayer/) instead of inventing a new pattern, and the repository boundary is the one seam that makes 'swap mockData for a real backend later' possible without touching component internals.
- (decision) AD-2 [ASSUMPTION] Component layering: App.tsx becomes a thin composition root only (top-level nav state + which feature is active); each former top-level view (Dashboard, CourseDiscover, CourseOverviewScreen, CoursePlayer, AssignmentsView, GroupStudyView, TutorHubView/TutorEducatorHubView/StudentTutorBookingView, ProgressAndCertificate) moves under src/features/<FeatureName>/ as a feature-folder owning its own state via a colocated hook (use<FeatureName>.ts) and its own subcomponents. Binds: src/App.tsx, src/features/**. Prevents: a single 1000+ line file mixing data-shaping, state, and JSX (e.g. current TutorEducatorHubView.tsx at 1152 lines). Rule: a feature folder's top component orchestrates; it delegates rendering to child components under the same folder and delegates data-shaping to the colocated hook.
- (decision) AD-3 [ASSUMPTION] Data-access boundary: src/services/ gets one module per domain entity (coursesService.ts, tutorService.ts, groupStudyService.ts, userService.ts, reviewsService.ts), each exporting async functions with the exact shape a future REST/API client would have (e.g. getCourses(): Promise<Course[]>, bookTutorSlot(slotId, notes): Promise<TutorCalendarSlot>). Internally these resolve from src/data/mockData.ts today. Binds: all data reads/writes. Prevents: components or hooks importing src/data/mockData.ts directly (only services/ may import it). Rule: swapping mock for a real backend later means editing services/ only -- zero changes to features/ or ui/.
- (decision) AD-4 [ASSUMPTION] State management: no new state library added (React 19 built-in useState/useReducer only, matching current practice -- no redux/zustand/jotai in package.json today). Cross-cutting state (authenticated user/session, active language, active nav tab) lives in a small set of React Context providers created at the App composition root; feature-local state stays inside each feature's own hook and is never lifted higher than it needs to be. Binds: all state. Prevents: re-introducing App.tsx as a God-component that owns every feature's local state, and prevents overengineering with a new dependency the project doesn't need at this scale.
- (decision) AD-5 [ADOPTED] Dependency direction (enforced import direction): features/* may import ui/*, hooks/*, services/*, lib/*, types.ts. ui/* may import lib/* and types.ts only -- never features/* or services/*. services/* may import lib/* and types.ts only -- never features/* or ui/*. Binds: all src/ modules. Prevents: circular deps and presentational primitives silently growing business/domain knowledge. This is the direct generalization of how CoursePlayer/ already relates to the rest of the tree, so it's adopted from existing reality, not invented.
- (decision) AD-6 [ASSUMPTION] Testing conventions: vitest + @testing-library/react + jsdom, config lives in vite.config.ts (test key) reusing the existing @/* alias -- no separate test bundler config. Test files are colocated next to the source they test (Component.test.tsx / useThing.test.ts / thingService.test.ts), matching the codebase's existing colocation style (CoursePlayer/ subfiles, not a mirrored __tests__ tree). Binds: all new and refactored code. Rule: services/ and hooks/ get pure-logic unit tests (no DOM); ui/ primitives get RTL render + interaction tests; feature top components get at least one RTL smoke test asserting the feature renders and its primary action fires the right service/hook call.
- (constraint) Naming conventions ratified from existing code: components PascalCase.tsx (Dashboard.tsx), utility/lib files camelCase.ts (offlineStorage.ts, i18n.ts), mock/constant data SCREAMING_SNAKE_CASE exports (MOCK_COURSES). New conventions follow the same pattern: hooks camelCase starting with use (useCourses.ts), services camelCase ending in Service (coursesService.ts), feature folders PascalCase (features/CourseDiscover/) matching the CoursePlayer/ precedent.
