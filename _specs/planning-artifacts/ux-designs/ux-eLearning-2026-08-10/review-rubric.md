# Spine Pair Review — FlexDemy

## Overall verdict

A downstream consumer can source-extract cleanly for most of this pair: tokens resolve, all four mockup files are linked with clear dispositions, all five PRD sources exist on disk, section shape matches the canonical templates, and the four new ContentAuthoring components (content-doc-heading, content-page-marker, content-resource-block, content-slash-menu) are coherent and consistently flagged wherever the superseded content-tree-node model still appears. Two real gaps keep this from "strong": the ContentAuthoring PRD's UJ-2 (extraction-to-blocks) and UJ-3 (resource depth/inheritance/delete-guard) have no Key Flow mirror at all — and UJ-2's "Insert from file" mechanic may be a genuine capability drop, not just a documentation gap — and the new authoring surface's "empty document / first open" state, despite being explicitly called out as replacing the old wizard's removed "Continue setting up" state, only exists as flow narrative, not as a formal State Patterns row like every other empty state in the document.

## 1. Flow coverage — thin
Checked every UJ implied by EXPERIENCE.md's sources frontmatter (Dashboard PRD UJ-1/2, Assignments PRD UJ-1/2, CourseWizard PRD UJ-1–4, ContentAuthoring PRD UJ-1–4) against EXPERIENCE.md's Key Flows section for named protagonist, numbered steps, climax, and edge/failure path.
### Findings
- **high** ContentAuthoring PRD's UJ-2 (Meera extracts a PDF section into editable blocks via "Insert from file" / two-pane section selector) and UJ-3 (per-node/page resource attachment depth, ancestor inheritance, delete-blocked-while-in-use) have no Key Flow entry anywhere in EXPERIENCE.md — only UJ-1 is mirrored, and it's explicitly reinterpreted through the document/slash-command model (EXPERIENCE.md "Key Flows" §ContentAuthoring PRD · UJ-1, lines 281–293; PRD `prd-eLearning-ContentAuthoring-2026-08-16/prd.md` UJ-2/UJ-3). *Fix:* add Key Flow entries for UJ-2 and UJ-3, reinterpreted through the validated document model the same way UJ-1 was, or explicitly scope them out with a `[NOTE FOR UX→PM]`.
- **medium** The extraction-into-blocks mechanic itself (PRD FR-19–21: upload picker, two-pane section selector, copy-on-insert into the body) has no clear analog in EXPERIENCE.md — the only "Insert-from-file" text sits inside the Learning Resources block row (Component Patterns, "Content document — Learning Resources block") and reads as a resource-attach action, not a content-into-body-blocks action. (EXPERIENCE.md Component Patterns, line 82.) *Fix:* confirm with PM/UX whether extraction-to-blocks survives in the validated document model; if it does, document where it lives, if not, record the descope explicitly.

## 2. Token completeness — strong
Extracted every token in DESIGN.md's YAML frontmatter (colors, typography, rounded, spacing, components) and every `{path.to.token}` reference across both files, then checked each reference resolves to a definition and every color has a hex value.
### Findings
- **medium** `{components.spinner}` is referenced in DESIGN.md's `extraction-status-badge.inProgressSpinner` field ("additionally carry a small `{components.spinner}` (xs, white...)", DESIGN.md line 192) but `spinner` is never defined as an entry in the frontmatter `components:` block. (All 17 colors have hex values — no other misses found; typography/spacing/rounded references all resolve.) *Fix:* add a minimal `spinner` component entry to frontmatter, or drop the token syntax and describe it as plain prose.

## 3. Component coverage — adequate
Extracted every component name used in either file and checked for a DESIGN.md visual row and an EXPERIENCE.md behavioral row, with particular attention to the four new ContentAuthoring components and the superseded content-tree-node entries.
### Findings
- **medium** DESIGN.md's `{components.course-content-editor}` bullet (## Components) still reads "Composed from `{components.content-tree-node}` rows plus `{components.extraction-status-badge}`..." with no supersession note of its own — the correction lives in the *preceding* bullet ("Course Content Editor — body composition"), so a reader who jumps straight to `course-content-editor` (the token EXPERIENCE.md's Course Content Editor rows actually cite) can land on stale tree-composition language. (DESIGN.md lines 276–277.) *Fix:* add a short inline pointer inside the `course-content-editor` bullet itself rather than relying on bullet order.
- **low** State Patterns rows for extraction/confirmation/publishing ("Node pending confirmation," "Publishing (async batch)" — "12 of 34 confirmed nodes generated," "Node generation failed/degraded") still use generic "node" language inherited from the pre-ContentAuthoring tree model, while the new model's confirmable units are specifically headings (`content-doc-heading`) and pages (`content-page-marker`). Not contradicted, but not renamed either. (EXPERIENCE.md State Patterns, lines 128–131.) *Fix:* define "node" as an explicit umbrella term for heading-or-page in the new model, or rename these rows.
- **low** "Course version history" (Component Patterns row, EXPERIENCE.md line 84) has no corresponding DESIGN.md visual entry at all. Every other Component Patterns row either has a matching DESIGN.md bullet or an explicit "composes from X, not separately defined" disclaimer (see DESIGN.md Do's and Don'ts' Course card/Booking grid/Masterclass card note); this one has neither. *Fix:* add a one-line visual note, or fold it into the existing "not separately defined" disclaimer list.
- **low** Row/bullet display names differ verbatim between the two files for the same token — e.g. DESIGN.md "Content resource block" vs. EXPERIENCE.md "Content document — Learning Resources block" for `{components.content-resource-block}`; DESIGN.md "Content page marker" vs. EXPERIENCE.md "Content document — Page marker." Token IDs match so resolution isn't broken, but it complicates a straight name-match check between the two specs. *Fix:* align display names to the token name, or a fixed transform of it.
- Positive: the four new components (content-doc-heading, content-page-marker, content-resource-block, content-slash-menu) each have real, specific behavioral rules in EXPERIENCE.md (not one-word descriptions), and the superseded content-tree-node entry is explicitly marked "Superseded... kept as history" in every location it still appears (DESIGN.md frontmatter, DESIGN.md Components bullet, EXPERIENCE.md Component Patterns row, EXPERIENCE.md Accessibility Floor bullet) except the one course-content-editor composition sentence noted above.

## 4. State coverage — thin
Walked every IA surface's states, focusing on Course Content Editor given the removal of the old wizard's "Continue setting up" state.
### Findings
- **high** No dedicated State Patterns row exists for "empty document / first open" on the new Course Content Editor authoring surface. The state is described only narratively, inside the ContentAuthoring UJ-1 Key Flow ("she sees one empty document titled with the course name, cursor active on the first line... there is no 'Continue setting up' affordance because there was never a step to resume," EXPERIENCE.md lines 285, 291) — not as a table row, unlike every other empty state in the document (Empty — no submissions, Empty — no certificates yet, Empty — tutor has no courses yet, etc., all in the State Patterns table). A consumer who scans only the canonical State Patterns table — the documented pattern this spec uses everywhere else — would miss this state entirely. *Fix:* add an explicit "Empty — first open / no content yet" row for Course Content Editor to the State Patterns table, cross-referencing the Key Flow.
- **low** No explicit "cold-load / loading existing document" state is defined for Course Content Editor's document body itself when re-opening a Chapter with existing content (distinct from My Courses' own "Loading" row, which covers the list, not the editor's content). *Fix:* add a loading-state row, or state explicitly that it inherits the app's global loading pattern.

## 8. Shape fit — strong
Checked DESIGN.md section order against the canonical order and EXPERIENCE.md against its required section list.
### Findings
- **low** DESIGN.md matches the canonical order exactly (Brand & Style → Colors → Typography → Layout & Spacing → Elevation & Depth → Shapes → Components → Do's and Don'ts). EXPERIENCE.md has all nine required sections present, but the actual order is Foundation → IA → Voice and Tone → Component Patterns → State Patterns → Interaction Primitives → Accessibility Floor → **Responsive & Platform → Key Flows** — the last two sections are swapped relative to the canonical order (Key Flows before Responsive & Platform). Not load-bearing, purely ordering. *Fix:* move Key Flows above Responsive & Platform, or treat the swap as an accepted convention if intentional.
