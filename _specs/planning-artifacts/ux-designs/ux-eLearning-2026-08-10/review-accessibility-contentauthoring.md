# Accessibility Review — Content Authoring Document/Slash-Command Model

- **The "accessible primary entry" affordance is entirely absent from the reference mock.** EXPERIENCE.md's Accessibility Floor states the "+" click path "is the accessible primary entry, independently focusable and Tab-reachable" — but `mockups/key-content-doc-slash.html` never renders a "+" affordance anywhere in the document body (the only "+" in the file is `.rail-cta`'s unrelated "+ New chapter" button). The one artifact meant to validate this interaction shows only the "/"-triggered state. There is no visual spec for what "+" looks like, where it sits relative to a block, its hit-target size, or whether it's always-visible or hover/focus-revealed — which matters directly for whether a keyboard-only user can ever discover it (see next finding).

- **No confirmation that "+" is keyboard-discoverable rather than hover-only.** Notion-style block affordances conventionally render a "+"/handle only on mouse hover near a line. Neither DESIGN.md's `content-slash-menu` entry nor EXPERIENCE.md's Interaction Primitives/Accessibility Floor states that "+" must also appear on keyboard `:focus`/`:focus-within` (not just `:hover`). If it's implemented hover-only, the "accessible primary entry" the spec relies on to justify keeping "/" as a shortcut would itself be keyboard-inaccessible, undermining the whole justification in Interaction Primitives ("'/' … never … only").

- **The "/" keydown listener isn't shown being suppressed during IME composition.** Interaction Primitives (EXPERIENCE.md) correctly identifies that "IME-heavy input … can consume or reinterpret a bare '/' keystroke during composition" and offers "+" as the accessible alternative — but offering an alternative path doesn't stop the "/" keydown handler itself from still firing during Hindi/Devanagari IME composition. Nothing in either file specifies gating the handler on `event.isComposing` / `compositionstart`–`compositionend`, so a tutor composing Devanagari on an empty line could still have "/" misfire and pop the menu mid-composition, corrupting the composition — the presence of "+" doesn't fix this, it only gives an escape hatch after the fact.

- **Firefox's native Quick Find ("/") conflict is not addressed.** In Firefox, pressing "/" with focus anywhere outside a form field opens the browser's built-in Quick Find toolbar. Neither file specifies the DOM structure of an "empty line" (contenteditable region vs. a focused `<textarea>`/`<input>`) precisely enough to confirm this can't happen, and the browser-level keybinding conflict for a bare "/" trigger is never mentioned anywhere in the Accessibility Floor or Interaction Primitives sections, despite this being one of the most well-known real-world failure modes of a bare "/" shortcut.

- **The underlying editing DOM model (contenteditable vs. discrete form fields) is unspecified, and the mock's own implementation contradicts the spec's semantic-heading promise.** EXPERIENCE.md's Component Patterns row "Content document — heading structure" states Topic/Sub-Topic render as "real semantic `<h2>`/`<h3>` elements … not styled `div`s." But the mock (`key-content-doc-slash.html`, lines 232–247) implements exactly the pattern the prose disclaims: `<div class="doc-heading h2"><span class="eyebrow-tag">Topic</span><textarea class="field-ml" rows="1">Chemical Equations</textarea></div>` — a styled `<div>` with a CSS class named "h2" wrapping a `<textarea>`, not a real `<h2>` element at all. Neither file resolves how an element can simultaneously be (a) a real heading discoverable by a screen reader's heading-navigation (H key), and (b) a live in-place-editable text field for the tutor, without either breaking the heading's accessible name computation or abandoning true heading markup for something like `<h2 contenteditable>`. This is a load-bearing open technical question the spec asserts is solved but the only artifact demonstrating it disproves.

- **Chapter-title heading level is never specified, leaving the hierarchy possibly headless at the top.** DESIGN.md's `content-doc-heading` and EXPERIENCE.md both commit only Topic=h2 / Sub-Topic=h3 — neither ever states what element/level the Chapter title itself (the big Fraunces-serif document title at the top of the flowing document, e.g. "Chemical Reactions and Equations" in the mock) uses. Logically it should be h1, but the mock renders it as a bare `<textarea class="doc-title">` with no heading role whatsoever. If shipped as-is, a chapter document's highest heading is h2 (Topic) with no h1 above it — an orphaned hierarchy — and it's also unclear whether the app shell's own editor-header text (`.course-title`, "CBSE Class 10 Science · Content Editor") is intended as the page's real h1, which would put an unrelated chrome heading, not the actual chapter content's title, at the top of the page's heading outline.

- **Page markers are excluded from the heading tree but included in the ToC rail — contradicting the "same structure" accessibility claim.** Both files correctly state Page markers are not headings, only Chapter/Topic/Sub-Topic are. But the mock's outline rail (`.rail`, lines 198–209) lists a page-marker item (`📄 What is a combination reaction?`) as a nav target alongside real heading nodes, and DESIGN.md/EXPERIENCE.md both describe the rail as "auto-derived from the document's headings." A sighted tutor using the rail can jump straight to a Page; a screen-reader user relying on native heading-navigation (which the Accessibility Floor explicitly claims "work[s] against the same structure a sighted tutor sees") cannot reach that same Page via heading shortcuts at all, since it was deliberately left out of the heading tree. This is a direct contradiction between the literal claim and the described mechanism, not just an edge case.

- **The slash-menu's keyboard model repurposes Tab in a nonstandard way with no clarified semantics.** The Accessibility Floor states "Up/Down (or Tab) moves the highlighted row." Tab conventionally moves focus out of the current widget to the next focusable element on the page; using it interchangeably with Arrow-Down to navigate options inside an open menu is a nonstandard combobox/listbox pattern (ARIA APG uses Arrow keys within the list, Escape/Tab to close/exit) and isn't reconciled here — it's ambiguous whether Tab is meant as an alternate "next option" key (breaking users' expectation that Tab always advances focus) or a "commit and exit" key (which would need separate wording from "moves the highlighted row").

- **Zero-match state for the slash menu is undefined, breaking the product's own "never a silent empty state" discipline.** EXPERIENCE.md's State Patterns table catalogs an empty state for nearly every surface in the product (search/filter, submissions, notes, assignments, etc.) but has no row for "no commands match the typed query" in the slash menu — despite this being trivially reachable (e.g., typing "/xyz"). Neither the menu row's own Component Patterns/Accessibility Floor description addresses what renders, or what if anything is announced, when the filtered list is empty.

- **Escape's focus-return destination is unstated, unlike the pattern set elsewhere in the same spec.** The Assignment creation modal's Accessibility Floor bullet explicitly specifies "focus … returns to the triggering 'Create Assignment' button on close." The slash-menu's Accessibility Floor bullet says only "Escape closes without inserting" — it never states where focus lands afterward (back into the same line at the cursor position where "/" was typed, presumably, but this is assumed, not specified), nor whether the literal typed "/" and filter characters remain in the document as plain text or are stripped on cancel.

- **ARIA wiring for the menu is incompletely specified.** The Accessibility Floor names only `aria-activedescendant` for the highlighted row. A working combobox/listbox pattern additionally needs `role="listbox"`/`role="option"` on the menu and its rows, `role="combobox"` (or equivalent `aria-controls`/`aria-expanded`) on the triggering text field, and a defined relationship between grouped category-label rows (are they `role="group"`/`aria-label`, or do they need `aria-setsize`/`aria-posinset` handling so Arrow-Down correctly skips over non-option label rows?). None of this is addressed, only the single `aria-activedescendant` attribute is named.

- **No aria-live confirmation when a block is actually inserted.** Every other new async/state-changing surface in this spec (extraction status, Publishing progress, Hold→Reviewed reveal, keyword popover, confirmation reversion) gets an explicit `aria-live="polite"` announcement commitment. The slash-command menu — the headline new interaction — has none: after a screen-reader user selects "Image" or "Topic heading" from the menu and it closes, there's no specified announcement of what was inserted or where focus/cursor landed, leaving a non-visual user to infer structural changes purely from re-reading the document.

- **Confirmed/unconfirmed heading state may not actually clear "never color-alone."** DESIGN.md's `content-doc-heading.confirmedState` describes the differentiator as "a subtle `{colors.signal-green}` dot beside the heading once confirmed — unconfirmed stays a plain muted dot." Both states are described as dots that differ only in color (green vs. muted gray), with no shape, icon, or text difference called out — unlike the Page marker's confirmation state, which correctly uses a textual `Confirmed`/`Unconfirmed` badge-pill. As literally described, the heading-level indicator doesn't clearly satisfy the "never color-alone" rule it's claimed to follow (WCAG 1.4.1); it needs a specified non-color cue (a filled vs. outline dot, a checkmark glyph, or an `aria-label` distinct from styling) to actually meet the bar the Page-marker version does.

- **Learning Resources block: non-drag path for the upload step is stated, but metadata edits (role, caption, remove, reorder) are not confirmed keyboard-operable at all.** EXPERIENCE.md's Component Patterns row correctly requires a non-drag Upload/Attach-existing/Insert-from-file button row for the *initial add*. But nothing specifies how a tutor sets a resource's Inline vs. Attachment role, edits/adds its caption ("Worked-example script referenced above" in the mock — shown as static text with no visible control), removes a resource, or reorders resource rows without a mouse. The mock itself shows the role only as a static, non-interactive `badge-pill` and the caption only as plain text — there's no rendered control for either, so it's not even confirmed a keyboard-accessible version of these actions exists to check against.

- **The mock's own resource drop-zone doesn't render the buttons the spec promises.** EXPERIENCE.md explicitly requires "an explicit Upload/Attach-existing/Insert-from-file button row" as the non-drag equivalent. The mock's `.res-drop` element (line 310) renders only hint text — "Drag a file, or / resources → Attach existing…" — with no actual buttons for Upload, Attach-existing, or Insert-from-file. As the one visual reference for this component, it fails to demonstrate the very equivalent controls the written commitment depends on.

- **"Pointer to the ancestor" for inherited/read-only resources is not confirmed to be a real operable link.** EXPERIENCE.md says inherited resources render "muted and read-only, with a pointer to the ancestor where they're actually managed." Given this product's own stated discipline elsewhere ("a real focusable/keyboard-operable element … not a `div` with only an `onClick`"), it's not specified whether this "pointer" is an actual focusable link that navigates/scrolls to the ancestor's resource block, or just descriptive text (e.g., "(inherited from Chapter)") with no operability at all.

- **No loading state defined for opening Course Content Editor's document view.** EXPERIENCE.md's State Patterns table gives explicit labeled-loading treatment to My Courses ("Loading your courses…"), the whole-app load, and Home/Discover's cold load — but has no row for fetching an existing chapter's document content when Course Content Editor opens on a non-empty course. UJ-1 (ContentAuthoring PRD section) narrates only the empty-course case ("she sees one empty document … cursor active on the first line"); the populated-course fetch/loading path is unaddressed.

- **No error state defined for autosave failure in the flowing document.** The Accessibility Floor commits to "autosave on each node's edit-then-blur" as the *sole* save mechanism (explicitly replacing a page-level "leave without saving?" dialog) but never defines what happens when that autosave call itself fails (e.g., a network drop mid-editing-session). Unlike My Courses' explicit "Load failure" / "action failure" rows with friendly inline errors, or the general "never a silent failure" discipline applied everywhere else in State Patterns, a tutor could lose typed content with no defined visible-text error, no retry affordance, and no `aria-live` announcement — a real regression risk introduced specifically by moving off a beforeunload-prompt safety net.

- **Editing state of a Published (read-only?) course is unaddressed.** My Courses' Component Patterns row states Take Offline is "the sole path back to Draft" from Published. It's never stated whether Course Content Editor even opens on a Published course, and if so, whether the document becomes read-only, and what (if any) permission-denied or read-only state/announcement is shown — unlike Group Study's and Admin's explicit "permission-denied" state rows, Course Content Editor has no analogous row for this scenario.

- **Editing interaction for block types beyond heading/paragraph is unspecified.** The mock shows headings and body paragraphs as editable `<textarea>` fields, but bulleted lists, tables, code blocks, and math blocks are rendered as static, non-editable-looking markup (plain `<ul><li>`, a static `<table>`, a static `.code-block`, a static `.math-block`) with no visible editing affordance for any of them. Neither DESIGN.md nor EXPERIENCE.md specifies the actual in-place editing/keyboard model for these block types, so their keyboard operability (and therefore AA compliance) can't be assessed at all from the current spec — only Image (via its alt-text field) has a demonstrated edit control.

- **Reduced-motion coverage doesn't explicitly name the slash menu's own open/dismiss transition or the flowing document's block-insert transition.** The Accessibility Floor's Motion bullet enumerates confetti, section-nav smooth-scroll, tab crossfade, the Adaptive Ways tray, the keyword popover, and the Publishing checklist as required to respect `prefers-reduced-motion` — every other overlay/animated surface in the spec is listed by name, but the slash-command menu's appear/dismiss animation (`shadow-xl` overlay per DESIGN.md) and any block-insertion animation are absent from this enumerated list, despite being new, animated UI introduced by this same PRD.

- **ToC rail activation for keyboard/AT users isn't confirmed to move real focus.** Dashboard's section nav is explicitly specified elsewhere as click-to-`scrollIntoView`. It's not stated whether activating a Table-of-Contents rail entry in Course Content Editor moves actual DOM focus to the corresponding heading (e.g., via `tabindex="-1"` + `.focus()`) or only visually scrolls — if it's scroll-only, a keyboard/screen-reader user who activates a rail link ends up visually/scroll-positioned at the target but with focus left behind at the rail link, breaking the expected "activate and land there" behavior standard in-page anchors provide.

- **Focus destination after inserting a structural or content block via the slash menu is unstated.** Neither file specifies where the cursor/focus lands after selecting, e.g., "Topic heading" or "Image" from the menu (into the new heading's title field? the new block's first editable field?). This matters for both sighted keyboard users and screen-reader users tracking their position in a continuously-growing document.

- **Multi-chapter navigation (the rail's "+ New chapter" / switching chapters) has no defined focus-management or heading-reset behavior.** Since this is a client-side-state SPA with no router (per EXPERIENCE.md's Foundation section), switching the flowing document from one Chapter to another likely swaps content in place without a full page navigation. Neither file addresses whether focus/heading-navigation state resets appropriately when this happens (e.g., moving focus to the new chapter's title, so a screen-reader user isn't left positioned inside now-replaced DOM content) — the kind of SPA-content-swap accessibility gap the rest of the spec is otherwise careful about (e.g., Admin's "you don't have access" and other explicit state rows).
