FlexDemy — Content Authoring Update — UX Design Validation Report

_specs/planning-artifacts/ux-designs/ux-eLearning-2026-08-10/{DESIGN.md, EXPERIENCE.md}

A downstream consumer can source-extract cleanly for most of this pair: tokens resolve, all four mockup files are linked with clear dispositions, all five PRD sources exist on disk, section shape matches the canonical templates, and the four new ContentAuthoring components (content-doc-heading, content-page-marker, content-resource-block, content-slash-menu) are coherent and consistently flagged wherever the superseded content-tree-node model still appears. Two real gaps keep this from "strong": the ContentAuthoring PRD's UJ-2 (extraction-to-blocks) and UJ-3 (resource depth/inheritance/delete-guard) have no Key Flow mirror at all — and UJ-2's "Insert from file" mechanic may be a genuine capability drop, not just a documentation gap — and the new authoring surface's "empty document / first open" state, despite being explicitly called out as replacing the old wizard's removed "Continue setting up" state, only exists as flow narrative, not as a formal State Patterns row.

The accessibility pass found deeper problems than a routine check usually turns up, and they materially shift the picture. The one artifact meant to demonstrate the new interaction contradicts the spine's own semantic-heading promise — Topic/Sub-Topic render as styled <div>s wrapping <textarea>s in key-content-doc-slash.html, not real <h2>/<h3> elements. The "+" click affordance the spine names as the accessible primary entry point (justifying "/" as a shortcut layered on top, not the sole path) is never actually rendered anywhere in that same mock. And Page markers are excluded from the heading tree while still appearing in the Table-of-Contents rail, directly contradicting the Accessibility Floor's claim that screen-reader heading-navigation "work[s] against the same structure a sighted tutor sees." None of this is unfixable, but the a11y story for this product's first command-driven interaction is currently asserted more confidently in prose than it's demonstrated in the one artifact meant to prove it out.

Accessibility review — Content Authoring document/slash-command model

review-accessibility-contentauthoring.md

A focused WCAG 2.1 AA-minded pass on the new "/" slash-command menu, the flowing-document heading model, and the Learning Resources block — the highest-novelty, highest-risk surface in this update. 23 findings; reported as a flat list per its review method (no severity ranking), preserved in its own adversarial-skeptical voice below.

Flag

The accessible "+" primary entry is entirely absent from the reference mock

EXPERIENCE.md's Accessibility Floor states "+" is "the accessible primary entry," but key-content-doc-slash.html never renders it anywhere in the document body — the only unrelated "+" is the rail's "+ New chapter." No visual spec for size, placement, or hover/focus-reveal exists either.
Flag

No confirmation "+" is keyboard-discoverable rather than hover-only

Neither file states "+" must appear on keyboard :focus/:focus-within, not just :hover. If hover-only, the "accessible primary entry" justifying "/" as a mere shortcut is itself keyboard-inaccessible.
Flag

"/" keydown isn't shown being suppressed during IME composition

Offering "+" as an alternative doesn't stop the "/" handler from still firing mid-Devanagari-composition. Neither file specifies gating on event.isComposing / compositionstart–compositionend.
Flag

Firefox's native Quick Find ("/") conflict is not addressed

Pressing "/" outside a form field opens Firefox's built-in Quick Find toolbar. The DOM structure of an "empty line" (contenteditable vs. focused textarea) isn't specified precisely enough to rule this out, and the conflict is never mentioned.
Flag

The mock's own heading markup contradicts the spec's semantic-heading promise

EXPERIENCE.md says Topic/Sub-Topic are "real semantic <h2>/<h3> elements... not styled divs" — the mock implements exactly that anti-pattern: a styled <div class="doc-heading h2"> wrapping a <textarea>. How an element is simultaneously a real heading and a live-editable field is never resolved.
Flag

Chapter-title heading level is never specified — hierarchy possibly headless at the top

Only Topic=h2/Sub-Topic=h3 are committed. The mock renders the Chapter title as a bare <textarea> with no heading role, leaving h2 as the highest level with no h1 above it, and it's unclear whether the app chrome's own title is meant as the real h1.
Flag

Page markers excluded from the heading tree but included in the ToC rail — contradicts "same structure" claim

A sighted tutor can jump to a Page via the rail; a screen-reader user relying on native heading-navigation cannot, since Page markers are deliberately not headings — directly contradicting the Accessibility Floor's "same structure a sighted tutor sees" claim.
Flag

Slash-menu's keyboard model repurposes Tab nonstandardly

"Up/Down (or Tab) moves the highlighted row" conflicts with Tab's conventional role of moving focus out of the widget; not reconciled against ARIA APG's listbox/combobox pattern.
Flag

Zero-match state for the slash menu is undefined

Every other surface in State Patterns has an empty state defined; the trivially-reachable "no commands match" case (e.g. typing "/xyz") has none.
Flag

Escape's focus-return destination is unstated

Unlike the Assignment creation modal's explicit focus-return spec, the slash-menu's Accessibility Floor bullet says only "Escape closes without inserting" with no stated focus destination or whether typed filter characters are stripped.
Flag

ARIA wiring for the menu is incompletely specified

Only aria-activedescendant is named. A working combobox/listbox needs role="listbox"/"option", role="combobox" or aria-controls/aria-expanded on the trigger, and defined handling for category-label rows — none addressed.
Flag

No aria-live confirmation when a block is actually inserted

Every other async/state-changing surface in the spec commits to an aria-live announcement; the headline new interaction has none for what was inserted or where focus landed.
Flag

Confirmed/unconfirmed heading state may not clear "never color-alone"

content-doc-heading.confirmedState describes both states as dots differing only in color, unlike the Page marker's textual badge-pill — as literally described this doesn't satisfy WCAG 1.4.1.
Flag

Learning Resources block: metadata edits not confirmed keyboard-operable

The non-drag upload path is specified, but setting role, editing caption, removing, or reordering resources has no specified control at all — the mock shows role/caption as static, non-interactive text.
Flag

The mock's resource drop-zone doesn't render the buttons the spec promises

EXPERIENCE.md requires an explicit Upload/Attach-existing/Insert-from-file button row; the mock's .res-drop element renders only hint text, no actual buttons.
Flag

"Pointer to the ancestor" for inherited resources not confirmed operable

Not specified whether this is a real focusable link or just descriptive text, inconsistent with the product's own "real element, not div onClick" discipline elsewhere.
Flag

No loading state for opening Course Content Editor on a non-empty course

State Patterns gives labeled-loading treatment elsewhere (My Courses, whole-app, Discover); the populated-course document fetch path is unaddressed.
Flag

No error state for autosave failure

Autosave-on-blur is the sole save mechanism, explicitly replacing a beforeunload dialog, but no visible-text error, retry, or aria-live announcement is defined if it fails — a real regression risk versus the safety net it replaced.
Flag

Editing state of a Published (read-only?) course is unaddressed

Unclear whether Course Content Editor even opens on a Published course, and if so whether it's read-only — no analogous permission-denied/read-only row exists, unlike Group Study/Admin.
Flag

Editing interaction for blocks beyond heading/paragraph is unspecified

Bulleted lists, tables, code, and math render as static markup in the mock with no visible editing affordance or specified keyboard model — only Image (via alt text) has a demonstrated edit control.
Flag

Reduced-motion coverage omits the slash menu and block-insert transitions

The Motion bullet names every other overlay/animated surface by name; the slash-command menu's own appear/dismiss animation is absent from that list despite being new, animated UI.
Flag

ToC rail activation not confirmed to move real focus

Not stated whether activating a rail entry moves DOM focus to the target heading or only scrolls — if scroll-only, a keyboard/screen-reader user ends up positioned at the rail link, not the target.
Flag

Focus destination after inserting a block via the slash menu is unstated

Neither file specifies where cursor/focus lands after selecting e.g. "Topic heading" or "Image" — matters for both sighted keyboard users and screen-reader users tracking position.
Flag

Multi-chapter switching has no defined focus-management/heading-reset behavior

In this router-less SPA, switching Chapters likely swaps content in place; neither file addresses whether focus/heading-navigation state resets appropriately when this happens.
