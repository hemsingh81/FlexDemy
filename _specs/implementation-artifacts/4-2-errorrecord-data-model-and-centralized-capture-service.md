# Story 4.2: ErrorRecord Data Model and Centralized Capture Service

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a platform engineer,
I want one `ErrorRecord` entity and one `IErrorCaptureService` that owns fingerprinting, categorization, and priority assignment,
so that every future capture site (Stories 4.3, 4.4) shares the same dedup/categorize/prioritize logic instead of reimplementing it.

## Acceptance Criteria

1. **Given** `IErrorCaptureService.CaptureAsync(request)` is called with an exception's type/message/stack/origin, **when** the resulting Fingerprint (exception type + normalized message + origin) does not yet exist, **then** a new `ErrorRecord` is created with `OccurrenceCount = 1`, `FirstOccurredAt`/`LastOccurredAt = now`, `Category` assigned per the FR-9 mapping table (Task 3), `Priority` assigned per FR-10 Phase A (Task 4), and `CorrelationId` populated (Task 6 — see the explicit-override note below). [Source: epics-ErrorObservability.md Story 4.2; PRD FR-8, FR-9, FR-10]
2. **Given** the same Fingerprint occurs again on an existing, non-`Archived`, non-`Resolved` record, **when** `CaptureAsync` runs, **then** `OccurrenceCount` increments and `LastOccurredAt` updates on the same row, not a new one, **and** Phase B's spike-threshold check runs and escalates Priority to P1 if it crosses the threshold while at P2/P3. [Source: PRD FR-8, FR-10 Phase B]
3. **Given** an existing `ErrorRecord` with `Status = Resolved` or `Status = Archived`, **when** its Fingerprint recurs, **then** `CaptureAsync` flips `Status` back to `New`, increments `OccurrenceCount`, updates `LastOccurredAt`, and does **not** reset `Priority` — even if it was previously manually increased. [Source: PRD FR-16]
4. **Given** a captured value under a deny-listed field name (`Authorization`, `ApiKey`, `Password`, `Token`, case-insensitive) or matching a secret-shaped free-text pattern (Bearer tokens, `gsk_`/`sk_`/`AIza`-style prefixes, `Password=`/`Pwd=` connection-string segments), **when** it appears anywhere in the captured `Message`, `StackTrace`, or structured context, **then** that value is replaced with `"[REDACTED]"` before the row is persisted. [Source: PRD FR-5]
5. **Given** `CaptureAsync` itself fails (e.g. a database write error), **when** that happens, **then** the failure is swallowed inside `IErrorCaptureService` and never propagates back to the caller. [Source: PRD NFR2 (Reliability)]
6. **Given** `CaptureAsync` is invoked from a request or job's hot path (NFR1), **when** it runs, **then** it does not add more than ~50ms to p99 request latency or ~200ms to a background job's total run time — no synchronous blocking database write sits on the caller's critical path. [Source: PRD Cross-Cutting NFRs, `[ASSUMPTION: confirm before build]`]
7. **Given** the `ErrorRecord` table, **when** the future admin list view (Story 4.5) queries it, **then** it is indexed on `Fingerprint`, `Category`, `Priority`, `Status`, and `LastOccurredAt`. [Source: PRD FR-8's NFR, NFR3]

## Dev Notes

- **This story, too, has no independently observable user value** — it's the shared engine Stories 4.3/4.4 (capture sites) and 4.5-4.7 (admin UI) all depend on. Same atomic-release-unit framing as Story 4.1.
- **AD-24's two-controller split is Story 4.5's concern, not this one's** — this story only builds the service both controllers will eventually call; do not build `ErrorsController`/`ErrorReportingController` here.
- **Do not let this service throw, ever** — NFR2 is explicit that the observability system must never become a second source of outages. Every other Application service in this codebase signals failure via a thrown `AppException` subtype (AD-5/AD-10); this is a deliberate, narrow exception to that house rule, scoped to exactly this one method.
- **The redaction guardrail (Task 5) is the one piece of this story with real security consequence** — get the regex patterns reviewed carefully; a pattern that's too narrow silently leaks a secret shape the PRD's own "Corrections Made During Review" section already flagged as a real, previously-missed gap (see addendum's item 3).
- **This story deliberately resolves the FR-22/FR-23 Correlation ID plumbing gap the implementation-readiness review flagged (2026-08-13)** — see Task 6's `CorrelationIdOverride ?? accessor.Current` resolution. Story 4.4 must pass the frontend-supplied Correlation ID into this parameter; it must not rely on this service falling back to the ambient accessor for that one call path.
