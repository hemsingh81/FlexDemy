# Story 2.4: Course Metadata Persistence & Live-Wire Wizard

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tutor,
I want Story 2.1's wizard to persist my Title, Thumbnails, and step progress to a real Draft,
so that my work is saved, not just held in local mock state.

## Acceptance Criteria

1. **Given** real course/draft endpoints exist, **when** a wizard step is completed (Next, Back, or Finish), **then** state auto-persists as a real `Course` row with `LifecycleState = Draft` after every step — not just held in the wizard's local React state. [Source: epics.md Story 2.4]
2. **Given** a required, single-line Course Title, **when** submitted, **then** it is trimmed, validated non-empty, and enforced against `COURSE_TITLE_MAX_LENGTH` (120) — both client-side (already true, Story 2.1) **and** server-side (new in this story — the backend must not trust the client alone, matching Story 1.5/1.9's established convention). [Source: epics.md Story 2.4]
3. **Given** up to 3 thumbnail images, **when** uploaded and cropped, **then** each is stored with preview, reorder, delete, and set-primary actions working against real data — a real uploaded file, a real generated id, and real persisted `order`/`isPrimary`/`crop` fields, surviving a page reload. [Source: epics.md Story 2.4]
4. **Given** the new wizard is now persisting real Draft state, **when** this story ships, **then** the old 4-step Course Creation Wizard in `TutorEducatorHubView.tsx` (flat Module/Lesson model) is removed, not left running alongside the new wizard. [Source: epics.md Story 2.4]
5. **Given** `Course` now represents both the pre-existing public catalog AND in-progress tutor Drafts, **when** the public catalog is browsed (`GET /api/v1/courses`), **then** only `LifecycleState = Published` courses are returned — an in-progress Draft must never leak into the public catalog. This is not explicitly stated in epics.md's AC list, but is required for the existing catalog-browsing feature to keep working correctly once `Course` gains Draft rows (see Dev Notes — "the dev agent owns this" per this project's create-story convention for behavior the system needs even when not spelled out in the AC). [Source: Dev Notes design decision below]

## Dev Notes

- **Sizing risk, acknowledged up front (mirrors Story 1.5's own precedent):** this story spans a real Domain/entity redesign, a new file-storage abstraction, 6 new endpoints, and a frontend rewire touching 4 files plus a deletion in a 5th. Tasks are grouped into **Backend** (1-8) and **Frontend** (9-14) as the natural split point, exactly like Story 1.5. If a single `dev-story` pass cannot complete both groups, it is acceptable to complete Backend fully (tests green, story left with Frontend tasks unchecked) and resume Frontend in a follow-up pass of this same story file — do not fabricate a new story key.
- **The biggest design decision this story makes, made explicitly rather than silently:** epics.md's AD-20 only specifies the *content-tree* entities (Chapter/Topic/Subtopic/ContentBlock, Story 2.9's scope) supersede the old Module/Lesson model — it says nothing about the pre-existing flat `Course` catalog entity. Research for this story found `Course`/`ICourseService`/`CoursesController` already exist, but as a public-catalog-only shape (no `LifecycleState`, no owner, single `ThumbnailUrl` string, no live frontend caller of its `POST` endpoint). Two designs were possible: (a) extend the existing `Course` entity with `LifecycleState`/`TutorId`/a real thumbnail collection, or (b) introduce a wholly separate `Draft` entity that later gets "promoted" to a `Course` on first publish. **This story chooses (a).** Reasoning: the PRD's own Glossary (§4.11-ish, "Lifecycle State") already frames `Draft`/`In Review`/`Review Confirmed`/`Published` as *states of a Course*, not a separate table — "a Draft (Lifecycle State)" in FR-10's own wording is the strongest textual signal. Introducing a parallel `Draft` entity would also require a real, non-trivial "promote Draft → Course" migration step nowhere else in the plan, whereas (a) needs no such step — a Draft simply *is* a Course whose `LifecycleState` hasn't reached `Published` yet. This decision is foundational for every remaining live-wire Epic 2 story (2.5 through 2.9) — if a later story's own research surfaces a reason (a) doesn't hold up, that's a real finding worth raising, not something to silently work around.
- **Why `InstructorName`/`Subject`/`Level`/`TargetGradeTag` are left empty on a wizard-created Draft, not backfilled from somewhere:** `InstructorName`/`InstructorRole`/`InstructorAvatar` are today just denormalized display strings on `Course` (not a real FK to `TutorProfile`) — properly deriving them from the authenticated tutor's own profile is a reasonable future improvement, but doing it *in this story* would mean also reading/joining `TutorProfile`, which nothing in this story's AC asks for and which risks silently guessing at a shape Story 2.5+ hasn't defined yet. `Subject`/`Level` are explicitly Story 2.5's Taxonomy-wiring responsibility (the wizard's Step 3 stays mock in this story). Left blank is the honest, minimal-scope choice; a course only ever reaches `Published` after passing through the full content pipeline (Stories 2.5-2.9, then Epic 3's publish flow), by which point these fields will have been populated by their owning stories.
- **`GetByIdAsync` (the repository method) stays unfiltered by `LifecycleState` — but `CourseService.GetCourseByIdAsync` (the service method one layer up) is not, as of a code-review patch.** The original reasoning here (an id-guessing attacker has no way to obtain a Draft's GUIDv7 id) undersold a real risk: ids leak out-of-band all the time (URLs, logs, referrer headers, shared links) — "hard to guess" is not the same as "authorized." The fix, applied during this story's own code review rather than left as an acknowledged gap: `GetCourseByIdAsync` now throws `NotFoundException` for any non-`Published` course unless the caller is its owning tutor — same repository read, an added visibility check in the service. `NotFoundException` (not `UnauthorizedAppException`) so a non-owner can't distinguish "doesn't exist" from "exists but isn't yours," standard practice for hiding a private resource's existence.
- **Why title/description persist on every Next/Back/Finish click (`commitStep()`), not on a debounced per-keystroke timer:** AC #1 says "after every step," and a per-keystroke autosave would be far chattier than needed for a 2-field (title, description) form with no evidence any other story or UX-DR calls for it. `commitStep()` being idempotent (a harmless re-`PUT` of unchanged data on steps 2/3, which don't touch title/description) is a deliberate simplification over step-type-specific persistence logic.
- **Thumbnails persist immediately per-action (add/remove/reorder/set-primary), not via `commitStep()`** — these are already real, standalone mutations (a file upload, a delete) with no "unsaved draft" concept of their own in the mock version either; keeping that immediacy avoids inventing a new "pending thumbnail changes" state that didn't exist before.
- **`IFileStorageService`/`LocalFileStorageService` is explicitly interim and unscanned** — flagged in Task 3 and again here so it's unmissable: Story 2.6 owns adding ClamAV malware scanning to whatever the real upload path becomes. This story's minimal content-type/size validation (Task 3) is a sanity floor, not a security boundary.
- **Confirmed via repo-wide search during story research:** the existing `POST /api/v1/courses` (`CreateCourseAsync`/`CreateCourseRequest`, full-catalog fields) has no current frontend caller anywhere in this codebase — `FrontEnd/src/services/coursesService.ts` (the catalog's actual data source) is a fully separate in-memory mock. This story does not touch that existing endpoint/request type at all; the new `/drafts` endpoints are additive.
