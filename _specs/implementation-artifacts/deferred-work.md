## Deferred from: code review of 1-8-budget-threshold-enforcement (2026-08-11)

- A missing `AiTaskBudget` row (a seeding gap) makes `AiTaskGateway`'s pre-flight reserve fail identically to a genuinely exhausted budget (`AiTaskBudgetExceededException`, 429), while `AiConfigService`'s config-read path (`GetAllTaskConfigsAsync`/`GetTaskConfigAsync`) defaults the same missing row to `CurrentSpend: 0m` — an admin sees the task reading as healthy ("$0.00 / $80.00 spent") while every real call for it is instantly rejected. Deferred: this story's own Dev Notes already named and deliberately accepted this exact ambiguity ("a missing `AiTaskBudget` row blocks the call, indistinguishably from a genuinely exhausted budget") — adding a second, non-atomic existence check before the reserve to distinguish the two would reintroduce the concurrency race the atomic reserve exists to prevent. Both independent reviewers (Blind Hunter, Edge Case Hunter) re-surfaced this from different angles during this story's review, confirming it's worth tracking even though it isn't being fixed here.
- If `AiTaskConfig.PricePerMillionInputTokens`/`PricePerMillionOutputTokens` are both `0` for a task (the seeded default for every free-tier task today), `EstimateChatReservationCost`/`EstimateEmbeddingReservationCost` always compute a `$0` reservation regardless of `MaxTokens`/input size — the pre-flight gate trivially passes every time. Deferred: correct behavior for a genuinely free task (there is no real budget to protect), and becomes a live concern only once real, nonzero pricing is set for a task — at which point the already-fixed prompt+completion estimate formula (this story's own review patch) prices it properly; not a gap specific to this story's design.
- An admin lowering `AiTaskConfig.BudgetThreshold` below a task's current `AiTaskBudget.Spent` (via `UpdateTaskConfigAsync`) permanently blocks all future calls for that task — `TryReserveAsync`'s `spent + estimatedCost <= threshold` check fails even for a `$0` estimate once `spent` alone exceeds the new threshold, and nothing resets/reconciles `Spent` on a threshold change. Deferred: this is the correct, intended behavior of a live-threshold enforcement system (AD-18 explicitly reads the threshold live, not a snapshot) — an admin who lowers a threshold below current spend is knowingly locking out further spend until the threshold is raised again or spend naturally has room; no AC asks for automatic reconciliation, and building one (a rollover, a spend-reset job) is a real, separate feature decision.
- `AiTaskBudgetRepository`'s two raw-SQL methods (`TryReserveAsync`, `AdjustSpentAsync`) have no `AND is_deleted = false` clause, so they would still find and mutate a soft-deleted `AiTaskBudget` row, while the LINQ-based reads (`GetByTaskIdAsync`/`GetAllAsync`, and `AiTaskBudgetConfiguration`'s `HasQueryFilter`) treat that same row as absent. Deferred: no delete path exists anywhere for `AiTaskBudget` in this diff (matches the identical, already-deferred "unique indexes not filtered by `IsDeleted`" gap tracked from Story 1.5's review for `AiTaskConfig`/`AiPromptVersion`) — currently unreachable, not a live bug.
