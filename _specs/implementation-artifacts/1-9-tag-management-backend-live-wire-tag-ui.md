# Story 1.9: Tag Management Backend & Live-Wire Tag UI

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an admin,
I want Story 1.3's UI to read and write real Tag data,
So that tag governance is enforced server-side, not just in the mock UI.

## Acceptance Criteria

1. `Domain/Tags/`, `Application/Tags/`, and `Api/Controllers/TagsController.cs` exist; Story 1.3's `TagManagement.tsx` UI (add, rename, deactivate, search) persists to and reads from this real backend, replacing `INITIAL_TAGS`/`tagsRef`'s mock data entirely. [Source: epics.md Story 1.9]
2. A duplicate tag name — matching an existing tag case-insensitively, whether that existing tag is active OR deactivated — is rejected server-side on both create and rename. [Source: epics.md Story 1.9; PRD FR-26: "Attempting to create a tag with a name matching an existing (active or deactivated) tag, case-insensitively, is rejected."]
3. Deactivating a tag already attached to a course leaves it attached (nothing in this story touches `Course.tags`), but the tag can no longer be newly selected going forward — the same "inactive tags don't disappear, they stop being offered" semantics Country/State/etc. already establish for master data, applied here too. [Source: epics.md Story 1.9; PRD FR-26: "deactivating a tag hides it from new selection (FR-7) but does not remove it from courses it's already attached to"]

## Dev Notes

- **Tag is deliberately NOT part of the Master Data scaffold — this affects both backend AND frontend file placement.** `Domain/Tags/` (not `Domain/MasterData/`), `Application/Tags/` (not `Application/MasterData/`), `TagsController` at `api/v1/tags` (not `api/v1/master-data/tags`), `tagsService.ts` as its own file (not added to `masterDataService.ts`). This is explicit in both `ARCHITECTURE-SPINE.md`'s Structural Seed and PRD FR-26's own text, quoted in Task 1 — don't reuse `IMasterDataEntity`/`MasterDataRepository<TEntity>` just because Tag's shape (`Id`/`Name`/`IsActive`) looks identical to Country's; the architectural intent is a standalone slice, confirmed by two independent planning documents, not an oversight to "fix" by unifying them.
- **Duplicate prevention is application-level, not a DB constraint.** No existing Master Data entity in this codebase has a case-insensitive unique constraint on `Name` (`Country` only uniquely indexes `IsoCode` — confirmed by reading `CountryConfiguration.cs`), and Postgres's default collation is case-sensitive, so a true DB-level case-insensitive unique index would require a `citext` column or a functional index on `lower(name)` — real added complexity with no precedent anywhere in this codebase. This story's `TagService.CreateAsync`/`UpdateAsync` enforce it entirely at the application layer via `ITagRepository.GetByNameAsync`'s `EF.Functions.ILike` check before insert/update. **Known, accepted tradeoff:** two concurrent create requests for the same name could theoretically both pass the check before either commits, landing two duplicate tags. This is the same category of scale tradeoff already accepted elsewhere in this codebase (AD-18's own "single container, moderate volume" framing) — an admin-only, low-frequency-write screen doesn't need protection against a race that requires two admins creating the identically-named tag in the same instant. If this ever becomes a real problem, the fix is a Postgres functional unique index, not a rework of this story's logic.
- **`EF.Functions.ILike` is Npgsql-specific and untestable against `InMemory`** — this is not a new gap this story introduces; `BackEnd/CLAUDE.md`'s own Testing section already documents it as a known, accepted limitation ("It can't translate Npgsql-specific LINQ (`EF.Functions.ILike`, etc.)... those code paths are exercised against real Postgres, not covered by these unit tests"), and `CourseRepository`'s own `search` parameter (Epic 2 territory, but already in the codebase) is the existing precedent — read it before writing `TagRepository.GetByNameAsync` to match its exact usage, don't re-derive the API shape from scratch.
- **No `includeInactive` parameter, no server-side search, no delete action — three deliberate scope-narrowing decisions, not omissions.** Every one of them exists on Country's backend but isn't needed here: `includeInactive` because Tag has exactly one consumer (the always-shows-everything admin table) unlike Country (which also has a presumed future active-only consumer); server-side search because `MasterDataTable`'s `fetchAll` prop is a zero-arg function with no search parameter to plumb one through, and `TagManagement.tsx`'s own header comment already states "`MasterDataTable` has no built-in search"; delete because neither the epics AC nor `TagManagement.tsx`'s existing mock ever exercises `MasterDataTable`'s optional `deleteFn` prop. Building any of these three would be scope creep beyond what this story's own AC and existing frontend contract actually require.
- **Removing `tagsRef`/`nextIdRef` is itself the fix for two items `deferred-work.md` already named as "Story 1.9's job"** from Story 1.3's review: client-side ID generation colliding with server-assigned IDs, and duplicate-checking existing only in mock closures with nothing guaranteeing the real backend replicates the same rule. Both are resolved by this story's design, not by extra defensive code — a server-assigned ID has no client-generated counterpart to collide with once `nextIdRef` is gone, and `TagService.CreateAsync`'s `ConflictException` check is the "nothing guaranteed" gap being filled.
- **`Course.tags` is untouched by this story.** AC #3's "stays attached but cannot be newly selected" is a property of `Tag.IsActive` existing and being real (an inactive tag simply won't appear in whatever future Epic 2 tag-picker UI queries `GET /api/v1/tags` and filters `isActive`) — this story does not modify `Course` or build that picker; `Course.tags` today is still "a plain string array with no master-data backing" per FR-26's own text, and stays that way until an Epic 2 story wires it to real `Tag` ids. Don't build a `CourseTag` join table or migrate `Course.tags` here — nothing in this story's AC asks for it.
