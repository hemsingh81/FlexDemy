# Story 2.7: Document Parsing/OCR Pipeline

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As the system,
I want each accepted file run through a dedicated parsing pass (with OCR for scans) before structure extraction,
so that `extractStructure()` receives clean text, not raw/degraded input.

## Acceptance Criteria

1. **Given** a scanned or text-based file, **when** the parsing pass runs (Docling), **then** it produces clean structured text. [Source: epics.md Story 2.7]
2. **Given** low-confidence parse output, **when** detected, **then** the file routes to failed/retry, not silent pass-through. [Source: epics.md Story 2.7; PRD FR-12 — "non-empty alone does not satisfy this FR"]
3. **Given** Story 2.2's status badges, **when** parsing completes or fails, **then** they reflect real parsing state instead of mock simulation. [Source: epics.md Story 2.7]

## Dev Notes

- **This story is backend-only** — the first Epic 2 story in this batch with no frontend task at all, because Story 2.6 already built the generic polling/badge-rendering infrastructure this story's status transitions ride on for free. Verify this claim rather than assuming it (see Task's own note above).
- **This story adds the second and third genuinely new piece of infrastructure this Epic** (Docling, following Story 2.6's ClamAV+Hangfire) — `Infrastructure/Parsing/` and `Infrastructure/Jobs/ParseFileJob.cs` are both already reserved by ARCHITECTURE-SPINE.md's Structural Seed (`Infrastructure/Parsing/` is explicitly listed: "HTTP client calling the self-hosted Docling service (AD-21)").
- **Hangfire itself is not stood up by this story** — Story 2.6 already added `Hangfire.Core`/`Hangfire.PostgreSql`, DI registration, and `app.UseHangfireServer()`. This story is purely a new job class (`ParseFileJob`) registered the same way `ScanFileJob` was. If Story 2.6 has not actually landed/been implemented yet when this story is picked up for dev, its Hangfire scaffolding is a hard prerequisite — check `Infrastructure/DependencyInjection.cs` for existing `AddHangfire(...)` before assuming it's missing.
- **Why Docling's own async job API (`/v1/convert/file/async` + polling/WebSocket) is deliberately NOT used, even though it exists:** this client is only ever called from inside `ParseFileJob`, which is itself already a Hangfire background job with its own retry semantics. Using Docling's sync `/v1/convert/file` endpoint and letting the *outer* Hangfire job be the thing that's "async" from the rest of the system's perspective is simpler and avoids a confusing nested-polling-inside-a-background-job shape. If a single parse genuinely needs longer than Task 3's HTTP timeout allows, that's a timeout-tuning problem (`Docling:TimeoutSeconds`) or a case for Hangfire's own retry, not a reason to add a second async mechanism on top.
- **The confidence signal design changed mid-authoring of this story — read Task 2's inline note in full, don't rely on a stale summary of it.** An earlier research pass concluded Docling's HTTP API had no confidence field at all and designed around a derived heuristic; a second, independent verification pass during this same story's authoring found that conclusion was already out of date (docling-serve v1.25.0 added it). This is left in the story deliberately, not scrubbed out, as a concrete reminder that even "verified via web research" claims should be re-checked if the story sits unbuilt for a while — Docling/docling-serve is an actively developed project and this story's own web research is a snapshot from 2026-08-12, not a permanent fact. The two remaining open questions for a human to confirm before/during build are both flagged `[ASSUMPTION]` in Task 2: the exact JSON field path for the confidence object in docling-serve's response, and whether `POOR` alone (vs. `POOR`+`FAIR`) should fail the confidence check.
- **Retry semantics stay identical to Story 2.6's `ScanFileJob`, deliberately** — same `[AutomaticRetry(Attempts = 5)]` count, same "final-attempt catch sets a terminal Failed status" mechanism. Two independently-invented retry mechanisms for two structurally identical jobs in the same epic would be a real consistency gap; if Story 2.6's dev agent picked a different final-attempt mechanism than described in that story's Dev Notes (e.g. `IElectStateFilter` vs. a manual retry-count check), this story reuses whatever was actually built, not what was originally proposed.
- **No new backend retry/delete endpoint** — same reasoning as Story 2.6: retry is "re-upload the same file through the existing upload endpoint," which re-runs the whole scan→parse pipeline from scratch. This story doesn't change that.
