# Story 6.5: Combined Typography presets with a Custom fallback

Status: done

## Story

As a Master or Support admin,
I want to pick a ready-made Typography preset (font pairing + size together) or fall back to choosing each independently,
so that the common case is one click instead of two separate decisions, without losing the ability to mix and match when a preset doesn't fit.

**Context (why this story exists, not from a PRD FR):** direct user request after Epic 6's first four stories shipped Font Pairing and Font Size as two fully independent Settings. The user asked to (1) combine them into one experience, (2) seed at least 5 predefined combinations, (3) keep a custom option to pick each independently, and explicitly delegated UX/UI detail. This story was scoped and designed directly (no PRD amendment ceremony — the user's own three requirements plus this Dev Notes section constitute the spec), but still follows this session's established engineering discipline (independent quality-validator pass, full test coverage, code review) given it introduces a new atomic-transaction design — exactly the category of change that has twice caught real bugs earlier in this epic.

## Acceptance Criteria

1. The Settings screen offers a curated list of at least 5 named Typography presets, each specifying a font pairing and a font size together, for one-click selection.
2. Selecting a preset shows a live combined preview (font family and size together) before being applied, and applying it updates both the Font and Font Size Settings atomically — both succeed or neither does; there is no partial-preset state.
3. A "Custom" option remains available, letting an admin choose a Font Pairing and a Font Size independently, reusing the exact Preview/Apply/History mechanisms already built for each (Stories 6.2/6.4) — no parallel/duplicate implementation of that machinery.
4. Applying a preset is rejected server-side if the preset itself, or either definition it references, is not currently curated — the same enforcement discipline already applied to direct Font/FontSize writes (Stories 6.2/6.4).
5. The existing per-Setting Apply path (direct `PUT /{id}/apply` on a single Font or FontSize Setting) is completely unchanged and still independently reachable — this story adds a new composed operation, it does not replace or modify the existing one.

Two separate `SettingChangeHistory` entries are correct and intentional — Font and FontSize remain independently-tracked Settings (AC #5/FR-20's independence guarantee is unaffected by this story), the atomicity is about the *write* succeeding or failing together, not about merging their history into one entry.

Build and return a `TypographyApplyResultDto` from the two updated `Setting` rows (same construction pattern `ApplyAsync` already uses for its single-row `SettingDto`) — do **not** re-query the database; use the pre-transaction `fontSetting`/`sizeSetting` entities' unchanged fields (`Key`/`KeyType`/`CreatedAt`/`CreatedBy`) plus the atomic call's fresh `Value`/`UpdatedAt`, exactly like `ApplyAsync` already does (see its own comment on why re-querying a tracked-but-now-stale entity is wrong).

## Dev Notes

- **Atomicity is the point of this story, not an incidental detail.** `ApplyTypographyCombinationAsync` exists specifically so a preset can never leave the two Settings in a mismatched state (Font updated, FontSize not, or vice versa) the way two independent frontend API calls could under a mid-sequence network failure. Task 5's atomicity test (force the second write to fail, assert nothing committed) is the one that actually proves this — don't skip it or treat it as redundant with the happy-path test.
- **`ApplyAsync` (Stories 6.2/6.3's existing single-Setting path) is untouched by this story.** `ApplyTypographyCombinationAsync` is additive — a new operation built from the same lower-level pieces (`repository.ApplyValueAsync`, `historyRepository.Add`, one transaction), not a refactor. AC #5 exists to keep this boundary explicit for whoever reviews this story next.
