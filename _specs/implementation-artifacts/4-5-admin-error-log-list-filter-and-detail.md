# Story 4.5: Admin Error Log — List, Filter, and Detail

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

*(Release-checkpoint note, per epics-ErrorObservability.md's own "Implementation notes": this story is the first point in Epic 4 where an admin can see anything. It should ship immediately adjacent to Story 4.4 — no released increment where Story 4.4's anonymous endpoint is live and writing `ErrorRecord`s nobody can yet view.)*

## Story

As a Master admin,
I want to see every captured error in one server-side-paginated, filterable list with a detail view,
so that I can find and investigate real problems without reading container logs by hand.

## Acceptance Criteria

1. **Given** a new `FeatureKeys.ErrorsManage` policy seeded Master-only, **when** a non-Master user calls the admin API directly, **then** they receive 403, not just a hidden menu item; **given** a Master admin, **when** they open the Admin panel, **then** a new "Error Log" sub-tab is visible (wired through `useAdminPanel.ts`/`ADMIN_SUBTAB_META`), absent for every other role. [Source: epics-ErrorObservability.md Story 4.5; PRD FR-19]
2. **Given** `ErrorsController`'s list endpoint, **when** called with no filters, **then** it returns a server-side-paginated page of `ErrorRecord`s newest-`LastOccurredAt`-first, each row showing Category, Priority (color-coded badge), Status, truncated Message, Source, OccurrenceCount, and LastOccurredAt, **and** `Archived` records are excluded by default. [Source: PRD FR-11]
3. **Given** Category, Priority, Status, Source, date-range, and free-text filters, **when** combined (e.g. Category = External Integration Error AND Priority = P0/P1), **then** results match all active filters simultaneously; **given** the "include Archived" toggle, default off, **when** turned on, **then** `Archived` records appear in the results too. [Source: PRD FR-12]
4. **Given** a single `ErrorRecord`'s detail view, **when** opened, **then** it shows the full untruncated `StackTrace`, `RequestPath`/`Route`, `OriginContext`, and the occurrence timeline (`FirstOccurredAt`/`LastOccurredAt`/`OccurrenceCount`), **and** when `RelatedEntityType`/`RelatedEntityId` is set, a link back to the originating record is shown. [Source: PRD FR-13]
5. **Given** Story 4.4's reporting endpoint has already been live, **when** this story ships, **then** any `ErrorRecord`s it already produced — including frontend crashes — are immediately visible in this list, closing the visibility gap flagged in the epics document's own "Implementation notes." [Source: epics-ErrorObservability.md Story 4.5]

### Review Findings

- [x] [Review][Patch] `ErrorRecordRepository.QueryAsync` self-contradicting filter: `if (!query.IncludeArchived) filtered = filtered.Where(r => r.Status != ErrorStatus.Archived);` runs unconditionally alongside the explicit `Status` filter — an admin selecting Status = Archived without also flipping the separate "include Archived" toggle (the two controls are independent in the UI, and `Archived` is a selectable Status option) gets `Status != Archived AND Status == Archived`, always zero rows, no error or explanation shown. Fix: skip the default exclude-Archived clause when `query.Status == ErrorStatus.Archived` [BackEnd/src/FlexDemy.Infrastructure/ErrorObservability/ErrorRecordRepository.cs:26-30] — confirmed independently by Blind Hunter, Edge Case Hunter, and the Acceptance Auditor
- [x] [Review][Patch] `ErrorLogFilters.tsx`'s "To" date filter uses start-of-day (`new Date(dateString).toISOString()` = that day's `00:00:00.000Z`) compared via `LastOccurredAt <= ToDate`, excluding nearly the entire selected day — only records at exactly midnight UTC survive. Fix: construct end-of-day (`23:59:59.999`) for `ToDate` specifically (`FromDate`'s start-of-day + `>=` comparison is already correct) [FrontEnd/src/features/Admin/ErrorLog/ErrorLogFilters.tsx] — confirmed independently by Blind Hunter and Edge Case Hunter; the Acceptance Auditor raised the same underlying bug but attributed it to local-timezone date parsing, which is incorrect (`new Date('yyyy-mm-dd')` parses as UTC per the ISO 8601 date-only spec, verified directly) — the start-of-day-vs-end-of-day framing is the real, confirmed root cause
- [x] [Review][Patch] `ErrorListQuery.Page`/`PageSize` are bound straight from the query string with no bounds — `Page <= 0` produces a negative `Skip()` argument (undefined/provider-dependent behavior, likely a 500 on a real relational provider), and an unbounded `PageSize` lets any Master-authenticated caller force a full-table scan in one request. Fix: clamp `Page` to a minimum of 1 and `PageSize` to a sane range (e.g. 1-100) in the repository before `Skip`/`Take` [BackEnd/src/FlexDemy.Infrastructure/ErrorObservability/ErrorRecordRepository.cs:57-59]
- [x] [Review][Patch] `QueryAsync`'s `OrderByDescending(r => r.LastOccurredAt)` has no tie-breaker — multiple rows sharing the exact same `LastOccurredAt` (plausible: `DateTimeOffset.UtcNow` at insert time, or a burst of related failures) straddling a page boundary can be duplicated across two pages or dropped entirely between two paginated requests, since `Skip`/`Take` pagination is only stable with a fully deterministic sort. Fix: add `.ThenByDescending(r => r.Id)` as a tie-breaker [BackEnd/src/FlexDemy.Infrastructure/ErrorObservability/ErrorRecordRepository.cs:57]
- [x] [Review][Patch] `ErrorLogFilters.tsx`'s debounced-search `useEffect` depends only on `[searchInput]` and closes over `filters` from whenever it last ran — if another filter (Category/Priority/etc.) changes while the 250ms search debounce timer is still pending, the timer fires with the *stale* closed-over `filters` object, silently reverting the other filter change just made. Fix: read the latest filters via a ref at the moment the timer fires, not the closed-over value [FrontEnd/src/features/Admin/ErrorLog/ErrorLogFilters.tsx:16-23]

### Completion Notes List

- **`ErrorRecordDetailDto.Message` is the full untruncated value, not re-truncated to Summary's 200-char cap.** Task 4's text says Detail is "everything in Summary plus [more fields]" without addressing Message specifically, but AC #4 frames the whole detail view around showing "full untruncated" data — applying Summary's list-row truncation to the one field a detail view exists to let an admin actually read in full would contradict that intent. Verified via `ErrorRecordMapperTests.ToDetailDto_maps_every_AC4_field_including_the_full_untruncated_Message`.
- **`ErrorsControllerTests`' RBAC coverage exercises `FeaturePolicyProvider`/`FeatureAuthorizationHandler` directly (mirroring `AdminUsersControllerTests`' own `BuildRealAuthorizationService` helper), not the controller's action bodies.** A class-level `[Authorize(Policy = FeatureKeys.ErrorsManage)]` is enforced by ASP.NET Core's own filter pipeline *before* the action executes — directly constructing and calling `ErrorsController.GetList(...)` (as the other 4 tests in that file do, for mapping/pass-through behavior) bypasses that pipeline entirely and would prove nothing about AC #1's actual 403-vs-200 behavior. This repo has no `WebApplicationFactory` infra to drive the real HTTP pipeline through instead (confirmed, matching every prior story's identical finding) — the `AuthorizeAsync` call the attribute delegates to is exactly what determines 403 vs. 200 in the real pipeline, so testing it directly is equivalent in effect, not a lesser substitute.
- **Category renders as plain text in `ErrorLogTable.tsx`, not a color-coded badge, unlike Priority and Status.** The Dev Notes explicitly left this "reasonable either way, not specified." 9 category values have no natural severity/lifecycle ordering the way 4 Priorities or 3 Statuses do — a 9-color badge palette would be arbitrary, not meaningful signal, so plain text (still humanized via a generic PascalCase-to-spaced-words helper, not a hardcoded label table) reads better.

- Fixed a confirmed-real bug all three review layers independently caught: `ErrorRecordRepository.QueryAsync` unconditionally applied the default "exclude Archived" clause even when the caller explicitly filtered `Status = Archived`, producing a self-contradicting `Status != Archived AND Status == Archived` query that always returned zero rows with no error shown. - Fixed `ErrorLogFilters.tsx`'s debounced-search effect closing over a stale `filters` object — a filter change made while the 250ms search debounce was still pending could be silently reverted when the timer fired.
