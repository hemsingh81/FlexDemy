# Story 1.4: AI Service Layer Interface & Gateway Client

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a backend developer,
I want a single internal `IAiGateway` interface and an HTTP-calling implementation that targets the self-hosted Portkey OSS gateway,
so that all AI-driven features call one abstraction instead of a vendor SDK.

## Acceptance Criteria

1. `IAiGateway` (`FlexDemy.Application/AiGateway/`) is a single interface with one method per AI Task — `ExtractStructureAsync`, `ExplainTopicAsync`, `RewriteExplanationAsync`, `GenerateExerciseAsync`, `DefineKeywordAsync`, `DescribeNotationAsync`, plus `GenerateEmbeddingAsync` — not per-task interfaces. Any future feature module that needs an AI capability calls `IAiGateway`, never a vendor SDK directly. [Source: epics.md Story 1.4; ARCHITECTURE-SPINE.md AD-14: "one fat `IAiGateway` interface — not per-task interfaces... one method per AI Task"; PRD FR-1]
2. `IAiGateway`'s HTTP implementation (`FlexDemy.Infrastructure/AiGateway/`) sends every request to the configured self-hosted Portkey OSS gateway endpoint, using an OpenAI-compatible request/response shape: `POST {BaseUrl}/v1/chat/completions` for the six chat-style methods, `POST {BaseUrl}/v1/embeddings` for `GenerateEmbeddingAsync`, JSON body `{ model, messages, temperature, max_tokens }` (chat) / `{ model, input }` (embeddings). [Source: epics.md Story 1.4; AD-14: "targeting a self-hosted Portkey OSS gateway... at `http://ai-gateway:8787`... using an OpenAI-compatible request/response shape"]
3. The provider actually used for a call is caller-specified per request (via `AiGatewayRequest.Provider`/`Model`, not resolved internally from a config store) — `IAiGateway` is a pure transport abstraction; per-task provider/model *resolution* is Story 1.5's job (`AiTaskConfig`) and per-task fallback-on-failure is Story 1.6's job (Polly), both layered **above** `IAiGateway`, not inside it. The HTTP implementation sets the Portkey provider-routing header (`x-portkey-provider: {Provider}`) and an `Authorization: Bearer {provider's API key}` header, resolving the API key for `Provider` from configuration (`AiGatewayOptions.ProviderApiKeys`), never from the caller. [Source: epics.md Story 1.4 Dev Notes — design decision, see below; web-verified Portkey self-hosted header convention, Aug 2026: `x-portkey-provider` + `Authorization: Bearer <token>`, no `x-portkey-api-key` (Portkey Cloud-only)]
4. The gateway client is registered via DI in `AddInfrastructure()` (`FlexDemy.Infrastructure/DependencyInjection.cs`) using the typed-client pattern (`AddHttpClient<IAiGateway, PortkeyAiGateway>()`), with `AiGatewayOptions` bound from configuration (`appsettings.json`'s `"AiGateway"` section) — never `new`'d up directly by a feature service (AD-2). [Source: epics.md Story 1.4; AD-14: "DI registration follows AD-2 (wired in Program.cs/AddInfrastructure())"]
5. A non-success HTTP response from the gateway (or a network/timeout failure) surfaces to the caller as a new `AiGatewayException` (`FlexDemy.Application/Common/AppException.cs`), which `ExceptionHandlingMiddleware` maps to HTTP 502 — not an unhandled exception or a generic 500. [Source: AD-5: "Application-layer failures reach this boundary as exceptions... caught by one global exception-handling middleware"; existing `AppException.cs`'s own doc comment: "add a new subtype here... when a use-case needs a new failure kind"]

## Dev Notes

- **This story is transport only — no business logic, no config store, no fallback.** `IAiGateway` does not know about AI Tasks' *configured* provider/model (that's `AiTaskConfig`, Story 1.5) and does not retry on failure (that's Polly, Story 1.6). Every method here just: takes a `Provider`/`Model`/`Messages` the caller already decided on, calls Portkey, and returns the result or throws. Resist the temptation to add task-name-to-config resolution logic in this story — there is no config store yet for it to read from, and building one prematurely here would duplicate Story 1.5's actual scope.
- **Why `Provider`/`Model` are caller-supplied, not looked up by task name inside `PortkeyAiGateway`:** re-reading AD-14 closely — "Per-task fallback... is implemented with Polly 8.7.0... as a fallback policy **wrapping each `IAiGateway` method's primary-provider call**, falling back to that task's configured secondary provider/model on failure" — this only makes sense if whatever wraps `IAiGateway` (Story 1.6) is the thing deciding which provider/model to call it with (primary first, secondary on retry), not `IAiGateway` deciding internally. Story 1.5's `IAiConfigService` will be the thing Story 1.6's wrapper reads `AiTaskConfig` from to build each `AiGatewayRequest`.
- **Portkey self-hosted header convention (web-verified Aug 2026, not in the architecture spine — confirm still current at implementation time):** self-hosted/OSS Portkey gateway deployments (as opposed to Portkey Cloud) route to a provider via the `x-portkey-provider` header and authenticate to that provider via a plain `Authorization: Bearer <provider-api-key>` header — Portkey converts this into whatever auth shape the underlying provider actually expects (e.g. `x-api-key` for some providers). The Portkey-Cloud-only `x-portkey-api-key` header does **not** apply here and should not be sent. [Source: Portkey docs, `portkey.ai/docs/api-reference/inference-api/headers`, fetched 2026-08-11]
- **`/v1/chat/completions` and `/v1/embeddings` are the two OpenAI-compatible endpoints in play** — every one of the 6 chat-style AI Tasks (including `describeNotation`, which produces alt-text) is a chat completion; only `GenerateEmbeddingAsync` uses the embeddings endpoint.
- **Do not add per-AI-Task business parameters** (e.g. `explainTopic`'s drill-down `level`, `rewriteExplanation`'s `way`) to any DTO in this story. Those are feature-story concerns (Epic 3): the caller constructs whatever `Messages` (prompt) content encodes that business parameter and passes it in as plain chat messages — `IAiGateway` has no opinion on prompt content.
- **`ProviderApiKeys` values must never be committed** — `appsettings.json`'s default is an empty dictionary; real keys arrive via environment-variable overrides (`AiGateway__ProviderApiKeys__{provider}`, ASP.NET's standard double-underscore nested-config convention, same pattern as `ConnectionStrings__Default`) or `dotnet user-secrets` locally.
