# Story 6.3: Change history and one-click restore

Status: done

## Story

As a Master or Support admin,
I want to see what changed on a setting and restore a prior value,
so that a bad or unexplained change can be traced and undone without guessing.

## Acceptance Criteria

1. When an admin applies a change to a Setting (Story 6.2's Apply), exactly one change-history entry is recorded with the Key, the freshly-read prior Value (read at the moment of the write, not a stale page-load snapshot), the new Value, the admin who applied it, and a timestamp. [Source: epics-AdminSettings.md#Story 6.3; prd.md#FR-15]
2. The Settings screen provides a way to view a given Setting's history as a reverse-chronological list. [Source: epics-AdminSettings.md#Story 6.3; prd.md#FR-16]
3. Selecting a prior history entry to restore populates it as the preview candidate, going through the same Preview and Apply steps as any other change — restoring is not a separate, unvalidated code path. [Source: epics-AdminSettings.md#Story 6.3; prd.md#FR-17, FR-10]
4. Restoring a historical Value that is no longer a currently curated pairing is rejected the same way an uncurated direct write would be, and the admin is prompted to choose a currently-curated pairing instead. [Source: epics-AdminSettings.md#Story 6.3; prd.md#FR-17]
5. If the settings store is unreachable, returns malformed data, or times out at page load, the app falls back to hardcoded defaults rather than failing to load. [Source: epics-AdminSettings.md#Story 6.3; prd.md#NFR-4 — already satisfied by `SiteSettingsContext`'s existing fail-safe design from Story 6.2; this story's job is to not weaken that guarantee, not to rebuild it.]

**FR numbering note:** `prd.md` numbers these FR-15 (record), FR-16 (view), FR-17 (restore); `epics-AdminSettings.md` renumbers the same requirements as FR14/FR15/FR16 in its own local sequence. Both refer to the identical requirements — cited here by each document's own numbering to avoid ambiguity when cross-referencing either source.

- [x] Task 3: Backend — atomic `ApplyValueAsync` on `ISettingRepository` (AC: #1)
  - [x] Add `Task<(string OldValue, DateTimeOffset UpdatedAt)> ApplyValueAsync(string id, string newValue, string? updatedBy, CancellationToken cancellationToken = default)` to `ISettingRepository`/`SettingRepository`. This is the **only** place in the codebase that mutates a Setting's `Value` — it replaces the plain EF-tracked `setting.Value = value` assignment `SettingsService.ApplyAsync` currently does (Story 6.2). Purpose: capture the Value that was live *immediately before this write*, atomically, so no concurrent Apply to the same row can slip a write in between a read and a later `SaveChangesAsync` the way a separate earlier `GetByIdAsync` call could. `NewValue` isn't part of the return — the caller already has it (it's the `newValue` parameter it just passed in), so there's no need to round-trip it back out.
  - [x] **Implement this as two statements, both run inside the transaction Task 4's `ExecuteInTransactionAsync` opens** (do NOT attempt a single combined CTE+`UPDATE`+`RETURNING` statement — verified this is unsafe/unsupported, see rationale below):
    ```csharp
    var oldValue = await db.Database
        .SqlQuery<string>($"SELECT value FROM settings WHERE id = {id} FOR UPDATE")
        .SingleAsync(cancellationToken);

    var now = DateTimeOffset.UtcNow;
    await db.Database.ExecuteSqlInterpolatedAsync(
        $"UPDATE settings SET value = {newValue}, is_active = TRUE, updated_at = {now}, updated_by = {updatedBy} WHERE id = {id}",
        cancellationToken);

    return (oldValue, now);
    ```
    The first statement is a plain `SELECT ... FOR UPDATE` — this is squarely within `Database.SqlQuery<T>`'s documented, `SELECT`-shaped contract (unlike a `RETURNING`-bearing `UPDATE`, which is not), and the `FOR UPDATE` row lock is what provides the atomicity/race-safety guarantee: it's held until the transaction Task 4 opened commits, so no concurrent Apply to the same Setting can write in between this read and the `UPDATE` below. The second statement mirrors `AiTaskBudgetRepository.cs`'s actual existing pattern exactly (`Database.ExecuteSqlInterpolatedAsync`, not `SqlQuery<T>` — that file uses `ExecuteSqlInterpolatedAsync` for its own conditional `UPDATE`, and this method reuses that exact call for the same reason: it's the correct API for a DML statement with no result set to read back). Both calls share `SettingRepository`'s injected `FlexDemyDbContext`/`Database` — the same connection `ExecuteInTransactionAsync`'s `BeginTransactionAsync()` opened — so they genuinely execute inside one transaction, not two independent auto-committed statements.
  - [x] **Why not a single-round-trip `WITH ... UPDATE ... RETURNING` CTE, even though it looks more elegant:** `Database.SqlQuery<T>`'s `FormattableString` overload is designed and documented for `SELECT`-shaped raw SQL that projects into `IQueryable<T>`; composing further LINQ operators onto it (this method needs `.SingleAsync()`) risks EF Core wrapping the raw SQL in a row-limiting subquery (`SELECT ... FROM (<raw sql>) AS t LIMIT 2`-style), and PostgreSQL does not allow a bare `UPDATE` (even CTE-prefixed) to serve as a subquery/derived-table source — only `SELECT`/`VALUES`/a `SELECT`-shaped CTE qualify. This either fails at EF's translation step or produces SQL Postgres rejects. `Database.SqlQueryRaw<T>` shares the same underlying `IQueryable<T>`-composition machinery as `SqlQuery<T>`, so it is **not** a working fallback for this specific problem — swapping interpolation for manual parameters doesn't change what `.SingleAsync()` composes on top of. The two-statement approach above sidesteps this entirely: the `SqlQuery<T>` call is a genuine, uncomposed `SELECT`, and the `UPDATE` never goes through `SqlQuery<T>` at all.
  - [x] This is genuinely new usage in this codebase — no prior `SqlQuery<T>` call of any kind exists anywhere in `BackEnd/` yet (confirmed by repo-wide search: zero matches for `SqlQuery<`, `SqlQueryRaw`, `FromSqlInterpolated`, `FOR UPDATE`, or `RETURNING`). Only `ExecuteSqlInterpolatedAsync` (the `UPDATE` half) has a direct precedent, in `AiTaskBudgetRepository.cs`.

## Dev Notes

- **This story's central design decision:** `SettingsService.ApplyAsync`'s persistence step changes from Story 6.2's plain `setting.Value = value; unitOfWork.SaveChangesAsync()` to a transaction wrapping (a) a new atomic repository method (`SELECT ... FOR UPDATE` then `ExecuteSqlInterpolatedAsync UPDATE`, two statements, one transaction — not a single combined `RETURNING` statement, which turned out to be unsafe with `SqlQuery<T>`'s composition model, see Task 3) that updates `settings.value` and captures the true pre-write value, and (b) a normal EF-tracked insert of a `SettingChangeHistory` row (picked up by `AuditSaveChangesInterceptor` like any other new entity — this row is not special-cased). Story 6.2's own Dev Notes flagged this exact rewrite as coming — this is that rewrite, and it's additive to the transaction/history layer, not a change to the curation-check logic Story 6.2 already built (that stays untouched).
- **Timestamp note:** `SettingChangeHistory.CreatedAt` (stamped by the interceptor at `SaveChangesAsync` time) and `Setting.UpdatedAt` (set explicitly inside `ApplyValueAsync`'s `UPDATE` from a separately-captured `DateTimeOffset.UtcNow`) will differ by a few milliseconds, since they're two different `UtcNow` calls for the same logical event. Harmless given AC #1 only requires "a timestamp," not perfect equality between the two — no fix needed, just don't be surprised by it in a test assertion.
- **`IUnitOfWork.ExecuteInTransactionAsync` already exists** (`Application/Common/IUnitOfWork.cs`) — built for exactly this "genuine multi-commit use-case," with `PublishService.PublishAsync`'s zero-node finalize path as its own cited precedent. Use it; do not hand-roll transaction management elsewhere (e.g. inside the repository) — that would duplicate an abstraction this codebase already has.
- **The stale-tracked-entity gotcha (Task 4) is the single easiest mistake to make here:** once `ApplyValueAsync`'s raw SQL commits, the `Setting` entity `ApplyAsync` fetched earlier via `GetByIdAsync` no longer reflects the database — EF's `ChangeTracker`/identity map has no way to know a raw SQL statement changed anything. Returning `setting.ToDto()` after the atomic call would silently return the *old* Value in the response (and, if that same tracked instance were ever queried again within the same request's `DbContext`, still-stale data). Build the response DTO from the atomic call's returned tuple, not from the pre-write tracked entity's mutable fields.
- **No repository-level automated test can verify `ApplyValueAsync`'s SQL is actually correct** — the `InMemory` provider (all `Infrastructure.Tests` repository tests use it) cannot execute Postgres-specific raw SQL (`FOR UPDATE` row locking) at all. This is a sharper version of the same `AD-7` limitation Story 6.1 discovered for unique-index enforcement. Cover the *orchestration* (does `ApplyAsync` call the right things in the right order) via mocked-repository service tests; be explicit in the story's Debug Log that the SQL's real correctness needs a live Postgres verification this test suite structurally cannot provide, exactly as Story 6.1 was honest about its own InMemory gap.
- **Restore is not a new backend capability** — it reuses `ApplyAsync`/`PUT {id}/apply` verbatim, with the Value sourced from a history entry's `newValue` instead of the curated picker's dropdown. This is deliberate (FR-17/AC #3's "same Preview and Apply steps, not a distinct code path") and means Task 8's frontend work is additive UI on top of Story 6.2's existing `FontPairingPicker`/`candidateSlug`/`handleApply`, not a parallel implementation.
- **Minor, non-exploitable today:** `ApplyValueAsync`'s raw SQL writes directly to `settings` by `id`, which bypasses `SettingConfiguration.cs`'s `HasQueryFilter(s => !s.IsDeleted)` (query filters only apply to LINQ, never to raw SQL). Nothing in this codebase ever soft-deletes a `Setting` today, so this has no live consequence — noted for future-proofing only, not something to fix in this story.

### Debug Log References

- **`ApplyValueAsync`'s InMemory limitation, reproduced directly (not assumed):** wrote a throwaway probe test calling `SettingRepository.ApplyValueAsync` against an InMemory-backed `FlexDemyDbContext`. It threw `InvalidOperationException: "Relational-specific methods can only be used when the context is using a relational database provider."` — the exception fires the instant `db.Database.SqlQuery<T>(...)` is invoked, before any SQL shape/translation is attempted. This is one level further out than Story 6.1's InMemory discovery (there, InMemory ran the statement but silently didn't enforce a constraint; here it refuses to run the raw-SQL call at all). No test pins this specific exception — it would just be testing InMemory's own limitation, not this repository's behavior — but `SettingRepositoryTests.cs` documents it in a comment for the same reason Story 6.1 documented its unique-index gap. The probe test was removed after confirming the behavior.
- **One necessary deviation from the story's exact Task 6 text:** the story's `SettingsControllerTests.cs` bullet asked for Master/Support/Student/Tutor authorization coverage specific to `GetSettingHistory`, matching the phrasing used for other endpoints. On inspection, `[Authorize(Policy = FeatureKeys.SettingsManage)]` is a **class-level** attribute on `SettingsController` (established in Story 6.1) — the existing `A_Master_user_is_authorized_for_SettingsManage`/`A_Support_user_is_authorized_for_SettingsManage_unlike_AiConfigManage_or_MasterDataManage`/`A_Student_or_Tutor_is_not_authorized_for_SettingsManage` tests already cover the policy for the whole controller, not per-action, and the file's own class comment explains why per-action authorization can't be exercised by directly constructing/calling a controller action. Added a plain `GetSettingHistory_returns_the_service_result_wrapped_in_200` action-body test instead (matching `GetAllSettings`/`GetFontPairings`'s existing shape) rather than a redundant/misleading duplicate authorization test.
- **NSubstitute gotcha hit and fixed during Task 6:** `SettingsServiceTests.cs`'s `CreateSut` helper originally configured a wildcard default for `repository.ApplyValueAsync(...)` unconditionally, including when a caller passed its own pre-configured `repository`. Since NSubstitute resolves overlapping matchers by most-recently-configured (not most-specific), the helper's later wildcard config silently overrode a test's own specific `.Returns(...)` setup, causing two new tests to fail with wrong values. Fixed by only applying the default when `repository` was freshly created inside the helper (i.e. the caller didn't supply one).
- **Code Review Fix Pass (2026-08-16):** the combined Epic 6 code review found a real bug in this story's own scope, distinct from Epic 6's critical authorization bug (see 6.2's Debug Log for that one): `Settings.tsx`'s `handleApply` only refetched the history cache `if (isHistoryOpen)` at the moment Apply succeeded — a plain picker Apply made while the history panel happened to be closed left the stale cached list in place, so reopening history afterward showed data missing the just-applied entry. This is exactly the failure mode this story's own Task 8 text warned against by name ("without this, reopening history right after a restore... would show stale data") but the shipped code only covered the restore-from-open-history case, not a plain Apply from the main picker while history was closed. Fixed by unconditionally invalidating the cache (`setHistory(null)`) when Apply succeeds and history isn't currently open, forcing a real fetch on the next open — covered by a new test (`invalidates the cached history when Apply succeeds while the history panel is closed...`) that reproduces the exact sequence: Apply with history closed → open history → asserts a fresh fetch occurs and the new entry renders.
