# Story 2.8: AI Structure Extraction (`extractStructure`)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tutor,
I want the system to propose a Chapter → Topic → Subtopic → Content structure from my parsed files,
so that I edit and confirm rather than build the structure from a blank page.

## Acceptance Criteria

1. **Given** a successfully parsed file, **when** `extractStructure()` runs via Epic 1's `IAiGateway`, **then** it proposes a nested Chapter → Topic → Subtopic → Content structure with per-file status. [Source: epics.md Story 2.8]
2. **Given** one file's extraction fails, **when** other files are still processing, **then** the failure never blocks other files' extraction, and the failed file is independently retryable. [Source: epics.md Story 2.8]

## Dev Notes

- **This story has a hard sequencing dependency on both Story 2.6 (Hangfire, `CourseFile`, the job-chaining pattern) and Story 2.7 (`ParsedContent`, the `ParseFileJob` this story's Task 4 modifies)** — check the actual codebase state, not just these stories' own files, before starting dev; if either hasn't actually been implemented yet, this story can't be either.
- **The Story 2.8 → Story 2.9 entity-sequencing gap is the central design problem this story solves** — see Task 1's inline contract description for the full reasoning. This is worth restating plainly: without the staged-JSON approach, Story 2.8 (numbered before 2.9) would have no legal place to put its output, since the real `Chapter`/`Topic`/`Subtopic`/`ContentBlock` tables don't exist until Story 2.9 creates them. Staging the proposal as JSON on the already-existing `CourseFile` row sidesteps that ordering problem cleanly, at the cost of one extra "materialize" step Story 2.9 must own. If Story 2.9 is ever resequenced to build *before* this story, this whole staged-JSON design becomes unnecessary complexity and this story should instead write directly into real entities — but as currently ordered (2.8 before 2.9, per epics.md), staging is required, not optional.
- **This story is the first real caller of `IAiTaskGateway`, and the first to supply genuine `CourseId`/`TutorId` context** — `AiTaskModels.cs`'s own header comment names this story as exactly that. `AiTaskGateway.cs` (Story 1.6, already built) already owns budget reservation, fallback-on-failure, usage recording, and translating "both providers failed" into `AiTaskBudgetExceededException`/`AiTaskUnavailableException` — this story's job does **not** reimplement any of that. Task 4's exception handling is deliberately not a hardcoded two-case switch (an earlier draft of this story assumed it could be — corrected after checking `AiTaskGateway.DispatchAsync`'s real code, which can also throw a raw `NotFoundException` from its own config lookup before either documented exception type is even reachable): the job explicitly special-cases only `AiTaskBudgetExceededException` (no retry), and treats everything else uniformly as retry-worthy.
- **AD-16's `ExtractionBatch`/claimed-last-item batch-completion pattern is deliberately not built by this story — a real scope decision, not a silent gap.** ARCHITECTURE-SPINE.md's AD-16 explicitly binds "the extraction use-case" to the same claimed-last-item finalize mechanism as course publish, framed around "transitioning a file-set out of its extraction phase." This story's design has no such transition to make: each `CourseFile` reaches its own terminal `Done`/`Failed` status independently (per FR-13's own "results from files that finish first surface immediately... not waiting on the whole batch"), nothing anywhere aggregates "has this whole upload batch finished extracting" into a single course-level state change, and Story 2.9's materialization step (per this story's own contract, above) operates per-file/lazily on editor-open, not on a batch-complete signal. `ExtractionBatch` exists in AD-16/the Structural Seed to solve a problem — "who finalizes the batch as a whole, and when" — that this per-file-independent design does not have. If a future story does introduce a course-level "extraction batch complete" concept (e.g. to gate something on "every uploaded file has finished extracting"), that is exactly when `Domain/Jobs/ExtractionBatch.cs` should actually get built — not preemptively here.
- **No chunking/summarization for very large parsed documents** — this story sends `CourseFile.ParsedContent` to the AI in one call, relying on `AiTaskRequest.MaxTokens`/the configured model's own context window. A very large source document (e.g. a full textbook chapter) could exceed a smaller model's context window, causing a real (if not obviously labeled) failure. `[ASSUMPTION: out of scope for this story — a known limitation, not silently handled; if this becomes a real problem in practice, a future story should add chunking/map-reduce-style extraction, not this one]`.
- **Retry semantics for the transient-failure path (`AiTaskUnavailableException`) stay identical to Stories 2.6/2.7's `ScanFileJob`/`ParseFileJob`, deliberately** — same reasoning as Story 2.7's own note on this: three independently-invented retry mechanisms for three structurally similar jobs in the same epic would be a real consistency gap. `AiTaskBudgetExceededException`'s no-retry handling is the one deliberate deviation, and it's deviating for a stated reason (retrying cannot help), not by oversight.
- **No new backend retry/delete endpoint** — same reasoning as Stories 2.6/2.7: retry is "re-upload the same file through the existing upload endpoint," re-running the whole scan→parse→extract pipeline from scratch. A tutor whose file failed only at the extraction step (scan and parse both already succeeded) re-pays for a full re-scan/re-parse on retry, which is wasteful but consistent with the existing design across all three stories — flagged as a known inefficiency, not fixed here (a genuinely more efficient "retry from this step only" mechanism is a reasonable future hardening, not required by any AC).
