# Story 6.4: Curated font-size scale with the same preview/apply/history flow

Status: done

## Story

As a Master or Support admin,
I want to preview a candidate font-size scale and only apply it after confirming, the same way I already do for font pairing,
so that I can adjust text sizing site-wide without accidentally breaking legibility or layout, or affecting the live site before I'm sure.

## Acceptance Criteria

1. The Settings screen offers a fixed, pre-approved list of Font Size scales for selection — a selectable list, not a free-numeric-value field. [Source: prd.md#FR-18]
2. Any attempt to set the FontSize setting's Value — via the picker or a direct API call — is rejected server-side (not just in the picker UI) if it isn't one of the currently curated scale identifiers. [Source: prd.md#FR-19]
3. Font Size and Font Pairing are completely independent Settings — changing one never affects the other's Value, IsActive state, or change history. [Source: prd.md#FR-20]
4. Selecting a candidate Font Size scale goes through the exact same Preview, Apply, curation-check, and Change History mechanisms already built for Font Pairing — no new preview/apply/history UI or backend path. [Source: prd.md#FR-21]
5. A Font Size scale is a single, indivisible Setting Value — a proportional root-scale factor, not several independently mutable roles — so there is no partial-update state possible. [Source: prd.md#FR-22]

  - [x] **The Preview mechanism needs a different technique than `FontPairingPicker`'s, and this is the single most important implementation detail in this story — read carefully before writing any code, including the baseline-pinning subtlety in the last paragraph, which is easy to get subtly wrong even after grasping the general idea.** `FontPairingPicker`'s preview works by setting `--font-display`/`--font-sans`/`--font-mono` as inline CSS custom properties on a local wrapper `<div>`; because CSS custom properties inherit normally down the DOM tree, and the sample children reference `var(--font-display)` etc. directly, the override stays scoped to that wrapper's subtree without ever touching `document.documentElement`. **This does NOT work the same way for `text-*` Tailwind classes**, because Tailwind's rem-based sizing is relative to the **document root's** font-size specifically (that's what "rem" — root em — means), not the nearest ancestor's. Setting `font-size` on a local preview wrapper has **zero effect** on any `rem`-sized descendant, no matter how deeply nested — rem units skip every intermediate ancestor and resolve straight against `<html>`. Using `document.documentElement`'s actual font-size to preview would violate the same hard rule `FontPairingPicker`'s preview already respects (AD-8: Preview never touches `document.documentElement`; only Apply does, and only `SiteSettingsContext` does it). The general direction: set a wrapper's `fontSize` to reflect the candidate's `rootFontScale`, and give each sample child an explicit **`em`-based** (not Tailwind `text-*` class-based) inline `fontSize` — `em` units resolve against the *nearest ancestor's* font-size, not the document root, so a properly-anchored wrapper genuinely and correctly previews "what the site would look like at this root scale," confined to its own subtree, with the live site completely unaffected. Do not attempt to reuse Tailwind `text-*` utility classes anywhere inside this specific preview block.

    **The baseline-pinning subtlety:** a plain `<div style={{ fontSize: candidate.rootFontScale }}>` (e.g. `fontSize: '112%'`) is **wrong** — a percentage `font-size` on a *non-root* element resolves relative to its *parent's currently-computed* font-size (ordinary CSS inheritance), which itself already reflects whatever `--root-font-scale` is *currently live* on `<html>` — not the neutral 100% baseline a real Apply would start from. Previewing "112%" while a different, already-applied scale (say 90%) is active would silently compound to roughly 112% of 90%, not a clean 112% — an inaccurate preview that misleads the admin about what Apply will actually do. (This defect would not surface during this story's own testing, since Task 1 seeds only one 100% scale — it only manifests once a second curated scale exists, which the PRD's own Open Items anticipate as near-future work, so get it right now rather than shipping a latent bug.) Fix: pin the preview to a fixed, known baseline before applying the candidate's percentage — e.g. an **outer** wrapper hard-set to `style={{ fontSize: '16px' }}` (the same neutral UA-default reference `<html>`'s own percentage math is anchored to when nothing overrides it), with an **inner** wrapper inside it applying `style={{ fontSize: candidate.rootFontScale }}` (now correctly computing as a percentage of that fixed 16px, not of whatever's currently live) — and the `em`-based sample children go inside the inner wrapper.

## Dev Notes

- **Central design correction, read this before anything else:** an earlier planning pass (the PRD's own reviewer-gate round) assumed Font Size would need the same Display/Body/Mono three-role atomic-resolution structure Font Pairing has (mirroring FR-11 with a new FR-22). This story's own implementation research verified that assumption was **wrong**: `index.css` has zero font-size CSS custom properties, no `tailwind.config` override exists anywhere in this repo, and Tailwind's default rem-based `text-*` scale is in full, unmodified effect. There is no natural role split for *size* the way there is for *family* — text sizing varies continuously per element through Tailwind's granular scale, not through three semantic buckets. The PRD (`prd.md` §4.7, Glossary, NFR-6, Non-Goals, Open Items) and `epics-AdminSettings.md` (FR17/FR21, Story 6.4's own ACs) were both corrected to match this reality before this story was drafted — read the current text of both, not any earlier assumption. `FontSizeDefinition` therefore has **one** value field (`RootFontScale`), not three, and there is no FR-11-style atomicity bug to guard against (see FR-22/AC #5's actual current wording: "no partial-update state possible," not "roles resolved together").
- **The `rem`-vs-`em` distinction in Task 7 is the single easiest way to get this story subtly wrong — and even the right general idea has a baseline-pinning trap inside it (see Task 7's full text, not just this summary).** `FontPairingPicker`'s scoped-preview technique (CSS custom properties + matching `var()` references on children) does not transfer to font size, because Tailwind's `text-*` utilities are `rem`-based (relative to the *document root*, always, regardless of DOM nesting) rather than inheriting from the nearest ancestor the way a CSS custom property does. A naive single-wrapper `em`-based fix still has a bug: a plain percentage `fontSize` on a non-root wrapper inherits from whatever the *currently-live* root scale already is, not a neutral 100% baseline, so previewing compounds with reality instead of replacing it — invisible while only one scale is seeded (this story's own DoD), live the moment a second one exists. Task 7 specifies the fixed-baseline nested-wrapper fix; use it exactly.
- **`GetEffectiveFontsAsync` must be *restructured*, not extended in place — its current early-return shape breaks under a 4th DTO field.** Read Task 3's rewritten code sample before touching this method; the tempting "just hardcode a value where the compiler complains" fix would silently make font-size resolution permanently dead code, defeating AC #3's independence guarantee for the one endpoint every real visitor calls.
- **`SettingsService.ApplyAsync`'s curation-check branch is the only place FontSize-specific logic lives on the backend.** Everything else in the Apply/history/effective-value machinery is already fully KeyType-agnostic (confirmed by reading the current shipped code, not assumed) — this is precisely what AC #3's independence guarantee rests on structurally, not just on test coverage.
- **`GetEffectiveFontsAsync`/`EffectiveFontsDto` is extended, not duplicated.** A second public endpoint (e.g. `GET /effective-font-size`) was considered and rejected: typography (family + size) is one coherent concept for an anonymous caller, and the code-review fix that introduced this endpoint was deliberately designed around "one minimal public endpoint, no admin-shaped data" — splitting it now would contradict that design without a real reason to.
- **`index.css`'s new `html { font-size: var(--root-font-scale); }` rule is genuinely new UI machinery**, same category as `FontPairingPicker`'s scoped-preview mechanism was for Story 6.2 — no existing precedent in this codebase for a runtime-adjustable root-level type scale.
