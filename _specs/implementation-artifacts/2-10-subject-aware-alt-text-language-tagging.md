# Story 2.10: Subject-Aware Alt-Text & Language Tagging

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a student using assistive technology,
I want math/chemistry notation to carry AI-generated alt-text and Hindi content to carry correct language tagging,
so that a screen reader announces this content correctly.

## Acceptance Criteria

1. **Given** a content block containing math or chemistry notation, **when** it is authored or AI-extracted, **then** `describeNotation()` generates screen-reader alt-text for it. [Source: epics.md Story 2.10; PRD FR-16]
2. **Given** a content block containing Hindi (Devanagari) text, **when** it is rendered, **then** it carries `lang="hi"` at the content-block level. [Source: epics.md Story 2.10; PRD FR-16]
3. This authoring-time output is what Epic 3's cross-view golden-file parity tests will validate against once the student view exists — not a task to build here, but a reason this story's output must be stable/deterministic where possible, not best-effort-and-forget. [Source: epics.md Story 2.10]

## Dev Notes

- **This story has a hard sequencing dependency on Story 2.9** (`ContentTreeService`, `ContentBlock.Format`/`Notation`/`Text`/`Lang`/`AltText` fields, the materialization step this story's Task 2 also modifies) and reuses Story 2.8's already-built `IAiTaskGateway` plumbing (no new gateway call shape — `DescribeNotationAsync` already exists on the interface, per `IAiTaskGateway.cs`, unused by any caller until this story). Check the actual codebase state before starting dev.
- **Why `DescribeNotationAsync` is called inline/synchronously inside a normal HTTP request, never as a Hangfire job** — this is AD-14's own explicit, adopted rule, not a choice this story is making independently: "`DescribeNotationAsync` runs inside the per-node extraction/authoring pipeline, not the publish-time batch job (AD-15) — alt-text is an authoring-time accessibility requirement (FR-16), not publish-gated content." Do not build a `DescribeNotationJob`/queue anything for this — every call site in this story is a plain synchronous service-layer call, wrapped in a try/catch for the best-effort/non-blocking behavior described in Task 2, not Hangfire retry semantics.
- **Best-effort alt-text generation is a deliberate accessibility-vs-availability tradeoff, stated explicitly so it isn't mistaken for an oversight later:** a tutor's ability to save their work must never depend on the AI gateway being reachable or under budget. The cost is that some Content Blocks may end up with `AltText = null` if generation failed at authoring time and the tutor never manually filled it in (Task 4's new editable field exists partly to make that gap visible and fixable by a tutor, not just invisible dead state). A future story could add a "regenerate missing alt-text" batch/retry mechanism if this becomes a real problem in practice — not built here, since no AC requires it.
- **Language detection is a plain code heuristic, deliberately not an AI call** — re-stated here because it's the one place in this story that could be mistaken for needing gateway/budget/fallback machinery the way `describeNotation()` genuinely does. A Unicode-range check is cheap, synchronous, has no cost/availability failure mode, and is more deterministic (relevant to this story's own AC#3 framing around Epic 3's future golden-file tests) than an LLM guess would be.
- **This story overrides, not extends, Story 2.8's own AI-guessed `lang` field during materialization** — Story 2.8 explicitly scoped its own `lang` output as "a reasonable first pass... not a hardened detection pipeline," deferring the real version to this story. Don't try to reconcile/merge the two signals; the detector's output wins unconditionally during materialization.
- **Scope boundary — this story does not touch Chapter/Topic/Subtopic titles**, only `ContentBlock.Text`/`Notation`/`Lang`/`AltText`, matching both AC's own "content block" framing and FR-16's literal text.
