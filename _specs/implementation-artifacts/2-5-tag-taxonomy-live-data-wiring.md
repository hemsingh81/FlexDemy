# Story 2.5: Tag & Taxonomy Live Data Wiring

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tutor,
I want Story 2.1's Tags and Taxonomy steps to read real, admin-governed data,
so that my selections are valid and consistent with the rest of the platform.

## Acceptance Criteria

1. **Given** Epic 1's real Tag backend (Story 1.9), **when** the Tags step renders, **then** it shows a searchable, type-ahead multi-select populated from the live `GET /api/v1/tags` list — no free-text entry. [Source: epics.md Story 2.5]
2. **Given** the existing taxonomy master-data system, **when** the Taxonomy step renders, **then** Country → State → City → Board → Class → Subject cascade correctly, with State/City required-ness read from real master data per board (`Board.stateId`), not hardcoded. [Source: epics.md Story 2.5]
3. **Given** the epic-wide auto-persist requirement (FR-10, "auto-persists wizard state as a Draft after every step") and Story 2.4's own Dev Notes explicitly naming this story as where `Subject`/taxonomy persistence happens, **when** a tutor makes a Tags or Taxonomy selection and advances/goes back/finishes, **then** the selected tag ids and taxonomy ids persist to the real Draft the same way Title/Description already do — not just held in local React state until Story 2.4's `commitStep()` runs. This is not explicitly spelled out in epics.md's 2-bullet AC list (which only describes step-*rendering* behavior), but leaving selections unpersisted would silently regress the very Draft-persistence guarantee Story 2.4 just built, for exactly the 2 steps this story owns. [Source: Dev Notes design decision below; Story 2.4 Dev Notes: "Subject/Level are explicitly Story 2.5's Taxonomy-wiring responsibility"]

## Dev Notes

- **This story is meaningfully smaller/lower-risk than Story 2.4** — both the Tag backend (Story 1.9) and the Master Data backend (earlier Epic 1) already fully exist, are already proven working (consumed today by `TagManagement.tsx`/`MasterDataManager.tsx` admin screens AND, more relevantly, by `useProfileSetup.ts`'s Tutor/Student-facing cascading form), and need **zero backend changes** of their own. The only backend work is extending `Course`/`CourseDto`/`UpdateDraftCourseRequest`/`CourseService.UpdateDraftCourseAsync` — already-established Story 2.4 surface, not a new feature folder.
- **The single explicit design decision this story makes (AC #3):** epics.md's own 2-bullet AC list for this story only describes step *rendering* behavior — it says nothing about persistence. Two readings were possible: (a) this story is scoped to rendering only, leaving Tags/Taxonomy selections un-persisted (lost on any reload, exactly like before this story); (b) this story also closes the persistence gap Story 2.4's own Dev Notes explicitly named it for ("`Subject`/`Level` are explicitly Story 2.5's Taxonomy-wiring responsibility"). **This story chooses (b).** Reasoning: FR-10 (epic-wide, not story-specific) already requires "auto-persists wizard state as a Draft after every step" — Steps 1 and 4 already do this (Story 2.4); leaving Steps 2/3 silently exempt would be an inconsistent, confusing half-implementation of that same FR, and Story 2.4's own Dev Notes already flagged the two new-taxonomy-field gap on `Course` by name, pointing squarely at this story to close it. If a future review finds reading (a) was actually intended, the fix is small (stop sending `tagIds`/taxonomy fields in `commitStep()`, drop the new `Course` fields) — but shipping without persistence and silently regressing FR-10 for 2 of 4 steps is the riskier default.
- **Why `Course.Tags` (legacy free-text strings) and the new `Course.TagIds` (real Tag id references) deliberately coexist, unreconciled, on the same entity:** `Tags` is the pre-Epic-2 catalog shape's free-text field (`List<string>` of arbitrary display strings, still used only by the old, still-unused-by-any-frontend `CreateCourseRequest`/`CreateCourseAsync` path — confirmed untouched by Story 2.4). Story 1.9's own Dev Notes already anticipated this exact split: *"`Course.tags` today is still a plain string array with no master-data backing... stays that way until an Epic 2 story wires it to real `Tag` ids. Don't build a `CourseTag` join table or migrate `Course.tags` here."* This story is that wiring — but it adds a **new, parallel** `TagIds` field rather than repurposing `Tags` in place, because reinterpreting an existing field's semantics (free-text strings → id references) out from under the old catalog-creation path would be a silent breaking change to code this story has no reason to touch. Reconciling the two (e.g. denormalizing `TagIds`→display names back into `Tags` for catalog search/filter compatibility once a course is actually published) is naturally Epic 3's publish-pipeline concern, not this story's — nothing currently transitions a `Course` out of `Draft` at all (confirmed during Story 2.4).
- **Why the 6 new taxonomy id fields are new columns, not a repurposing of the existing free-text `Subject`/`Level`/`TargetGradeTag` fields:** same reasoning as above — those free-text fields belong to the old catalog shape and its `GetCoursesAsync(gradeTag, search, subject)` filter, which nothing in this story's scope touches. The wizard's Taxonomy step is an id-based cascade (`Country→State→City→Board→ClassLevel→Subject`), a different, richer model than 3 flat strings; adding 6 new nullable id columns is the honest representation, not a lossy fit into the old shape.
- **Why there's deliberately no *referential-integrity* validation of `TagIds`/taxonomy ids server-side** (unlike Title, which the backend does re-validate, per Story 2.4's own "backend must not trust the client alone" precedent): AC #1/#2 are specifically about the *steps rendering real data* — every tag id and taxonomy id a tutor can select only ever comes from an `<option>`/multi-select populated by this story's own live fetch (Task 8), the same reasoning `deferred-work.md` already used for `isTaxonomyStepValid`'s unvalidated `boardId` ("unreachable via the UI today since `boardId` only ever comes from the rendered `<option>` list"). Adding full existence-checking would mean `CourseService` newly depending on `ITagService` + 6 MasterData service interfaces (`ICountryService`/`IStateService`/`ICityService`/`IBoardService`/`IClassLevelService`/`ISubjectService`, all of which already exist per-entity, confirmed by reading `Application/Tags/ITagService.cs` and `Application/MasterData/{Country,Board}/I{Entity}Service.cs` this session) purely to defend against a non-UI caller (a raw API call, a future non-web client) sending a garbage id — a real gap, but disproportionate to this story's stated scope and epics.md's own framing of it as a small, un-flagged-for-sizing-risk story. Flag as a legitimate future hardening item if a later story's review disagrees. **Note (code review):** this claim is about *existence*-checking specifically — cheap *format*-level sanitization (blank/whitespace filtering, `HasMaxLength(64)` enforcement) was added during this story's own review pass; see Review Findings below.
- **`useProfileSetup.ts` confirms the exact same `masterDataService.ts` calls already work for a Tutor/Student-facing (non-admin) form** — useful precedent for *which functions to call and how they behave*, but **not** a `useEffect`-based cascade to literally copy: that hook fetches `getStates`/`getCities` directly inside its `selectCountry`/`selectState` `onChange` callbacks, not from a `useEffect` watching state. `useCourseDraft.ts`'s `updateTaxonomy` is one generic switch-based setter (unlike `useProfileSetup.ts`'s per-field callbacks), so Task 8 uses a `useEffect` keyed on `data.countryId`/`data.stateId` instead — a deliberate, better-fitting divergence from that file's structure, not an inconsistency to resolve.
- **`StepTags.tsx` and `StepTaxonomy.tsx` need zero changes** — both are already fully generic over whatever `tags`/`lockedTags`/`countries`/`states`/`cities`/`boards`/`classLevels`/`subjects` arrays the hook returns (confirmed by reading both files in full this session); `StepTaxonomy.tsx` already does its own client-side parent-filtering (`states.filter(s => s.countryId === draft.countryId)` etc.) and already reads board-scoped State/City required-ness from `board?.stateId`, satisfying AC #2 exactly as written — this is presentation logic Story 2.1 already built correctly against mock data shaped identically to the real backend's DTOs. Confirm this remains true during dev rather than assuming it, but no changes are anticipated.
- **Tutor-role access already works for every endpoint this story needs, confirmed this session:** `TagsController`'s `GET` has no policy restriction beyond `[Authorize]` (any authenticated role); every MasterData controller's `GET` is identical — only `includeInactive=true` is gated to Master/Support server-side (a Tutor's request for it is silently ignored, always getting the active-only list, which is exactly the desired behavior for a wizard and needs no special handling — don't pass `includeInactive: true` from this hook).

### Review Findings

3-layer adversarial review (Blind Hunter, Edge Case Hunter, Acceptance Auditor) — 8 patches applied (2 confirmed independently by all 3 layers, 1 by 2 layers), plus several deliberately-deferred items already reasoned about above.

- [x] [Review][Patch] The migration's own `.Designer.cs` (`BuildTargetModel`) still configured `TagIds` with `.HasDefaultValue(new List<string>())` even after `CourseConfiguration.cs` and the main `FlexDemyDbContextModelSnapshot.cs` were both corrected to `.HasDefaultValueSql("'{}'")` [BackEnd/src/FlexDemy.Infrastructure/Persistence/Migrations/20260811192911_AddCourseTagsAndTaxonomy.Designer.cs] — **found independently by all 3 review layers**, the review's single highest-confidence finding. Root cause: the migration's `Designer.cs` and the main `ModelSnapshot.cs` are two separate auto-generated files that `dotnet ef migrations add` normally keeps in sync in one pass; this story's own migration was hand-patched (via manual file edits after `dotnet ef` command-line tooling hit connection issues, documented in Debug Log) to fix the `TagIds` default-value bug, and the fix was applied to the main snapshot but missed the per-migration `Designer.cs` copy. Runtime behavior was actually unaffected (EF's `PendingModelChangesWarning` check compares against the main snapshot, which was already correct — confirmed by the app starting cleanly both before and after this patch), but the migration's own historical record was self-contradictory. **Fixed:** `Designer.cs` now matches `CourseConfiguration.cs`/`ModelSnapshot.cs` exactly. Re-verified via a fresh Docker rebuild + restart (clean startup, no `PendingModelChangesWarning`). A new regression test (`TagIds_uses_HasDefaultValueSql_not_HasDefaultValue`) directly asserts the model metadata so this specific mistake can't silently recur.
- [x] [Review][Patch] A UI-only sentinel value leaked into a real backend call: the cascading `useEffect` on `[data.stateId]` called `getCities(data.stateId)` even when `data.stateId === NATIONAL_STATE_VALUE` ("National / Not Applicable"), sending a real `getCities('NATIONAL')` request on every render after that selection [FrontEnd/src/features/CourseWizard/useCourseDraft.ts] — found by Blind Hunter, who confirmed against `StepTaxonomy.tsx` that the *rendered* city list was unaffected (client-side filtering already masked it) but the wasted/spurious call still fired. **Fixed:** the cities effect's guard now excludes `NATIONAL_STATE_VALUE` explicitly, matching `commitStep()`'s existing identical guard.

  1. **Migration failed outright against a populated table**: the first-generated migration added `tag_ids text[] NOT NULL` with no `DEFAULT` clause at all (EF Core doesn't infer one for a `List<string>` property — its CLR default is `null`, not `[]`, since a C# field initializer isn't visible to migration-default inference). Applying it against the real (non-empty) `courses` table failed with `column "tag_ids" ... contains null values`. **Fixed:** added `.HasDefaultValue(new List<string>())` to `CourseConfiguration.cs`, regenerated the migration (required manually reverting a stale model-snapshot mismatch caused by deleting/regenerating migration files without keeping the snapshot in sync — see below).

Root cause: a `List<string>` is a mutable reference type with no stable value-equality; EF's snapshot-vs-model comparer constructs a *new* `List<string>()` instance every time `OnModelCreating` runs and can never recognize it as "the same" default the snapshot recorded, so the model looks permanently changed. **Fixed:** switched to `.HasDefaultValueSql("'{}'")` (a plain, directly-comparable SQL string) instead — re-verified via the same live stack: app starts cleanly, migration applies, and a real create-draft → update-with-tags/taxonomy → separate fresh GET round-trip correctly persists and returns `tagIds`/all 6 taxonomy fields (including confirming duplicate tag ids sent in a request are deduplicated server-side).
