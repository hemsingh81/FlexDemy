## Story

As a QA engineer,
I want automated visual regression tests comparing the editor and student views for math, chemistry, and Hindi content,
so that rendering drift between the two views is caught automatically, not by manual inspection.

## Acceptance Criteria

1. **Given** the editor (Epic 2) and student view (this epic) both exist, **when** the Vitest 4 `toMatchScreenshot()` suite runs, **then** it catches rendering drift for math, chemistry, and Hindi-script content between the two views. [Source: epics.md Story 3.11; frontend AD-6]
2. **Given** CI runs these tests, **when** fonts and KaTeX rendering are involved, **then** the suite waits for `document.fonts.ready` and pins fonts for determinism. [Source: epics.md Story 3.11; frontend AD-6]

- **Font-pinning gap (Task 2's first bullet) — only PARTIALLY satisfied, despite the checkbox**: this app loads no explicit webfont anywhere (`FrontEnd/index.html`, `FrontEnd/src/index.css` checked) — KaTeX math/chemistry rendering is deterministic regardless (self-hosted via `@import "katex/dist/katex.min.css"`, which bundles its own font files, not a system-font fallback), but Hindi/Devanagari text has no explicit webfont and renders via the browser's own system-font fallback in **both** the editor and student views alike. This is a real, pre-existing gap against AD-6's "no system-font fallback" determinism rule, for the Hindi pair specifically — AC#2's "pins fonts for determinism" is true for KaTeX and false for Hindi. The task checkbox above is marked done because the *task's other subtask* (the shared `document.fonts.ready` helper) is fully done and this gap is pre-existing/out-of-scope to fix, not because the font-pinning requirement itself is fully met — flagging that distinction explicitly here so a checkbox-only reader isn't misled. Fixing this means adding and self-hosting a Devanagari webfont (e.g. Noto Sans Devanagari), which changes real rendering output app-wide, not just test tooling — out of this story's own explicit scope ("adds tooling and tests only — does not change any rendering component," per Dev Notes). Flagging as a follow-up rather than silently fixing or silently ignoring it.
- **Task 3 comparison-pair mechanics**: math/chemistry pairs are "strong" parity tests — both `ContentTreeNode.tsx` (editor) and `ContentNodeReadingPane.tsx` (student, reached via `ReviewAsStudentPreview` — Story 3.9's real AD-3 cross-feature import) call the exact same shared `renderNotation()` function, so both sides are provably the same rendering path, not just visually similar. The Hindi/text pair is deliberately a "weaker" comparison, documented as such inline in `hindi-text-parity.test.tsx`: the editor renders an unstyled `<textarea>` form control (`ContentTreeNode.tsx`'s shared `EditableField`) while the student view renders a styled, keyword-highlighted `<p>` (`KeywordText.tsx`) — structurally different components by design, not a bug. Each of the suite's 6 assertions (3 pairs × 2 views) is independently compared against its own committed baseline PNG (the standard golden-file/snapshot mechanism — `toMatchScreenshot()` diffs against a stored reference image, not against a live sibling element); "catches drift between the two views" means: (a) both sides' baselines are human-reviewable side-by-side for the math/chemistry pairs to confirm they visually match, and (b) any future regression in either view's own rendering is caught independently by its own snapshot comparison.
- **Baseline screenshot storage path**: `toMatchScreenshot()`'s default convention nests baselines under a sibling `__screenshots__/` folder relative to the test file. Since the test files themselves already live in a directory named `__screenshots__/` (the story's own mirror-path convention, chosen so the `vite.config.ts` `visual` project's `include` glob can scope to exactly these files), this produces a double-nested `__screenshots__/__screenshots__/<test-file>/*.png` path. Cosmetically unusual but functionally correct — confirmed both `-u` baseline generation and a subsequent clean re-run (no `-u`) pass against the committed files.
- **Baseline filenames (post-review fix)**: `toMatchScreenshot()` derives its baseline filename from the full `describe > it` title by default (e.g. `Cross-view-visual-parity-math-notation-editor-rendering-matches-its-golden-baseline-1-chromium-win32.png` — ~100 characters), which is unwieldy and doesn't fit Windows path-length limits well when nested this deep. `toMatchScreenshot(name)` accepts an explicit name string as its first argument, which fully replaces that default (confirmed in `@vitest/browser`'s own source, `expect-element.js`: `o = typeof n === 'string' ? n : ...`). All 6 calls now pass an explicit `'editor'`/`'student'` — the test file's own directory name already identifies the content type (math/chemistry/Hindi), so the files are just `editor-chromium-win32.png` / `student-chromium-win32.png` under each test file's screenshot folder. Baselines regenerated and re-verified after the rename.
- **Task 4 (CI wiring confirmation) — real gap, not implementable, checkbox marked done in the "addressed/documented" sense, not the literal sense**: confirmed via repo-wide search that no CI pipeline exists in this repository at all (no `.github/workflows/*`, no other CI system's config file). There is nothing to "confirm both projects run in the same CI job" against, so the task as literally worded cannot be executed — the checkbox reflects that this was investigated and the outcome fully documented, not that a CI job was verified. Documenting the requirements for whenever CI is introduced: (1) the CI job must run `npx playwright install --with-deps chromium` before `vitest run` (which invokes both `test.projects` entries by default — no extra flag needed to include the `visual` project), and must not filter to `--project unit` only; (2) **the 6 committed baseline PNGs are platform-locked** — `@vitest/browser`'s own screenshot-path resolver embeds `os.platform()` directly into each baseline's filename (confirmed: all 6 committed files end in `-win32.png`, generated on this Windows dev machine), so a Linux CI runner (the common case for GitHub Actions) will look for `-linux.png` files that don't exist yet and every visual test will fail as "no baseline" on its first CI run — not a regression, but a one-time setup step (generate and review `-linux.png` baselines against whatever OS the CI runner actually uses, via `vitest run --project visual -u` run on that runner). Setting up CI from scratch for this repo is a separate, cross-cutting initiative well beyond this story's own scope (visual-regression tooling), so it is flagged here as a follow-up rather than built as unrequested new scope.
