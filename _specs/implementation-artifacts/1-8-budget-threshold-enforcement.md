# Story 1.8: Budget Threshold Enforcement

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

*(Sizing risk: this story introduces a genuinely new pattern for this codebase — raw atomic SQL outside the normal EF Core LINQ/`SaveChangesAsync` flow — plus a reserve/settle/release protocol threaded through both of `AiTaskGateway`'s dispatch paths. If it doesn't fit a single dev session, the natural split point is: reserve/settle/release mechanics first, the `CurrentSpend` live-wire (a small, separable backend-only read-path change) second.)*

## Story

As an admin,
I want a per-task cost threshold enforced pre-flight,
So that spend is blocked before it happens, not just reported after.

## Acceptance Criteria

1. Before any `IAiTaskGateway` call reaches the AI gateway (primary or fallback), an atomic reserve checks the task's running spend against its configured `BudgetThreshold` and blocks the call — via a single atomic SQL statement, not a read-then-write check that could race under concurrent calls — if the reservation would push spend past the threshold. [Source: epics.md Story 1.8; ARCHITECTURE-SPINE.md AD-18: "a single atomic statement that reserves spend against AD-19's live threshold and blocks... *before* the call happens, not a cached running total with periodic reconciliation"]
2. A blocked request fails with a new, distinct exception (never a silent no-op, never `AiTaskUnavailableException` — that's Story 1.6's "both providers failed" case, a different condition from "budget exhausted"), mapped to a 429 status. [Source: epics.md Story 1.8: "the request is blocked before it is made, via an atomic reserve, not post-hoc recording"]
3. Because the exact cost of a call isn't known until it completes (token counts only exist after the response returns), the pre-flight reserve uses a conservative *estimate*; once the real cost is known (Story 1.7's `AiUsageService.RecordUsageAsync`), the reservation is trued up to the real amount. If the call fails entirely (both primary and fallback), the full estimated reservation is released, since nothing was actually spent. [Source: derived from AD-18's rule — no prior story or AD resolves how a pre-flight reserve can use an unknown future cost; this story's own design decision, documented in Dev Notes]
4. `AiTaskConfigDto.CurrentSpend` (hardcoded to `0m` since Story 1.5, per that story's and Story 1.7's own Dev Notes: "real spend tracking is Story 1.8's `AiTaskBudget`") now reflects real, live spend — Story 1.1's threshold-warning UI (`AiTaskConfigRow.tsx`'s `isOverThreshold = task.currentSpend >= task.budgetThreshold`) starts firing on real data with **zero frontend code changes**, since the wiring is entirely on the read side of the existing `GET /api/v1/ai-task-configs` response. [Source: epics.md Story 1.8; FrontEnd/src/features/Admin/AiConfiguration/useAiTaskConfig.ts's existing "currentSpend always returns 0 until Story 1.7/1.8" comment; AiTaskConfigRow.tsx's existing threshold-warning logic, unchanged since Story 1.1]

## Dev Notes

- **Why raw SQL, and why it doesn't go through `IUnitOfWork`.** Every other repository in this codebase (`AiTaskConfigRepository`, `AiTaskUsageRepository`, all of `MasterData`, etc.) stages a change via EF Core's change tracker and lets the calling service's single `IUnitOfWork.SaveChangesAsync()` commit it (AD-11). That pattern is correct for "read an entity, mutate a property, save" — but it is *not* atomic under concurrency for "increment X only if X+delta stays under a limit read from a different table," which is exactly AD-18's requirement (the read-check-write would race between two concurrent requests both reading spend as $79 against an $80 threshold, both deciding they have room, both committing, landing at $80 + $80 = way over). A single `UPDATE ... WHERE ... <= (SELECT ...)` statement is atomic in Postgres on its own — no explicit transaction needed, and `IUnitOfWork` (which only exposes `SaveChangesAsync`, confirmed by reading `Application/Common/IUnitOfWork.cs` — there is no `BeginTransactionAsync` in this codebase at all) has nothing to add here. `TryReserveAsync`/`AdjustSpentAsync` therefore call `FlexDemyDbContext.Database.ExecuteSqlInterpolatedAsync(...)` directly and commit immediately, standalone, bypassing the stage-then-`SaveChangesAsync` flow entirely — a deliberate, narrow exception to AD-11's normal pattern, not a precedent to generalize elsewhere without the same atomicity justification.
- **Raw SQL bypasses `AuditSaveChangesInterceptor`.** That interceptor (confirmed by reading `Infrastructure/Persistence/Interceptors/AuditSaveChangesInterceptor.cs` and its registration) only fires on `SaveChangesAsync` — a raw `ExecuteSqlInterpolatedAsync` call never touches it, so `AiTaskBudget.UpdatedAt`/`UpdatedBy` are never stamped by reserve/settle/release operations (they're stamped once, at seed time, by the normal `SaveChangesAsync` insert). Acceptable: `AiTaskBudget` is an internal running counter, not a user-facing audited record — but don't build any admin UI or reporting that assumes `UpdatedAt` reflects the last spend change, because it won't.
- **Snake_case column names are load-bearing in the raw SQL.** `.UseSnakeCaseNamingConvention()` is registered on `FlexDemyDbContext` (in `Infrastructure/DependencyInjection.cs`'s `AddDbContext` call) — this only affects EF's own LINQ-to-SQL translation. Raw `ExecuteSqlInterpolatedAsync` strings must spell out the actual database identifiers (`ai_task_budgets`, `task_id`, `spent`, `ai_task_configs`, `budget_threshold`) directly; there is no automatic C#-property-to-snake_case translation inside a raw SQL string.
- **The reservation estimate is deliberately rough, not a claim of accuracy.** No tokenizer is used; `DefaultEstimatedCompletionTokens = 2000` and the embeddings' 4-chars-per-token heuristic are plain, named approximations, not tuned against real model behavior. This is acceptable specifically because the reservation window is only as long as the AI call itself (typically seconds) and gets trued up to the *exact* real cost (from Story 1.7's own already-precise `AiUsageService.RecordUsageAsync` computation) the moment the call finishes — the estimate only has to be in the right ballpark for that brief window, not exactly correct. If a future story needs the estimate itself to be materially more accurate (e.g. a real tokenizer), that's a self-contained follow-up to `EstimateChatReservationCost`/`EstimateEmbeddingReservationCost` — it doesn't touch the reserve/settle/release protocol around it.
- **Reserve fails closed; settle/release fail open — this asymmetry is deliberate.** `TryReserveAsync`'s call site in `AiTaskGateway` is *not* wrapped in a try/catch-swallow: if the reserve step itself throws (e.g. a DB connectivity blip), that exception propagates and the call is blocked — matching AD-18's whole purpose (guarantee enforcement, don't silently let spend through when enforcement can't be verified). This is the opposite instinct from Story 1.7's `RecordUsageSafeAsync`/this story's `SettleOrReleaseBudgetSafeAsync`, which *do* swallow failures — by the time settle/release runs, the AI call already succeeded and a real, usable response already exists; losing that response over a bookkeeping-correction failure would repeat the exact mistake Story 1.7's own code review caught and fixed for usage recording. Fail-closed for "should this call even start," fail-open for "correct the ledger after it's too late to un-start it."
- **A missing `AiTaskBudget` row blocks the call, indistinguishably from a genuinely exhausted budget.** `TryReserveAsync`'s `UPDATE ... WHERE task_id = ...` matches zero rows both when spend would exceed the threshold *and* when no budget row exists at all for that `taskId` (a seeding gap, or a hypothetical future 8th task not yet backfilled) — both surface identically as `AiTaskBudgetExceededException` → 429. This mirrors the same category of "missing-row edge case" Story 1.6/1.7's reviews already found and explicitly deferred elsewhere in this codebase (a missing `AiTaskConfig` row surfaces as a plain 404, not a distinguishable "misconfigured" error) — adding a second, non-atomic existence check before the reserve would itself reintroduce the exact race this whole story exists to prevent, so it's not a fix worth making. Deferred, not fixed, consistent with the established precedent.
- **`AiConfigService.GetTaskConfigAsync`'s new budget lookup must not let a missing budget row fail an otherwise-successful single-task config read** — catch `NotFoundException` from `budgetService.GetSpentAsync` and default to `0m`, don't let it propagate. `GetAllTaskConfigsAsync` avoids this problem entirely by using `GetAllSpentAsync`'s dictionary-with-omission shape instead of N individual `GetSpentAsync` calls.
- **This story does not touch `AiTaskUsage`/`IAiUsageService`'s existing recording *logic*** (Story 1.7, already `done`) beyond widening `RecordUsageAsync`'s return type from `Task` to `Task<decimal>` so `AiTaskGateway` can read the real cost back out for settling — the cost computation itself, the `AiTaskUsage` row it persists, and AC #1/#2 from Story 1.7 are all unchanged.
- **"Platform-wide" threshold (mentioned in epics.md Story 1.8's framing, "per-task and/or platform-wide," and PRD FR-29) is explicitly out of scope for this story.** No existing `AD`, entity, or UI (Story 1.1's `AiTaskConfigRow.tsx` only ever showed a per-task threshold input) supports a platform-wide concept — inventing one here would be scope creep beyond what any current architecture decision, UX design, or prior story's UI establishes. This story implements the per-task half of FR-29's "and/or," which every existing piece of infrastructure (AD-18, AD-19, `AiTaskConfig.BudgetThreshold`, Story 1.1's UI) already assumes. A platform-wide aggregate threshold, if still wanted, is a separate future story's scope decision, not a gap to silently fill in here.

## Previous Story Intelligence

Story 1.7 (`1-7-usage-cost-tracking-live-wire-usage-dashboard.md`, status: `done` — closed after a 2-patch adversarial review round):

- **Both of Story 1.7's patches are directly relevant precedent here.** (1) Its review found `AiTaskGateway`'s post-hoc recording call reused the caller's own `CancellationToken`, so a client cancellation after a successful AI response could silently drop an already-earned usage record — fixed by using `CancellationToken.None` for that write. This story's `SettleOrReleaseBudgetSafeAsync` must use the same `CancellationToken.None` reasoning from the start, not repeat the mistake and need a second review round to catch it. (2) Its review found a single shared price pair was applied regardless of which provider (primary or fallback) actually served a call, silently misreporting cost for every fallback-served invocation — fixed by splitting into `PricePerMillion*` and `FallbackPricePerMillion*` pairs. This story's `EstimateChatReservationCost`/`EstimateEmbeddingReservationCost` estimate against the *primary's* pricing only (a reasonable simplification for a short-lived pre-flight estimate that gets trued up immediately after) — this is a conscious choice, not the same class of bug, because the estimate is corrected to the exact real cost (using the correct primary-vs-fallback price pair, per Story 1.7's already-fixed logic) within the same call's lifetime via `SettleAsync`.
- **`RecordUsageAsync`'s return type is widening from `Task` to `Task<decimal>` in this story** — its only caller (`AiTaskGateway.RecordUsageSafeAsync`) is being modified in this same story anyway, so this isn't a breaking change to any other consumer; there is no other caller anywhere in the codebase (confirmed: Story 1.7's own Dev Notes state `IAiTaskGateway` has no real feature caller yet).
- **Story 1.7's review also independently confirmed** (both Blind Hunter and Edge Case Hunter converged on the same finding) that swallow-and-log around a post-success side effect is the correct pattern for a failure that must not undo an already-successful AI response — this story's `SettleOrReleaseBudgetSafeAsync` follows the identical shape (`try { ... } catch (Exception ex) { logger.LogError(...); }`), for the identical reason.
- **Test-writing pattern that worked well across 1.4-1.7:** direct `new Sut(dep1, dep2, ...)` construction per test (not a shared `CreateSut` helper) once a class has several dependencies each test configures differently. `AiTaskGatewayTests.cs` is about to gain a 5th constructor dependency (`IAiBudgetService`) on top of its existing 4 — default it to `TryReserveAsync(...).Returns(true)` in each test's own setup rather than introducing a shared helper now, consistent with how this file has evolved test-by-test across three prior stories already.
- **The Story 1.5 lesson, still the most important one in this codebase's history:** Dev Notes claiming a behavior exists that the code doesn't implement gets caught by every reviewer, every time. This story's Dev Notes make several load-bearing claims (fail-closed reserve vs. fail-open settle/release; the raw-SQL atomicity; the missing-row-blocks-identically-to-exhausted-budget behavior) — verify each one against the actual code before considering any task complete, the same self-check Story 1.6/1.7's own Completion Notes explicitly performed.
