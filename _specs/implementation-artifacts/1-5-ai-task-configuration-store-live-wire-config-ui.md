# Story 1.5: AI Task Configuration Store & Live-Wire Config UI

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an admin,
I want Story 1.1's UI to read and write real `AiTaskConfig` state,
so that config changes take effect on the next request with zero code deploy.

## Acceptance Criteria

1. `AiTaskConfig` (`Domain/AiConfig/`) is a real, persisted entity — one row per AI Task (`taskId`, `provider`, `model`, `fallbackProvider`, `fallbackModel`, `budgetThreshold`) — with `Application/AiConfig/IAiConfigService` (`GetAllTaskConfigsAsync`, `UpdateTaskConfigAsync`) and `Api/Controllers/AiConfigController` (`GET`/`PUT /api/v1/ai-task-configs`) exposing it. [Source: epics.md Story 1.5; ARCHITECTURE-SPINE.md AD-19]
2. `FrontEnd`'s `useAiTaskConfig.ts` (Story 1.1) is rewired to call the real endpoints instead of `MOCK_AI_TASK_CONFIGS` — behind the same `{ data, isLoading, error }` return shape — so that saving a row in the UI persists to the real store, and the next request for that task uses the new value immediately (no redeploy). `AiConfiguration.tsx` and `AiTaskConfigRow.tsx`'s markup/structure do not change; `AiTaskConfigRow.tsx`'s save-handling logic gets a deliberate, scoped update (AC #5). [Source: epics.md Story 1.5]
3. The dev-environment seed data assigns every AI Task a provider that does not train on input by default (NFR5) — matching Story 1.1's own mock precedent, every non-`embeddings` task seeds to `Groq`, `embeddings` seeds to `Local`. Changing a task away from this default is a visible, deliberate admin action (the existing Provider `<select>`), not a silent one. [Source: epics.md Story 1.5; PRD §4.14 NFR5: "free-tier dev usage... is restricted to providers that do not train on input by default"]
4. `AiPromptVersion` (`Domain/AiConfig/`) exists as a real, persisted, versioned entity (one seeded row per AI Task) — satisfying AD-19's "prompts/config for every AI Task live in this one centralized, versioned store." No UI or endpoint reads/writes it yet in this story (see Dev Notes — deliberately scoped out; nothing in Epic 1 needs to edit prompt text yet). [Source: epics.md Story 1.5: "prompts/config for every AI Task live in this one centralized, versioned store"; AD-19]
5. Because a real backend call can genuinely fail in ways the Story 1.1 mock never could, `AiTaskConfigRow.tsx`'s save action now distinguishes success from failure: a failed save shows an inline error (not a silent/incorrect "Saved!"), while a successful save behaves exactly as before. [Source: Dev Notes design decision below — a deliberate, justified, scoped deviation from a literal "zero consumer changes" swap, since silently treating every save as successful would hide a real functional regression against a live backend]

## Dev Notes

- **Sizing risk, acknowledged from planning (epics.md):** *"this is one of the larger stories in the plan — real entities, endpoints, and UI wiring in one pass. If it doesn't fit a single dev session, this is the natural split point: config store + endpoints first, UI live-wire second."* Tasks are grouped into **Backend** (1-7) and **Frontend** (8-11) precisely along that split point. If a single `dev-story` pass genuinely cannot complete both groups, it is acceptable to complete Backend fully (all 7 tasks, tests green, story left with Frontend tasks unchecked) and resume Frontend in a follow-up pass of the *same* story file — do not fabricate a "1.5b" story key or renumber anything; this file's own Tasks list already carries that state.
- **The `mockSpend` → `currentSpend` rename is deliberate, not a slip.** Story 1.7 (Usage & Cost Tracking Live-Wire) and Story 1.8 (Budget Threshold Enforcement) are what eventually make this field's value real (`AiTaskBudget`, AD-18) — until then it's a real API field that just always returns `0`, not a "mock" anymore in either direction. Keeping the old name would misleadingly suggest the field is still fake data. **Expected consequence, not a regression:** with `CurrentSpend` always `0`, `AiTaskConfigRow.tsx`'s existing `isOverThreshold = task.currentSpend >= task.budgetThreshold` check (after the rename) will never trigger until Story 1.7/1.8 land — the budget-warning UI goes quiet after this story ships, by design.
- **The `updateTaskConfig` async signature change is deliberate, not a "zero consumer changes" violation.** Every prior mock-to-real swap in this project (Stories 1.1-1.3's own hook-boundary convention) promised zero changes to consuming components. Here, `AiTaskConfigRow.tsx` currently has **no failure path at all** — it unconditionally shows "Saved!" the instant `onSave` is called, because a mock `setState` call can never fail. A real HTTP `PUT` genuinely can (network error, validation rejection, auth expiry) — silently telling an admin their provider/budget change saved when it didn't is a real functional regression against a *money-relevant* setting, not a cosmetic one. Fixing this requires `handleSave` to actually know whether the save succeeded, which requires an awaitable `updateTaskConfig`. This is the one deliberate exception to the "zero changes" pattern in this story, called out explicitly rather than silently introduced.
- **Prompt-version endpoints are deliberately out of scope for this story.** `AiPromptVersion` exists as a real entity + migration + seed (satisfying AD-19's "prompts... live in this centralized, versioned store" structural requirement), but no service method, controller action, or UI reads/writes it — nothing in Epic 1 (or the currently-planned Epic 2/3 stories, as far as this story's author can tell from `epics.md`) needs to *view or edit* prompt text yet; Story 1.1's UI never had a prompt-text field. Building CRUD/list/activate endpoints for a table nothing calls yet would be dead, untested surface area. If code review flags this as a gap, the correct resolution is "defer to whichever future story first needs to edit prompt text," not "add it now speculatively."
- **Backend must re-validate `BudgetThreshold >= 0` itself** (`AiConfigService.UpdateTaskConfigAsync`) — do not trust `AiTaskConfigRow.tsx`'s client-side `isThresholdValid` check alone; the frontend can be bypassed (a raw API call, a future non-web client).
- **Provider/Model are intentionally NOT validated against a closed backend enum.** FR-2's entire point is "a provider/model swap is a configuration change, never a code change" — hardcoding the frontend's `AI_PROVIDERS`/`AI_MODELS` arrays into a backend enum would silently defeat that (adding a new provider would require a backend redeploy again). Only non-empty-string validation applies server-side; the frontend's closed `<select>` dropdowns are a UX choice, not a data-integrity boundary this story should duplicate on the backend.
- **`useAiUsage.ts` (Story 1.2) is unaffected by the `AiTaskId`/`AI_TASK_IDS` exports staying unchanged** — it only imports those two, never `AiTaskConfig`/`mockSpend`/`updateTaskConfig`. Its own test (`useAiUsage.test.ts`) has one test asserting its mock usage totals reconcile against `useAiTaskConfig.ts`'s (now-removed) `MOCK_AI_TASK_CONFIGS.mockSpend` values — that specific test's premise no longer holds once the mock data is gone; remove or rewrite it (it was already documented in that story's own file as "moot once Story 1.7 replaces it with real backend-computed ranges" — this story is that removal point for the `useAiTaskConfig` side of the comparison, even though full replacement doesn't land until Story 1.7).

## Previous Story Intelligence

Story 1.4 (`1-4-ai-service-layer-interface-gateway-client.md`, status: done — closed after an 8-patch code review round):

- **The most valuable lesson from 1.4's review, directly applicable here too:** all 3 reviewers independently caught the same root-cause bug class — unguarded nested-null/malformed-response handling causing an unhandled exception instead of the documented failure path. The analog to actively guard against in `AiConfigService`/`AiConfigController`: don't assume the repository always returns a row for a validated `taskId` (guard with `NotFoundException`, per Task 4), and don't assume the frontend's `aiConfigService.ts` `get`/`write` helpers always get back well-formed JSON on a non-2xx response (mirror `masterDataService.ts`'s exact `problem?.detail || 'fallback'` guard, don't write a new, less-careful version).
- **1.4 also found**: a DI smoke test that duplicated registration code instead of exercising the real composition root, self-disclosed in that story's Completion Notes and caught anyway by 2 of 3 reviewers. This story's DI registrations (Task 6) are small enough that a dedicated DI test may not be warranted — but if one is written, exercise the real `AddInfrastructure()`/`AddApplication()`, not a hand-rolled duplicate (see 1.4's `AiGatewayDependencyInjectionTests.cs` for the corrected pattern).
- **Raw upstream/error content must never flow into a client-facing message unfiltered** — 1.4's review flagged this as a real info-disclosure risk. Not directly applicable here (no third-party upstream call in this story), but the same instinct applies to `AiConfigService`: don't echo raw exception details from a failed `SaveChangesAsync` (e.g. a Postgres constraint message) into a thrown `ValidationException`'s message — use a clear, first-party-authored message instead.
- **This is the first *frontend* change since Story 1.3** — re-read Story 1.3's own review findings once more before touching `useAiTaskConfig.ts`: that story's real bug was a `useEffect`-synced ref racing with a same-tick create-then-update call. The analog here: `updateTaskConfig`'s local-state patch (Task 9) happens inside a `.then()` after an awaited fetch — make sure nothing in `AiTaskConfigRow.tsx` (Task 10) assumes the patched `data` array is available synchronously right after calling `onSave()`, the way the old mock version was.
