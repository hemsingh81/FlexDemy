# Story 2.3: Course Content Editor UI (Mock Data)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

*(Sizing risk, not flagged in epics.md but real: this story adds tree CRUD, a confirmation state machine, keyboard+drag reorder, a new centered-modal primitive, and KaTeX+mhchem/Hindi rendering, all in one pass. If it doesn't fit a single dev session, the natural split is Tasks 1-3 (shell + data + read-only rendering) first, Tasks 4-6 (mutation/confirm/autosave behavior) second.)*

## Story

As a tutor,
I want a Chapter/Topic/Subtopic/Content-Block tree with add/edit/delete/reorder/confirm controls and subject-aware rendering, working against mock content,
so that the editor UX can be validated before backend wiring exists (Story 2.9 wires this to the real Chapter/Topic/Subtopic/ContentBlock entities).

## Acceptance Criteria

1. The tree extends the SAME `CourseContentEditor.tsx` screen Story 2.2 built (below the file list, in the same scrollable body), not a new/competing surface — Story 2.2's file-upload behavior, its `isOpen`/`onClose`/`draftId` contract, and its existing `aria-live` announcer all continue working unchanged. [Source: Story 2.2 Dev Notes/code comment: "Story 2.3 extends this same top component with the Chapter/Topic/Subtopic tree beneath the file list"]
2. Each Chapter/Topic/Subtopic/Content-Block renders as its own row: expand/collapse (Chapter/Topic/Subtopic only — Content Block is always a leaf), edit-in-place, delete, reorder among its own siblings, and an explicit per-node **Confirm** action distinct from having edited it. [Source: epics.md Story 2.3; EXPERIENCE.md "Course Content Editor — tree node" row]
3. Tree-node reordering is keyboard-operable — move-up/move-down controls equivalent to drag, not drag-only. Dragging is also supported (matching the Adaptive Schedule lesson planner as the product's only other drag surface), but keyboard operability is the AC, not the drag mechanic itself. [Source: epics.md Story 2.3 AC#1; UX-DR7]
4. Deleting a Chapter, Topic, or Subtopic (all three cascade-delete their descendants) goes through a new centered confirm-modal — never a plain click-and-it's-gone action. Deleting a leaf Content Block (no descendants) does not require the extra confirm step. [Source: epics.md Story 2.3 AC#2; UX-DR6; DESIGN.md `components.modal` — see Dev Notes for why Subtopic is included alongside Chapter/Topic despite the AC text naming only the latter two]
5. Each node's confirmed/unconfirmed state is visually exposed (never color-alone) per `{components.content-tree-node}`'s `confirmedState` token. Editing a Content Block's plain text preserves its confirmation state; editing its notation/image content, or adding/removing/reordering a node's children (a structural change), resets that node's confirmation to unconfirmed. When an edit auto-reverts a node from Confirmed to Unconfirmed, that reversion is announced at the moment it happens via a scoped `aria-live="polite"` region — reusing Story 2.2's existing announcer mechanism, not a second live region. [Source: epics.md Story 2.3 AC#3; FR15; UX-DR7; DESIGN.md `content-tree-node.confirmedState`]
6. Mock content includes math notation (KaTeX), chemistry notation (KaTeX+mhchem), an image-based diagram, and Hindi (Devanagari) text — all render correctly in the editor, and Hindi content blocks carry `lang="hi"`. [Source: epics.md Story 2.3 AC#4; FR16; UX-DR20 (editor side)]
7. Content Block edits autosave on edit-then-blur, per-node — never a single page-level "leave without saving?" prompt. [Source: epics.md Story 2.3 AC#4; UX-DR8]
8. Data access goes through a stable hook (`useCourseContentTree()`), never inline `useState`/mock-tree manipulation directly in the component tree, so Story 2.9 can swap the hook's internals from mock state to real Chapter/Topic/Subtopic/ContentBlock API calls without changing any component's code. [Source: epics.md Story 2.3 AC#4 hook-boundary clause; AD-1]

### Review Findings

- [x] [Review][Patch] Pressing Escape while `ConfirmModal` is open both cancels the modal AND closes/resets the entire Course Content Editor — `ConfirmModal.tsx`'s own Escape handler and `CourseContentEditor.tsx`'s pre-existing global Escape handler are two independent `document`-level listeners with no coordination; the outer one isn't gated on whether a delete confirmation is in progress. Reachable on the very first Escape press while cancelling any Chapter/Topic/Subtopic delete. [FrontEnd/src/ui/ConfirmModal.tsx; FrontEnd/src/features/CourseContentEditor/CourseContentEditor.tsx]
- [x] [Review][Patch] `ConfirmModal`'s focus trap is escapable on the very first Shift+Tab — focus lands on the outer panel `<div>` on mount (not a button), and the Tab handler only intervenes when `document.activeElement` is exactly the first or last `<button>`; from the container itself, a Shift+Tab falls through to native behavior and escapes the trap entirely. [FrontEnd/src/ui/ConfirmModal.tsx]
- [x] [Review][Patch] `renderNotation.ts`'s error-fallback path returns the raw, tutor-editable `notation` string unescaped, which `ContentTreeNode.tsx` then renders via `dangerouslySetInnerHTML` — a latent injection path if KaTeX ever throws on pathological input despite `throwOnError: false` (which suppresses most but not all internal errors). [FrontEnd/src/features/CourseContentEditor/renderNotation.ts]
- [x] [Review][Patch] Chapter/Topic/Subtopic title fields all share identical, non-unique `aria-label`s ("Chapter title", "Topic title", "Subtopic title" with no per-node identifier) — unlike Content Block fields, which already include a position index. A screen-reader user tabbing through the tree can't distinguish which node's title field they're on. [FrontEnd/src/features/CourseContentEditor/ContentTreeNode.tsx]
- [x] [Review][Patch] Clearing a node's title to empty and then deleting it produces a confusing confirmation message — `` `Delete "" and everything inside it?` `` — on a destructive, cascading safety gate. [FrontEnd/src/features/CourseContentEditor/CourseContentEditor.tsx]
- [x] [Review][Patch] `nextNodeId`'s module-level counter can collide with the seed tree's hardcoded literal ids (`chapter_1`, `topic_1`, `block_1`, etc.) — the very first `addNode`/`addChapter` call in a session can generate an id identical to an existing seed node's id, after which mutators matching by `id ===` silently operate on both nodes at once. The single most load-bearing finding from this review (independently identified as such by two review layers). [FrontEnd/src/features/CourseContentEditor/useCourseContentTree.ts]
- [x] [Review][Patch] `prevConfirmationsRef` (new in this story) is never pruned when nodes are deleted — it only grows for the life of the mounted component, accumulating entries for nodes that no longer exist. [FrontEnd/src/features/CourseContentEditor/CourseContentEditor.tsx]
- [x] [Review][Patch] `useCourseContentTree`'s tree state is never reset when `draftId` changes or the editor closes — unlike `useFileUpload`'s `resetFiles()`, the content-tree hook has no reset API, so opening Course Content Editor for a second, different course still shows the first course's edited Chapters/Topics/confirmations. The same class of bug already fixed for the file list in this exact component during Story 2.2's own review pass, now recurring for the new tree state. [FrontEnd/src/features/CourseContentEditor/useCourseContentTree.ts, CourseContentEditor.tsx]
- [x] [Review][Patch] Native HTML5 drag-and-drop reorder was never implemented despite Task 5 being checked off and this story's own Completion Notes/Change Log claiming "keyboard+drag reorder" — `ContentTreeNode.tsx` has no `draggable`/`onDragStart`/`onDragOver`/`onDrop` anywhere. AC#3 and Task 5 both explicitly required it as a supported (if secondary) input method, matching the Adaptive Schedule lesson planner. A false-complete checkbox and an inaccurate Change Log claim, not just a gap — the fix is to actually build it, not just correct the record. [FrontEnd/src/features/CourseContentEditor/ContentTreeNode.tsx, useCourseContentTree.ts]

Dismissed as noise (verified, not real defects for this story's scope): confirmation state not cascading upward to ancestors, and `confirmNode` not checking whether descendants are also confirmed, is exactly what this story's own Dev Notes already documented and deliberately scoped ("Structural reorder/add/delete resets only the immediately affected node's confirmation, not an upward cascade... a deliberate, separate scope decision" if ever needed) — re-flagging it isn't a new finding; the inability to create `'math'`/`'image'`-format Content Blocks through the "Add" UI (only `'text'` defaults are creatable) is equally already-documented, explicit scope in Task 5 ("no format-picker UI... in scope for this story"); every tree mutator rebuilding the whole array on each call is a real but currently-harmless performance characteristic appropriate for this story's small mock fixture, not a functional defect; and mutators silently no-op-ing on a nonexistent id, `editContentBlock`'s empty-patch edge case, and focus-restoration to a since-removed DOM element are all real but currently-unreachable defensive-programming gaps with no live trigger in this UI today.

## Dev Notes

- **This is a mock-data-only story.** No backend call, no `extractStructure()` AI call, no real Chapter/Topic/Subtopic/ContentBlock persistence — Story 2.9 wires this to the real entities. The entire point of Task 2's hook boundary is that Story 2.9 changes only `useCourseContentTree.ts`'s internals and touches zero tree-rendering component code.
- **Why Subtopic is included in the confirm-modal requirement even though the AC text only names Chapter/Topic.** EXPERIENCE.md's own framing is "Deleting a Chapter or Topic cascades to every descendant node — a genuinely destructive, hard-to-undo action... deleting a leaf Content Block... does not need the extra confirm step" — it names the two ends (cascading vs. true leaf) but a Subtopic is neither: it cascades its own Content Block children away just as destructively as a Chapter/Topic deletion does. Treating "has descendants that get cascade-deleted" (not "is specifically named Chapter or Topic") as the actual test is the conservative, safer reading and the one consistent with the underlying principle the AC is protecting. If this reading is wrong, it's a one-line change (drop the Subtopic branch from the confirm check) — flagging the reasoning here so it's an easy, deliberate override rather than a silent guess.
- **`ConfirmModal.tsx` is new, not a reuse of `ConfirmDialog.tsx`.** Confirmed via direct research: `ConfirmDialog.tsx`'s own doc comment says it is explicitly "not a modal" — it's an inline row-action-swap (`MasterDataTable.tsx`'s row delete), dismissed via `useClickOutside`, no backdrop. The epics.md AC's "centered confirm-modal pattern" needs `{components.modal}`'s actual shell (backdrop + centered panel) — genuinely new. Build it as a shared `ui/` primitive (not feature-local) since `{components.modal}` is a cross-app design token already informally duplicated in `FlashcardsModal.tsx`'s inline CSS; a real reusable component is the more correct target for future destructive-action call sites, not a one-off inside `CourseContentEditor/`.
- **KaTeX+mhchem is genuinely new capability, not already working.** Confirmed via research: `katex` is installed and used in two places (`DrilldownPanel.tsx`, `ReaderCanvas.tsx`), both via `katex.renderToString(str, { throwOnError: false, displayMode: true })`, copy-pasted per file with no shared helper. Neither currently imports `katex/contrib/mhchem` — chemistry notation is unsupported today. This story's Task 3 adds that import (ships inside the already-installed `katex` package, no new dependency) for its own local helper; it does not retrofit the two existing call sites (out of scope, unrelated files).
- **Hindi/Devanagari is genuinely new too.** Confirmed via research: no `lang="hi"` or Devanagari handling exists anywhere in the codebase today. No special font-stack work is implied by the AC beyond the `lang` attribute itself — browsers already render Devanagari Unicode correctly with system fonts; `lang="hi"` is what lets a screen reader switch pronunciation, which is the actual accessibility requirement (per EXPERIENCE.md's Accessibility Floor "Hindi (Devanagari) content — language of parts" note, distinct from the KaTeX alt-text requirement).
- **Structural reorder/add/delete resets only the immediately affected node's confirmation, not an upward cascade.** E.g. adding a Content Block under a Subtopic resets that Subtopic's confirmation, not its parent Topic's or Chapter's. No AC requires cascading the reset upward, and FR15's own wording ("a structural... edit resets it") reads as scoped to the node whose own content/children changed. If a future story needs upward cascade, that's a deliberate, separate scope decision, not something to guess into this one.
- **Out of scope, explicitly:** the Draft → In Review → Review Confirmed → Published sticky-header lifecycle indicator EXPERIENCE.md's Accessibility Floor mentions living in "the editor's sticky header" is Epic 3 territory (the Publishing Lifecycle UI story) — don't build it here. `describeNotation()` AI-generated alt-text for math/chemistry notation is Story 2.10's job, not this one's — this story's `altText` field on image blocks is tutor/mock-authored placeholder text, not AI-generated. Real `extractStructure()`-driven population of the tree (vs. this story's hand-seeded mock fixture) is Story 2.8's job.
- **No new state-management library** — `useState` only inside `useCourseContentTree.ts`, matching AD-4's "no redux/zustand/jotai" rule. Feature-local hook (single-feature state, not yet the confirmed-tree-shared-with-CoursePlayer's-Review-as-Student-mode state — that's `CourseContentContext`, still correctly out of scope until Story 2.9 per Story 2.2's own established reasoning).
