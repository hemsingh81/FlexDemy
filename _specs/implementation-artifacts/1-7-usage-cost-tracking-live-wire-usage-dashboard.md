# Story 1.7: Usage & Cost Tracking & Live-Wire Usage Dashboard

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an admin,
I want every AI Task invocation's token usage and cost recorded and shown live in Story 1.2's dashboard,
So that spend is attributable, auditable, and no longer mock data.

## Acceptance Criteria

1. Every successful `IAiTaskGateway` invocation (whether served by the primary or the fallback provider) records its token usage and computed cost, attributed to the AI Task and — where the caller supplied it — the course/tutor that triggered it. [Source: epics.md Story 1.7; PRD FR-4: "The gateway records token usage and computed cost for every AI Task invocation, attributed to the task and (where applicable) the course/tutor that triggered it."]
2. A failed invocation (`AiTaskUnavailableException` — both primary and fallback failed, Story 1.6) records nothing: there is no successful response to compute usage/cost from, so no `AiTaskUsage` row is written for that call. [Source: epics.md Story 1.7 AC framing ("every AI Task invocation completes... the response returns") — a call that never returns a response has nothing to record; PRD FR-4 is scoped to invocations that produce a response]
3. Story 1.2's usage/cost dashboard (`AiConfiguration.tsx`'s "Usage & Cost" section) reads real recorded usage/cost data from a new backend endpoint instead of `useAiUsage.ts`'s mock dataset, behind the same `{ data, isLoading, error, dateRange, setDateRange }` shape `useAiUsage.ts`'s own header comment already names as this story's job — `AiConfiguration.tsx` itself does not need to change shape, though its previously-inert `isLoading`/`error` values (always `false`/`null` in mock mode) now carry real state and should be surfaced in the UI, per that same file's header comment ("loading/error UI... will likely be added at that point"). [Source: epics.md Story 1.7; FrontEnd/src/features/Admin/AiConfiguration/useAiUsage.ts header comment, AiConfiguration.tsx header comment — both read in full this session]
4. Admin's usage/cost view supports the same 3 date ranges the mock already establishes (`last7`, `last30`, `all`), filtered server-side (not by fetching everything and filtering client-side), and remains filterable/viewable by AI Task the same way the existing `AiUsageSummary.tsx`/`AiUsageChart.tsx` client-side aggregation already does per task. [Source: epics.md Story 1.7; PRD FR-28: "Admin's usage/cost view (FR-28) can be filtered by AI Task and by date range."]

## Dev Notes

- **Where cost comes from (the real architectural gap this story fills):** no prior AD names a per-token price source anywhere in this codebase — `AiTaskConfig` (AD-19) holds `Provider`/`Model`/`FallbackProvider`/`FallbackModel`/`BudgetThreshold` but never a rate. FR-4/FR-28 require "computed cost," which needs one. Since `Provider`/`Model` are open, admin-editable free-text strings (FR-2's "no redeploy" guarantee — see `useAiTaskConfig.ts`'s own comment: "The backend does NOT validate against a closed enum"), the system has no way to look up a real-world $/token rate for an arbitrary provider/model pair from a static table — the admin is the only party who could know it. This story's decision: add `PricePerMillionInputTokens`/`PricePerMillionOutputTokens` directly to `AiTaskConfig` (Task 1), the natural existing per-task-provider home (same entity `BudgetThreshold` already lives on), rather than a new separate pricing-lookup entity keyed by (Provider, Model) — simpler, no new admin surface, and a task's fallback provider is expected to be a similar-tier backup (not a wildly different price point), so **one price pair covers both the primary and fallback provider for a task**, not 4 separate fields. This is a deliberate simplification, not an oversight — flag it in review if it should instead be per-(Provider,Model) or per-(primary/fallback) precision; either is a straightforward follow-up, not a rework, since the schema/DTO shape absorbs either change without touching `AiTaskGateway`'s call site.
- **Pricing is read-only in this story — deliberately not added to `AiTaskConfigRow.tsx`'s edit UI.** No UX design (`DESIGN.md`) specifies a pricing-edit control, and neither this story's AC nor FR-4/FR-28 asks for admin-editable pricing — only for cost to be *computed and shown*. Inventing new admin UI beyond what's spec'd would violate this project's UX-design-first discipline (every other admin screen in this session traced back to an explicit `DESIGN.md`/`EXPERIENCE.md` section). The DB column and `AiTaskConfigDto` field exist and are seeded (Task 1); a future story can add an edit control to `AiTaskConfigRow.tsx` without any backend rework. `UpdateAiTaskConfigRequest` deliberately does NOT gain these 2 fields — the existing PUT endpoint stays scoped to what `AiTaskConfigRow.tsx` actually edits today.
- **Seeded pricing is `0m`/`0m` for all 7 tasks — this is correct, not a stub.** Every seeded provider (`Groq`, `Local`) is genuinely free-tier in this dev-phase environment (PRD's own cost-control framing: "Free/cheap-tier models... by default in dev"). A real $0.00 computed cost for a free-tier call is the *accurate* number — do not seed a fake nonzero placeholder rate just so the dashboard shows non-zero numbers; that would make the live data less correct than the mock data it's replacing.
- **`AiTaskGateway` (Story 1.6, already `done`) is being extended, not rewritten.** This is expected, normal story-to-story evolution — Story 1.6's own Dev Notes named `IAiTaskGateway` as infrastructure with no real caller yet, and this story is the first to add a genuine cross-cutting concern (usage recording) to its one shared choke point (`DispatchAsync`/`GenerateEmbeddingAsync`, both already funnel every call through a single post-success point regardless of which provider served it — exactly why AC #1's "regardless of success/fallback path" and AC #2's "failure records nothing" both fall out of *where* the recording call is placed, not from any new conditional logic).
- **`CourseId`/`TutorId` attribution is real but currently always `null` in practice.** Nothing in Epic 1 calls `IAiTaskGateway` with actual course/tutor context yet (same "no real caller yet" state Story 1.6 documented) — the 2 new optional `AiTaskRequest`/`GenerateEmbeddingAsync` parameters exist so the schema and recording logic are ready for whichever Epic 2/3 story becomes the first real caller, per FR-4's explicit "(where applicable)" framing (some AI Tasks, like a platform-wide `embeddings` call, may never have one). Don't invent a caller or a course/tutor lookup here — there is nothing in this story's scope to attribute to yet.
- **Only successful invocations produce a usage row (AC #2).** `AiGatewayException` (Story 1.4) and `AiTaskUnavailableException` (Story 1.6) carry no `AiGatewayUsage` payload — a rejected/failed call has no token counts to record, so there is genuinely nothing to bill, not a gap to work around. Do not add a "record a zero-cost failure row" path — nothing in the ACs asks for failure-tracking here (that's closer to Story 1.8's/observability's territory, not this story's).
- **`Story 1.5`'s deferred item ("`aiConfigService.ts`'s `get`/`write` don't guard `response.json()` against a non-JSON/empty body") applies identically to the new `aiUsageService.ts` if you copy `aiConfigService.ts`'s helpers verbatim — that's fine, matching the existing pattern is correct here, not a new gap to fix in this story.**
