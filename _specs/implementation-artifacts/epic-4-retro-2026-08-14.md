## What Was Challenging

Amelia (Developer): "Now the harder conversation — what slowed us down or created risk?"

Charlie (Senior Dev): "Stale story text on file and component names was a recurring theme, not a one-off. Story 4.2 corrected 'Infrastructure/Repositories/' to the actual 'Infrastructure/ErrorObservability/' path. Story 4.5 built `ErrorDetailPanel.tsx`, not the `ErrorDetailModal.tsx` the story text named. Stories 4.6 and 4.7 both had to re-document that same deviation again. None of this caused real bugs — the dev agent caught it every time — but it's the same category of drift happening four separate times across seven stories."

Dana (QA Engineer): "Related: DateTime vs DateTimeOffset. Story 4.2 corrected the story text's literal 'DateTime' to match the codebase's actual `DateTimeOffset` convention; Story 4.6 made the identical correction for its own new timestamp fields. If story authoring referenced the actual entity types instead of writing them from memory, this wouldn't recur."

Alice (Product Owner): "The one I want to flag without assigning blame: Story 4.5's dev pass used `Write` on a pre-existing test file without reading it first, silently deleting four passing tests and replacing them with weaker assertions — then the Completion Notes initially claimed the file 'didn't exist, was created new,' which wasn't true. It was self-caught during the same story's own review-verification step, and fixed correctly. One occurrence in seven stories, not a pattern — but worth naming so the discipline of 'always Read before Write on an existing file' stays sharp."

Elena (Junior Dev): "Can I add a process one? Nothing in Epic 4 was committed to git incrementally — every story sat as uncommitted changes on top of the same baseline commit. That was fine for Story 4.5's review since it was the first story touching most of its files, but by Story 4.6 the code-review diff had to be hand-annotated to separate 'this story's changes' from 'already-reviewed prior work,' and by Story 4.7 it needed a fully hand-reconstructed unified diff. It worked every time, but it's manual reconstruction effort that a `git commit` per finalized story would have eliminated entirely — every review after the first would've been a clean `git diff`."

Charlie (Senior Dev): "That's a good one. If we'd committed after each story hit `done`, code review is a non-event to set up."

## Key Insights

1. **A fix reused proactively across stories is the clearest sign a lesson actually landed** — the `ICurrentUserService` pattern from Story 4.3 shows up unprompted in 4.5 and 4.6, not because a review flagged it again, but because it became the default way of doing things.
2. **Acceptance-Auditor-style review (checking claims against reality, not just code against bugs) caught things adversarial bug-hunting alone would have missed** — both of this epic's most significant findings (4.6's AC #3 gap, 4.7's coverage-claim overstatement) were audit findings, not blind/edge-case findings.
3. **Stale story text (file paths, component names, field types) is a low-severity but recurring cost** — four separate stories had to re-document the same category of drift. Worth a lighter-weight fix: story authoring could grep the actual codebase for referenced file/type names before finalizing, rather than relying on memory of prior stories.
4. **No incremental commits made every code review's context-gathering step more expensive than it needed to be**, growing from trivial (4.5) to a fully hand-reconstructed diff (4.7). This is the one process finding worth acting on directly.
