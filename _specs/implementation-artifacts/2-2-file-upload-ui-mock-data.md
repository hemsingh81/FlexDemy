# Story 2.2: File Upload UI (Mock Data)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a tutor,
I want to upload multiple files and see independent per-file progress and status, simulated against mock state,
so that the upload UX can be validated before real parsing exists (Stories 2.6/2.7 wire this to real scanning/parsing).

## Acceptance Criteria

1. Multiple files can be selected in one picker action; each accepted file renders as its own row with its own status — never a single combined progress bar for the whole batch. [Source: epics.md Story 2.2 AC#1; FR11]
2. Each file row cycles through a mock status sequence — `Queued → Parsing → Extracting → Done` (or `Failed`) — driven by a timed mock simulation (no real network/parsing call). The status renders via the existing `{components.badge-pill}` semantic colors: navy fill for the three in-progress states (Queued/Parsing/Extracting), `{colors.signal-green}` (`#179765`) for Done, `{colors.error}` (`#DC2626`) for Failed — no new color language. [Source: epics.md Story 2.2 AC#2; epics.md UX-DR9; DESIGN.md `extraction-status-badge`]
3. Each file's status transition is announced via a scoped `aria-live="polite"` region. If several files complete near-simultaneously, their announcements batch into one update rather than firing one region-mutation per file in a flood. [Source: epics.md Story 2.2 AC#2; epics.md UX-DR9]
4. A Failed file shows an inline retry action scoped to that file only — retrying does not affect any other file's status or progress. [Source: DESIGN.md `extraction-status-badge` "(with an inline retry action scoped to that one file)"; NFR4]
5. Data access goes through a stable hook (`useFileUpload()`), never inline `useState`/mock-array manipulation directly in step components, so Stories 2.6/2.7 can swap the hook's internals from a timer-driven mock to real upload/scan/parse calls without changing any component's code. [Source: epics.md Story 2.2 AC#2 hook-boundary clause; AD-1]
6. This screen is reachable via a real, permanent entry point — completing the Course Metadata Wizard (Story 2.1) now opens this screen, matching the "Advancing past Step 4..." continuation described in EXPERIENCE.md's UJ-1 — not left unreachable pending a later story. [Source: EXPERIENCE.md UJ-1 step 2; established Phase-A entry-point precedent from Stories 1.1 and 2.1's own Task 1]
7. This screen renders as a full-width surface (a takeover, not a `{components.side-panel}` blade) — consistent with Course Content Editor's own UX-DR5 "not a side-panel step" requirement, since this story's file-upload UI is the first-built slice of that eventual full-width Course Content Editor screen (see Dev Notes). [Source: epics.md UX-DR5; EXPERIENCE.md Component Patterns "Extraction status indicator" row attributing this UI to "Course Content Editor"]

Finishing the wizard a second time reopens Course Content Editor still showing the first course's uploaded files, misattributed to the new draft — reachable via the wizard's only forward path, not a rare edge case. Three independent review layers converged on this same root cause. Currently latent (the component is always mounted per the finding above), but becomes live the moment that's fixed with real conditional mounting. [FrontEnd/src/features/CourseContentEditor/useFileUpload.ts]

[FrontEnd/src/features/CourseContentEditor/CourseContentEditor.tsx]
- [x] [Review][Patch] The Dashboard's "New Course Wizard" trigger stays reachable (keyboard-tabbable, unguarded) while Course Content Editor is open, and `CourseContentEditor`'s `z-40` sits below `SidePanel`'s `z-50` with no shared z-index scale — a keyboard user can open a second `CourseWizard` session on top of an already-open Course Content Editor. ## Dev Notes

- **This is a mock-data-only story.** No backend call, no real upload/scan/parse — Stories 2.6 (malware scan + secure storage) and 2.7 (Docling parsing/OCR) wire this to real services later. The entire point of Task 2's hook boundary is that those stories change only `useFileUpload.ts`'s internals and touch zero component code.
- **Why `CourseContentEditor/`, not a new `FileUpload/` folder.** `ARCHITECTURE-SPINE.md`'s Structural Seed names exactly two new folders for the New Course Wizard PRD: `CourseWizard/` (Story 2.1's 4 metadata steps) and `CourseContentEditor/` (the eventual full-width tree editor, Story 2.3). There is no third "file upload" folder in the seed. `EXPERIENCE.md` independently and repeatedly attributes per-file upload/extraction status to "Course Content Editor" as the surface — its Component Patterns table's "Extraction status indicator" row, its State Patterns table's "File parsing/extraction in progress" row, and UJ-1's "Advancing past Step 4 opens Course Content Editor as a new full-width surface... she drags her scanned PDF in" all place file upload *inside* Course Content Editor, not as a separate screen. This story therefore creates `CourseContentEditor/` now and builds only its upload/status-list slice; Story 2.3 extends the same folder and top component with the Chapter/Topic/Subtopic tree beneath the file list — an incremental build of one screen across two stories, not two competing screens. **This does not contradict Story 2.1's "don't build a Course Content Editor placeholder" boundary** — that boundary was about not faking the tree/editing content Story 2.3 owns; it says nothing about a different feature (file upload) that the UX artifacts explicitly place in this folder.
- **Why the entry point is wired now, not deferred.** Both prior Phase-A mock stories in this project (1.1's new Admin sub-tab, 2.1's rewired Dashboard trigger) gave their screen a real, reachable, permanent entry point as part of the same story — never "build it, wire it up later." Story 2.2 follows the same discipline: `CourseWizard`'s `onComplete` currently just closes the wizard (a deliberate Story 2.1 stub, since this screen didn't exist yet); this story is what gives that stub somewhere real to go, matching UJ-1's literal next step. **This deliberately supersedes Story 2.1's own stated plan** — its AC#10 and Dev Notes explicitly said Course Content Editor "doesn't exist until Story 2.3" and that this story's "'done' state is onComplete firing, not a real screen transition." That was true when 2.1 was written; it stops being true the moment this story lands, since this story is what builds the first real slice of Course Content Editor. Acceleration, not an oversight — don't read Story 2.1's file as still-binding scope for what THIS story may build.
- **`CourseContentContext` (AD-4) is Story 2.3/2.9's concern, not this one's.** ARCHITECTURE-SPINE.md's Structural Seed describes `CourseContentEditor/` as reading/writing `CourseContentContext` — but that Context holds the *confirmed content tree*, which doesn't exist until Story 2.9 builds it. This story's file-upload/status state is legitimately feature-local under AD-4's single-feature carve-out (nothing outside this screen needs it yet), so `useFileUpload.ts` stays a plain feature-local hook, no Context wrapping. Story 2.3, when it extends this same `CourseContentEditor.tsx` with the real tree, is what introduces `CourseContentContext` — don't add it preemptively here.
- **UJ-1's "she drags her scanned PDF in" is narrative color, not a literal drag-and-drop requirement.** EXPERIENCE.md's own Do's/Don'ts list names exactly two drag surfaces in the entire product — the Adaptive Schedule lesson planner and Course Content Editor's *tree-node reordering* (a later story) — "no drag anywhere else." File upload is not one of them. The hidden-input-plus-button idiom (Task 3, matching `StepThumbnails.tsx`) is the correct, spec-consistent choice; it is not a scope cut against the user journey's prose.
- **Full-width takeover, not a blade.** UX-DR5 is explicit that Course Content Editor is "a new full-width surface (not a side-panel step)." Don't reuse `SidePanel` here even though it's the readiest-to-hand shell — build `CourseContentEditor.tsx`'s own shell (a `fixed inset-0` full-viewport takeover is sufficient for this story's scope; don't build real `App.tsx`-level route/feature-switching for this — that's a larger architectural change out of scope for a file-upload mock story, and nothing in this story's ACs requires it).
- **Mock failure rate is a deliberate design choice, not a literal spec number.** No AC specifies an exact failure probability — "roughly one in several" is this story's own reasonable choice so the Failed/retry path (AC#4) is naturally reachable in ordinary multi-file demo usage without every file needing manual intervention to reach it. Implement as a single named constant (e.g. a modulo/index check) so it's trivially tunable later.
- **Badge colors are the same "existing-code hex convention, not new CSS variables" tradeoff already made in Stories 1.1/2.1** — `DESIGN.md`'s Do's/Don'ts aspirationally prefers CSS variables in new code, but every existing badge-pill implementation in this codebase (including Story 2.1's own `StepThumbnails.tsx` Primary badge) uses raw hex. Match existing convention; don't introduce a CSS-variable layer unilaterally in this story.
- **No new state-management library** — `useState` + `setTimeout` only inside `useFileUpload.ts`, matching AD-4's "no redux/zustand/jotai" rule. Feature-local hook (single-feature state), not a `Context` candidate.
- **Scope boundary:** this story does not build the Chapter/Topic/Subtopic tree, does not call `extractStructure()`, and does not implement real file validation/scanning/parsing — those are Stories 2.6, 2.7, and 2.8's jobs respectively. `useFileUpload()`'s mock simulation existing at all is exactly the contract those stories need to build against.
