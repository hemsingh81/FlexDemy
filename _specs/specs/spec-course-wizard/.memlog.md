- (direction) Why: today a tutor authors course structure by hand with no help and no way to teach an idea at more than one depth or style; a student gets whatever single explanation the tutor wrote. This module lets a tutor turn raw material into a structured course via AI-assisted extraction (tutor edits/confirms, never auto-published), and gives students an adaptive way to understand any topic at their own depth and in their own preferred style. The AI itself is architected as swappable -- free/cheap models in dev, best-fit model at launch -- via configuration only, never a rewrite
- (capability) CAP-1 Pluggable AI backbone -- intent: every AI-driven feature in this module calls one internal, provider-agnostic AI service layer, never a vendor SDK directly, so the model/provider powering any task is a config choice not a code dependency (PRD FR-1-FR-5, FR-27-29; architecture backend AD-14, AD-19). success: an admin changes an AI Task's provider/model/fallback/budget in config and it takes effect on the next request with zero code deploy (PRD UJ-3)
- (capability) CAP-2 Course metadata wizard -- intent: tutor sets Title, Tags (admin-governed vocabulary, no free text), cascading Taxonomy (Country->State->City->Board->Class->Subject, admin-governed), and up to 3 cropped Thumbnails before content authoring begins (PRD FR-6-10). success: a course cannot advance past metadata with a required field unset; state auto-persists as Draft at every step
- (capability) CAP-3 AI-assisted content structuring from uploads -- intent: tutor uploads source files (PDF/Word/TXT/Excel), the system parses (incl. OCR for scans) and proposes a Chapter->Topic->Subtopic->Content structure the tutor can add/edit/delete/reorder/confirm before it's usable (PRD FR-11-15). success: per-file failure never blocks other files' extraction; a course cannot reach Review as Student while any node is unconfirmed
- (capability) CAP-4 Subject-aware WYSIWYG parity -- intent: math/physics, chemistry (formulas+reactions as notation, structural diagrams as images), biology diagrams, and English/Hindi text render identically between the tutor's editor and the student's live view (PRD FR-16). success: golden-file visual-regression tests catch drift between editor and student rendering for math/chemistry/Hindi content (UX AD-6)
- (capability) CAP-5 Five-level drill-down -- intent: every Topic/Subtopic exposes 5 progressive AI-generated depth levels of the same explanation, revealed one at a time by student choice, tutor-overridable (PRD FR-17). success: a student never sees level N+1 content before expanding level N; a tutor override is served in place of AI content for that level going forward
- (capability) CAP-6 Five alternative explanations (Ways) -- intent: every Topic/Subtopic exposes 5 AI-generated alternative explanations of the same idea, each with its own worked example, freely cycled by student choice, secondary in UI weight to drill-down (PRD FR-18). success: all 5 Ways have both explanation and example; cycling is unordered, not sequential
- (capability) CAP-7 Optional practice exercises -- intent: tutor optionally attaches AI-proposable or self-authored exercises per node; students get inline, subject-appropriate practice with immediate feedback (PRD FR-19). success: a node with no exercise shows no practice affordance at all -- not a disabled state
- (capability) CAP-8 Click-any-keyword definitions -- intent: any keyword in content is clickable for an inline, subject/language-aware AI-generated definition, tutor overrides take priority, routed to the cheapest AI Task tier given expected volume (PRD FR-20). success: the same keyword in two different-subject courses can surface different, correct definitions
- (capability) CAP-9 Pre-generated, cached adaptive content -- intent: drill-down and Ways content generates as an async batch at publish time (not on-demand per view), with per-node failure falling back to on-demand generation rather than ever showing empty content (PRD FR-21; architecture backend AD-15-AD-18, AD-20). success: opening a drill-down level or Way as a student returns cached content with no visible AI-generation latency; a failed node's generation never surfaces as broken to the student
- (capability) CAP-10 Draft to Review to Publish lifecycle -- intent: a course moves Draft -> In Review -> Review Confirmed -> Published; the tutor must experience the full course exactly as a student would (Review as Student) and explicitly confirm before Publish becomes available; post-publish edits are versioned (PRD FR-22-25). success: Publish is unreachable from any state before Review Confirmed; a small (text-only) edit to a confirmed node skips re-review, a structural or AI-content-affecting edit does not
- (capability) CAP-11 Admin tag governance -- intent: admin CRUD over a shared Tag vocabulary (add/rename/deactivate/search, dedupe), net-new work not an extension of the taxonomy master-data system (PRD FR-26). success: a deactivated tag stays attached to courses that already had it but can't be newly selected
- (capability) CAP-12 Admin AI configuration, usage & budget control -- intent: admin views/sets per-AI-Task provider, model, fallback, and budget threshold, and sees usage/cost broken out by task and date range (PRD FR-27-29). success: a budget threshold blocks a request before it would exceed spend (pre-flight, not post-hoc recording -- architecture backend AD-18)
- (constraint) AI provider/model swap must be a config change only, never a code change, including across the managed-to-self-hosted gateway migration -- rules out static appsettings.json-only config for AI task settings (PRD FR-2; backend AD-19)
- (constraint) WCAG 2.1 AA floor, product-wide -- rules out color-alone state signaling, drag-only interactions with no keyboard equivalent, and unannounced async state changes (UX EXPERIENCE.md Accessibility Floor)
- (constraint) No commercial/copyleft-risk dependencies matching the MediatR/AutoMapper pattern already rejected -- every new library choice (Hangfire, Polly, Vitest browser-mode) was picked and verified against this bar (backend AD-3, AD-14, AD-15)
- (constraint) Backend: Clean Architecture (Onion), dependencies point inward only, feature-folder organization, DTO-only service boundaries, single SaveChangesAsync per use-case except the explicit AD-16 batch-job carve-out (backend AD-1-AD-20). Frontend: feature-folder + repository/service data-access boundary, full-width no-max-w responsive, brand tokens (navy/amber/parchment/Fraunces+Outfit) (frontend AD-1-AD-6, UX DESIGN.md)
- (constraint) Dev-phase AI usage on real-ish student content restricted to providers that don't train on input by default -- rules out using a free tier that trains on input (e.g. a provider's default free tier) for anything beyond synthetic content (PRD S4.14, addendum.md)
- (non-goal) No auto-generated full assessments/quizzes beyond per-topic optional exercises; no student enrollment/consumption-analytics dashboards; no monetization; no collaborative multi-tutor editing; no automatic personalization (system never auto-selects a student's depth/style -- student always chooses); no bulk/API course import; does not rebuild taxonomy admin (reuses existing MasterDataManager); fully supersedes and removes the old 4-step Course Creation Wizard rather than extending it (PRD S5; frontend AD-3 seed note)
- (decision) Success signal: (1) % of topic/subtopic views engaging Drill-Down or Ways, (2) student self-reported understanding rate per topic, (3) % of AI-extracted structure confirmed with no/minor edits, (4) Draft->Published conversion rate, (5) cost per generated topic staying within its configured budget threshold across dev-free-tier and production. Counter-metrics: extraction-acceptance rate must not be gamed by vaguer structures; adaptive-mode engagement must not be gamed by weakening Level 1/Way 1; cost-per-topic must not be hit by degrading model quality below what comprehension requires (PRD S7, SM-1-5 + SM-C1-3)
